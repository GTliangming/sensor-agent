# AI Video Studio：ComfyUI 接入、本地运行与部署

## 1. 文档目标

本文说明如何把 Python 后端与 AutoDL.Art 上的 ComfyUI 工作流连接起来，并为后续本地开发、任务执行、文件存储和微信云托管部署做好准备。

目标工作流：

```text
React 前端
    ↓
FastAPI 后端
    ↓
数据库创建任务
    ↓
Python Worker
    ↓
AutoDL.Art API
    ↓
ComfyUI 工作流
    ↓
MiniMax H3 图生视频
    ↓
获取 MP4 视频
    ↓
保存结果并更新数据库
    ↓
前端查询任务和播放视频
```

## 2. AutoDL 与 ComfyUI 的职责

### 2.1 AutoDL.Art

负责 GPU 实例、模型运行环境和外部 API 访问能力。

### 2.2 ComfyUI

负责执行具体的生成工作流，包括输入图片、提示词、模型节点、采样参数和视频输出节点等。

### 2.3 MiniMax H3

负责实际的视频生成能力。具体输入参数、支持的画幅、时长和输出格式应以当前部署的模型及工作流为准。

### 2.4 Python 业务后端

不直接运行模型，而是通过 HTTP API 调用外部工作流。

这种方式可以降低本地开发环境要求，也可以避免业务服务和模型运行环境耦合。

## 3. 开始开发前的必要信息

先从 AutoDL 控制台或当前工作流配置中确认以下信息。

| 信息 | 用途 |
|---|---|
| API 基础地址 | 确定请求发送到哪里 |
| API Token | 进行外部服务认证 |
| Workflow ID | 指定需要执行的工作流 |
| 提交任务的 HTTP 方法 | 通常是 POST，但必须核实 |
| 提交请求体 | 确认提示词和图片如何传递 |
| 外部任务 ID 字段 | 用于后续查询 |
| 查询结果的路径 | 获取执行状态和输出 |
| 状态字段和状态值 | 转换为内部任务状态 |
| 视频输出字段 | 获取视频 URL 或文件信息 |
| 图片输入方式 | URL、上传文件或工作流指定的输入节点 |
| 工作流参数映射 | 确定各项参数对应的节点或输入字段 |

已知需要核实的 API 形式包括：

```text
POST /api/v1/comfyui/comfyui_workflow/{workflow_id}

GET /result/{task_id}
```

这两个路径应视为待实测确认的接口形式。必须核对当前 AutoDL 控制台的实际 API 文档、认证方式、请求体及返回结构后再正式使用。

不要直接假设所有 ComfyUI 工作流都采用同一种请求格式。

## 4. 第一次调用的验证流程

在开发完整后端之前，建议先完成一次最小验证。

### 第一步：确认实例正常

- 启动 AutoDL.Art GPU 实例。
- 确认 ComfyUI 已经正常运行。
- 在 ComfyUI 中手动执行一次工作流。
- 确认输出视频可正常播放。

### 第二步：准备工作流

确认：

- 工作流可以接收参考图片。
- 提示词能够传入正确的节点。
- 工作流包含视频输出节点。
- 输出视频格式和保存位置符合预期。
- 工作流 ID 与实际使用的工作流一致。

### 第三步：确认 API 认证

从平台控制台获取正确的 API Token，并确认认证头的实际格式。

Token 只能放在后端环境变量中，不允许写在前端代码中。

### 第四步：用 Python 提交任务

使用 Python HTTP 客户端发起请求，记录脱敏后的请求信息和原始响应。

需要确认：

- HTTP 状态码。
- 返回的 JSON 结构。
- 外部任务 ID 的字段名。
- 是否需要额外的图片上传步骤。
- 是否存在任务排队状态。

### 第五步：查询任务

使用外部任务 ID 查询状态。

确认：

- 哪个字段表示运行中。
- 哪个字段表示成功。
- 哪个字段表示失败。
- 失败时是否返回错误原因。
- 成功时是否返回视频地址或文件路径。

### 第六步：验证输出

下载生成的视频，并检查：

- 文件是否存在。
- 文件大小是否大于零。
- 视频是否可以正常解码。
- 画幅是否符合预期。
- 时长是否符合工作流实际能力。
- 视频是否存在明显的损坏或缺帧问题。

完成以上步骤后，再把真实请求和响应映射到后端 Provider。

## 5. 环境变量设计

后端 `.env.example`：

```env
APP_ENV=local
APP_HOST=0.0.0.0
APP_PORT=8000
LOG_LEVEL=INFO

DATABASE_URL=sqlite:///./data/ai_video_studio.db

REDIS_ENABLED=false
REDIS_URL=redis://localhost:6379/0

AUTODL_BASE_URL=
AUTODL_API_TOKEN=
AUTODL_WORKFLOW_ID=

AUTODL_REQUEST_TIMEOUT_SECONDS=30
AUTODL_POLL_INTERVAL_SECONDS=5
AUTODL_MAX_POLL_SECONDS=1800

LOCAL_STORAGE_DIR=./storage
PUBLIC_BASE_URL=http://127.0.0.1:8000
```

说明：

- `AUTODL_BASE_URL`：实际 API 基础地址。
- `AUTODL_API_TOKEN`：服务端 Token。
- `AUTODL_WORKFLOW_ID`：默认工作流标识。
- `AUTODL_REQUEST_TIMEOUT_SECONDS`：HTTP 请求超时。
- `AUTODL_POLL_INTERVAL_SECONDS`：任务轮询间隔的初始建议值。
- `AUTODL_MAX_POLL_SECONDS`：单次执行的轮询时限。
- `LOCAL_STORAGE_DIR`：本地文件保存目录。
- `PUBLIC_BASE_URL`：本服务对外访问地址。

这些配置项是业务后端的设计约定，并不意味着 AutoDL 平台一定采用相同的参数名。

`.env` 必须加入 `.gitignore`。

## 6. Provider 封装

建议在 `app/providers/autodl_comfyui.py` 中封装外部调用。

内部统一接口：

```python
from typing import Any, Protocol


class VideoProvider(Protocol):
    async def submit(self, payload: dict[str, Any]) -> str:
        """提交工作流，返回外部任务 ID。"""
        ...

    async def get_status(
        self,
        provider_task_id: str,
    ) -> dict[str, Any]:
        """查询状态并返回内部统一结构。"""
        ...

    async def get_result(
        self,
        provider_task_id: str,
    ) -> dict[str, Any]:
        """获取生成结果。"""
        ...
```

### Provider 的职责

1. 构造 HTTP 请求。
2. 处理认证。
3. 设置连接超时和总超时。
4. 校验 HTTP 状态码。
5. 解析外部响应。
6. 将外部状态转换成内部状态。
7. 识别超时、认证错误和参数错误。
8. 获取生成结果。
9. 将异常转换为统一的业务错误。

### Provider 不应该负责

- 直接向前端返回外部 API 的原始响应。
- 自己决定用户是否有权限执行任务。
- 在没有业务规则校验的情况下任意修改任务状态。
- 把 Token 输出到日志。
- 将外部 URL 当作永久文件存储地址。

## 7. 内部统一状态

建议将外部服务状态转换为以下结构：

```json
{
  "status": "running",
  "progress": null,
  "video_url": null,
  "error_code": null,
  "error_message": null
}
```

其中 `status` 只使用内部定义的状态。

例如，外部 API 可能使用不同的状态值表达排队、执行中、成功或失败。Provider 应根据实际返回结构进行映射，而不是让前端直接处理服务商的状态值。

如果外部响应缺少必要字段，应记录错误并按明确的恢复策略处理，不要默认将任务标记为成功。

## 8. 视频生成的完整业务流程

### 8.1 创建任务

前端调用：

```http
POST /api/v1/videos
```

后端执行：

1. 校验提示词和图片。
2. 校验时长和画幅。
3. 创建 `video_tasks` 记录。
4. 将状态设置为 `pending`。
5. 返回本系统的 `task_id`。

不要在创建接口中同步等待完整视频生成。

### 8.2 Worker 领取任务

Worker 从数据库或队列中领取待执行任务。

领取过程必须有并发保护，防止多个 Worker 同时执行同一任务。

### 8.3 提交工作流

Worker 调用 Provider 的 `submit()` 方法。

提交成功后：

- 保存外部 `provider_task_id`。
- 更新状态为 `submitted`。
- 记录提交时间和必要的执行事件。

如果请求超时，不能简单认定外部任务一定没有创建。应根据 API 的幂等能力、任务查询能力和请求结果决定是否重试，避免重复生成。

### 8.4 查询状态

Worker 根据 `provider_task_id` 轮询外部服务。

建议：

- 初始间隔从 3–5 秒开始评估。
- 长时间运行时可以逐步增加间隔。
- 设置总轮询时限。
- 对网络临时错误进行有限重试。
- 对认证和参数错误停止无意义的重试。

实际轮询间隔要根据服务商的接口限制和工作流耗时调整。

### 8.5 处理成功结果

外部服务成功后：

1. 获取视频地址或文件信息。
2. 下载或转存视频。
3. 校验文件是否有效。
4. 将视频保存到本地存储或对象存储。
5. 保存 `result_storage_key`。
6. 更新任务状态为 `succeeded`。
7. 记录完成时间和结果信息。

只有结果文件确实可用后，才应把任务最终标记为成功。

### 8.6 处理失败结果

外部任务失败时：

- 保存内部错误码。
- 保存脱敏后的错误摘要。
- 更新状态为 `failed`。
- 记录完成时间。
- 保留必要的任务事件。
- 根据错误类型决定是否允许重试。

不要将 Token、认证头或完整的敏感请求体写入错误日志。

## 9. 图片与视频存储

### 9.1 本地开发

建议目录：

```text
storage/
├── inputs/
│   └── 上传的参考图片
├── videos/
│   └── 生成的视频
└── thumbnails/
    └── 视频缩略图
```

`storage/` 应加入 `.gitignore`。

数据库保存：

- 存储键。
- 文件 MIME 类型。
- 文件大小。
- 创建时间。
- 可选的时长和画幅信息。

不要把整个视频二进制内容直接存入关系型数据库。

### 9.2 线上部署

线上应选择以下方案之一：

**方案 A：持久化卷**

适合平台确实提供可靠持久化磁盘的情况。

**方案 B：对象存储**

将图片和视频保存到对象存储，数据库只保存对象键。

如果 API 与 Worker 分开部署，推荐对象存储，因为不同实例的本地目录通常不共享。

### 9.3 临时 URL

外部服务返回的视频地址可能是临时地址。

建议流程：

```text
外部视频地址
      ↓
后端下载或转存
      ↓
对象存储
      ↓
保存 storage_key
      ↓
查询结果时生成访问 URL
```

不要假设外部视频地址永久有效。

### 9.4 文件安全

- 限制上传文件大小。
- 检查实际文件格式。
- 避免直接信任客户端传入的路径。
- 避免下载任意 URL 导致 SSRF。
- 对下载地址设置允许的来源范围。
- 对视频下载设置大小和时间限制。

## 13. 微信云托管部署设计

### 13.1 推荐架构

```text
微信小程序 / Web 前端
          |
          v
    FastAPI API 服务
          |
          +---- 线上关系型数据库
          |
          +---- 对象存储
          |
          +---- Redis（可选）
          |
          v
      独立 Worker
          |
          v
      AutoDL API
          |
          v
      ComfyUI / H3
```

### 13.2 为什么建议分开 API 与 Worker

视频生成是耗时任务。

如果把生成流程完全放在 HTTP 请求里，可能遇到：

- 请求超时。
- 用户关闭页面导致体验异常。
- 容器重启中断任务执行。
- 并发请求占满 Web 工作进程。
- 任务执行状态难以恢复。

因此，推荐 API 负责受理和查询，Worker 负责耗时操作。

开发初期可以采用更简单的单机 Worker，但需要明确任务恢复机制；正式部署时再根据平台能力拆分。

### 13.3 部署前必须确认

- Python 版本和依赖安装方式。
- 服务监听端口要求。
- 是否要求绑定 `0.0.0.0`。
- 健康检查路径。
- 容器重启策略。
- 是否支持持久化卷。
- 数据库网络连通性。
- 是否允许访问 AutoDL API。
- 外部请求超时限制。
- 后台 Worker 的运行方式。
- 环境变量与密钥配置方式。
- 日志保留和查询方式。

微信云托管的实际功能、限制和部署方式应以当前平台文档为准，不应假定所有云托管环境都支持相同的后台常驻进程或存储能力。

### 13.4 数据库配置

本地：

```env
DATABASE_URL=sqlite:///./data/ai_video_studio.db
```

线上示例：

```env
DATABASE_URL=postgresql+psycopg://USER:PASSWORD@HOST:5432/DBNAME
```

上线时需要：

1. 配置线上数据库。
2. 执行数据库迁移。
3. 验证连接和权限。
4. 确认数据库不是临时实例。
5. 验证服务重启后的数据保留情况。

### 13.5 Redis 配置

本地：

```env
REDIS_ENABLED=false
```

需要任务队列或多实例协调时：

```env
REDIS_ENABLED=true
REDIS_URL=redis://HOST:6379/0
```

具体地址、密码、TLS 和网络要求以实际 Redis 服务为准。

Redis 不是必选条件，但如果采用依赖 Redis 的队列方案，就必须同时部署并正确配置对应的队列服务。

### 13.6 视频文件存储

如果云托管实例使用临时磁盘，不能将视频只保存到容器本地目录。

建议：

- 输入图片保存到对象存储。
- 生成的视频转存到对象存储。
- 数据库只保存对象键和相关元信息。
- 前端通过后端获取受控的访问 URL。

这样即使 API 容器重新创建，也不会丢失已经生成的视频。

## 14. 超时与重试策略

### 14.1 HTTP 超时

所有外部 HTTP 请求必须配置超时。

提交任务和查询任务的超时可以分别配置，因为二者的响应特征可能不同。

### 14.2 轮询超时

轮询时间超过设定上限后，不应无限占用 Worker。

需要区分：

- 外部任务明确失败。
- 外部任务仍在执行。
- 外部查询接口暂时不可用。
- 本系统无法确认外部任务状态。

如果无法确认外部任务是否仍在运行，应保留必要信息并安排后续检查，避免直接重新提交导致重复生成。

### 14.3 重试分类

| 错误类型 | 建议策略 |
|---|---|
| 参数错误 | 不重试，修正参数 |
| Token 无效 | 不自动反复重试，修复认证 |
| 网络临时异常 | 有限重试 |
| 查询超时 | 退避后重试查询 |
| 外部任务明确失败 | 根据错误类型决定是否重新生成 |
| 文件下载暂时失败 | 有限重试下载 |
| 输出文件无效 | 记录失败并排查工作流 |

重试必须有次数上限、退避间隔和清晰的日志。

## 15. 日志设计

每条任务相关日志建议包含：

- `task_id`
- `provider_task_id`（已取得时）
- `event`
- `status`
- `duration_ms`（适用时）
- `error_code`（失败时）

示例：

```text
task_id=xxx event=provider_submit_started
task_id=xxx event=provider_submitted provider_task_id=yyy
task_id=xxx event=provider_running
task_id=xxx event=result_saved
```

不要记录：

- API Token。
- Authorization 请求头。
- 数据库密码。
- 未脱敏的敏感用户信息。
- 不必要的完整请求体。

## 16. 常见故障排查

| 现象 | 优先排查内容 |
|---|---|
| 401 / 403 | Token、认证头格式、权限和有效期 |
| 404 | API 基础地址、工作流 ID、查询路径 |
| 400 / 422 | 请求体、工作流输入字段、图片输入方式 |
| 提交超时 | 网络、服务端负载、HTTP 超时设置 |
| 任务一直运行 | 外部状态映射、轮询逻辑、工作流排队情况 |
| 成功但无视频 | 输出节点、结果字段、下载或转存流程 |
| 视频无法播放 | 文件是否完整、编码格式、下载是否中断 |
| 视频 URL 失效 | 是否为临时地址、是否应转存对象存储 |
| 重启后任务消失 | 任务是否只在内存中、数据库和文件是否持久化 |
| 重复生成 | 重复提交、任务领取并发保护、重试逻辑 |
| 云端无法访问 AutoDL | 网络出站规则、域名、端口、TLS 和认证 |
| SQLite 写入冲突 | 并发写入量、事务设计、是否需要切换服务端数据库 |

## 18. 最终实施顺序

建议按照下面的顺序推进：

1. 在 AutoDL 上手动运行工作流，确认能够生成视频。
2. 用 Python 验证真实 API 的提交和查询。
3. 建立 FastAPI 项目和 SQLite 数据库。
4. 实现 Provider 和任务执行流程。
5. 实现任务列表、详情和结果查询接口。
6. 实现 React 前端工作台。
7. 补充重试、并发保护和任务恢复。
8. 验证线上数据库和文件存储。
9. 根据实际部署平台完成微信云托管部署。
10. 在核心流程稳定后，再逐步引入 LangGraph 和更复杂的 Agent。

**最重要的原则：先以真实的 AutoDL 工作流打通生成闭环，再围绕真实接口构建系统。不要先写一套假设性的 API 集成，再到最后才发现工作流参数、任务状态和视频输出方式不匹配。**
