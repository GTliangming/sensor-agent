# AI Video Studio：后端接口与数据设计

## 1. 设计目标

后端负责视频任务的创建、执行调度、状态管理、结果保存和查询。

核心要求：

1. 本地默认使用 SQLite。
2. 通过 `DATABASE_URL` 切换线上数据库。
3. Redis 可以关闭，关闭后仍能运行核心业务。
4. 外部视频服务统一通过 Provider 调用。
5. 视频生成采用异步任务模式。
6. 任务状态以数据库记录为准。
7. 支持超时、有限重试、幂等和并发保护。
8. 不把模型 Token、数据库密码等敏感信息返回给前端。

## 2. API 规范

### 2.1 基础约定

基础路径：

```text
/api/v1
```

请求与响应使用 JSON；图片上传可以采用 `multipart/form-data`。

时间字段使用 ISO 8601 格式，数据库建议统一存储 UTC 时间。

任务 ID 使用 UUID 或 ULID，不使用数据库自增 ID 作为公开任务标识。

### 2.2 统一响应格式

成功示例：

```json
{
  "code": "OK",
  "message": "success",
  "data": {}
}
```

失败示例：

```json
{
  "code": "PROVIDER_TIMEOUT",
  "message": "视频生成服务响应超时",
  "details": {
    "task_id": "8a4d5d34-0000-4000-8000-000000000001"
  }
}
```

HTTP 状态码应与实际语义一致：

| 状态码 | 使用场景 |
|---|---|
| 200 | 查询成功或操作成功 |
| 201 | 资源创建成功；如果采用异步任务，也可以使用 202 |
| 202 | 请求已受理，任务尚未完成 |
| 400 | 请求参数或业务操作不合法 |
| 401 | 未认证 |
| 403 | 无权限 |
| 404 | 任务不存在 |
| 409 | 状态冲突或幂等冲突 |
| 422 | 请求数据未通过校验 |
| 429 | 请求频率或任务配额超限 |
| 500 | 内部错误 |
| 502 | 外部服务返回无效响应或失败 |
| 503 | 服务暂不可用 |
| 504 | 外部调用超时 |

## 3. 接口清单

| 方法 | 路径 | 功能 |
|---|---|---|
| GET | `/api/v1/health` | 健康检查 |
| POST | `/api/v1/videos` | 创建视频任务 |
| GET | `/api/v1/videos` | 查询任务列表 |
| GET | `/api/v1/videos/{task_id}` | 查询任务详情 |
| POST | `/api/v1/videos/{task_id}/retry` | 重试符合条件的失败任务 |
| POST | `/api/v1/videos/{task_id}/cancel` | 请求取消任务 |
| GET | `/api/v1/videos/{task_id}/result` | 查询生成结果 |
| GET | `/api/v1/providers/autodl/status` | 检查外部服务配置和连通性 |

最后一个接口建议只对管理员开放，或者只在开发环境启用。

## 4. 健康检查接口

### 请求

```http
GET /api/v1/health
```

### 响应

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "status": "healthy"
  }
}
```

健康检查不应该每次都触发昂贵的视频生成请求。

建议区分：

- 存活检查：进程是否正常运行。
- 就绪检查：数据库等关键依赖是否可以工作。
- 外部服务检查：单独检查 AutoDL API，不要让外部 GPU 服务的短暂故障直接导致业务 API 被判定为进程死亡。

## 5. 创建视频任务

### 5.1 请求

```http
POST /api/v1/videos
Content-Type: application/json
```

示例：

```json
{
  "prompt": "人物在温暖的室内自然转身，镜头平稳，动作连贯",
  "negative_prompt": "画面闪烁，人物变形，严重模糊，水印",
  "image_url": "https://example.com/reference.png",
  "aspect_ratio": "9:16",
  "duration_seconds": 12
}
```

### 5.2 参数说明

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `prompt` | string | 是 | 正向提示词 |
| `negative_prompt` | string | 否 | 负向提示词 |
| `image_url` | string | 视工作流而定 | 参考图片的内部地址或已验证地址 |
| `aspect_ratio` | string | 否 | 默认 `9:16` |
| `duration_seconds` | integer | 否 | 默认 12 秒，需受工作流能力限制 |

注意：

- 不应直接信任任意外部图片 URL。
- 更推荐先上传图片，再传递本系统的文件 ID。
- 不允许普通用户随意指定任意工作流 ID。
- 提示词长度、图片大小、文件类型和生成时长都必须校验。
- 实际时长、分辨率、帧率等参数应根据当前工作流能力进行映射。

### 5.3 响应

```json
{
  "code": "OK",
  "message": "任务已创建",
  "data": {
    "task_id": "8a4d5d34-0000-4000-8000-000000000001",
    "status": "pending",
    "created_at": "2026-10-28T03:00:00Z"
  }
}
```

返回 `202 Accepted`，表示系统已受理，不代表视频生成成功。

## 6. 查询任务列表

### 请求

```http
GET /api/v1/videos?page=1&page_size=20&status=running
```

支持参数：

| 参数 | 类型 | 说明 |
|---|---|---|
| `page` | integer | 页码，从 1 开始 |
| `page_size` | integer | 每页数量，设置最大值，例如 100 |
| `status` | string | 可选的任务状态 |
| `created_after` | datetime | 可选的起始时间 |
| `created_before` | datetime | 可选的结束时间 |

### 响应

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "items": [
      {
        "task_id": "8a4d5d34-0000-4000-8000-000000000001",
        "status": "succeeded",
        "prompt_preview": "人物在温暖的室内自然转身……",
        "duration_seconds": 12,
        "created_at": "2026-10-28T03:00:00Z",
        "updated_at": "2026-10-28T03:10:00Z",
        "thumbnail_url": null,
        "video_url": "由后端生成的访问地址"
      }
    ],
    "page": 1,
    "page_size": 20,
    "total": 1
  }
}
```

`video_url` 只有在任务成功并且结果可访问时才返回。

## 8. 查询生成结果

### 请求

```http
GET /api/v1/videos/{task_id}/result
```

成功响应：

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "task_id": "8a4d5d34-0000-4000-8000-000000000001",
    "status": "succeeded",
    "video_url": "后端生成的可访问地址",
    "content_type": "video/mp4",
    "duration_seconds": 12
  }
}
```

任务未成功时，不应返回一个看似可用的结果地址。

如果采用对象存储的临时签名 URL，应在查询结果时按需生成，数据库优先保存 `storage_key`，不要只保存可能过期的 URL。

## 9. 重试与取消

### 9.1 重试接口

```http
POST /api/v1/videos/{task_id}/retry
```

规则：

- 只允许重试符合策略的失败任务。
- 每次重试需要有次数上限。
- 参数错误、权限错误等不可恢复错误不应自动重试。
- 重试可以创建新的执行记录，也可以重置原任务，但必须保留历史执行信息。
- 不要在没有确认上一次外部任务是否仍在运行时盲目重新生成，避免重复消耗费用。

推荐后续增加 `video_task_attempts` 表，单独保存每次执行记录。

### 9.2 取消接口

```http
POST /api/v1/videos/{task_id}/cancel
```

取消任务时应判断当前状态。

- `pending`：可以取消尚未执行的任务。
- `submitted` 或 `running`：尝试调用外部取消能力。
- 如果外部服务不支持取消，应明确告知用户实际限制。
- `succeeded` 或 `failed`：不再执行取消操作。

## 10. 数据库设计

### 10.1 `video_tasks` 主任务表

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | UUID 字符串或原生 UUID | 主键/任务标识 |
| `status` | VARCHAR | 任务状态 |
| `prompt` | TEXT | 正向提示词 |
| `negative_prompt` | TEXT，可空 | 负向提示词 |
| `input_image_key` | TEXT，可空 | 输入图片存储键 |
| `aspect_ratio` | VARCHAR | 画幅比例 |
| `duration_seconds` | INTEGER | 目标时长 |
| `workflow_key` | VARCHAR | 系统内部工作流配置名 |
| `workflow_version` | VARCHAR，可空 | 工作流版本 |
| `provider_name` | VARCHAR | 外部服务商 |
| `provider_task_id` | VARCHAR，可空 | 外部任务 ID |
| `result_storage_key` | TEXT，可空 | 视频存储键 |
| `result_content_type` | VARCHAR，可空 | 文件 MIME 类型 |
| `result_size_bytes` | BIGINT，可空 | 视频大小 |
| `error_code` | VARCHAR，可空 | 错误码 |
| `error_message` | TEXT，可空 | 脱敏后的错误信息 |
| `retry_count` | INTEGER | 已重试次数 |
| `created_at` | DATETIME | 创建时间 |
| `updated_at` | DATETIME | 更新时间 |
| `started_at` | DATETIME，可空 | 开始执行时间 |
| `completed_at` | DATETIME，可空 | 完成时间 |

建议建立索引：

- `status`
- `created_at`
- `provider_task_id`
- 如有用户体系，则建立 `(user_id, created_at)` 索引。

### 10.2 `video_task_events` 事件表

用于记录状态变化和排查任务异常。

建议字段：

- `id`
- `task_id`
- `from_status`
- `to_status`
- `event_type`
- `message`
- `created_at`

示例事件：

```text
task_created
provider_submit_started
provider_submitted
provider_poll_started
provider_running
provider_succeeded
result_saved
provider_failed
retry_requested
task_cancelled
```

### 10.3 `video_task_attempts` 执行记录表

建议在引入重试时增加。

字段建议：

- `id`
- `task_id`
- `attempt_number`
- `provider_task_id`
- `status`
- `started_at`
- `completed_at`
- `error_code`
- `error_message`

这样可以保留多次执行记录，不必覆盖所有历史信息。

## 11. 数据库切换方案

### 11.1 本地 SQLite

`.env`：

```env
DATABASE_URL=sqlite:///./data/ai_video_studio.db
```

注意创建 `data` 目录，并确保文件具有读写权限。

### 11.2 线上数据库

例如 PostgreSQL：

```env
DATABASE_URL=postgresql+psycopg://USER:PASSWORD@HOST:5432/DBNAME
```

这里的连接串只是格式示例，部署时必须替换为真实配置。

### 11.3 代码层原则

使用 SQLAlchemy 统一数据库访问。

```text
API
 ↓
Service
 ↓
Repository
 ↓
SQLAlchemy
 ↓
SQLite / PostgreSQL
```

业务层不得到处写针对某个数据库的专有 SQL。

建议：

- 使用统一 ORM 模型。
- 使用数据库迁移工具 Alembic。
- 通过 `DATABASE_URL` 创建引擎。
- 根据 SQLite 和线上数据库分别配置连接池参数。
- 对关键查询和事务进行测试。
- 不依赖启动时自动建表来代替正式迁移。

### 11.4 需要特别注意

**更换 `DATABASE_URL` 不等于自动完成数据库迁移。**

切换到线上数据库时需要：

1. 创建线上数据库。
2. 配置网络权限。
3. 执行 Alembic 迁移。
4. 如需保留本地历史数据，再执行数据导入。
5. 检查任务、事件和文件元数据是否完整。
6. 验证读写、事务和并发行为。

SQLite 适合本地开发和轻量单机使用。如果部署环境采用多实例或有较高并发写入需求，优先使用服务端数据库。

## 12. Redis 可选设计

### 12.1 配置

```env
REDIS_ENABLED=false
REDIS_URL=redis://localhost:6379/0
```

### 12.2 关闭 Redis 时

系统应使用数据库任务记录和单机 Worker 完成核心流程。

需要注意：如果只依赖进程内后台任务，进程重启后可能丢失执行中的内存任务。因此应设计任务恢复扫描，重新检查 `pending`、`submitted` 和 `running` 状态的任务。

### 12.3 启用 Redis 时

Redis 可以用于：

- 任务队列。
- 短期缓存。
- 分布式限流。
- 任务领取协调。
- 分布式锁或去重机制。

Redis 不是业务数据的唯一存储。

推荐原则：

- 数据库是任务状态的事实来源。
- Redis 是可选的队列、缓存或协调组件。
- Worker 必须能够安全处理重复消息。
- 对执行中的任务设置超时和恢复策略。
- 任务领取需要具备原子性，避免多个 Worker 同时执行同一个任务。

## 13. Worker 设计

### 13.1 开发阶段

可使用一个独立的 Python Worker，定期从数据库领取待执行任务。

逻辑：

```text
循环
  ↓
查询可执行任务
  ↓
原子领取任务
  ↓
提交外部工作流
  ↓
保存 provider_task_id
  ↓
轮询外部状态
  ↓
成功则保存结果
  ↓
失败则保存错误
  ↓
继续处理下一任务
```

### 13.2 生产阶段

建议将 API 与 Worker 分开部署：

- API 负责接收请求和查询数据。
- Worker 负责耗时的模型调用、轮询和文件处理。
- 数据库保存任务状态。
- Redis 可选地提供可靠队列。

这样不会因为单个视频生成耗时过长而占用 HTTP 请求。

### 13.3 并发安全

任务领取时应避免：

1. Worker A 读取到任务。
2. Worker B 同时读取到同一任务。
3. 两个 Worker 都提交外部生成任务。

可采用数据库事务、条件更新、租约字段或可靠队列实现任务领取。

需要定义：

- `claimed_by`
- `lease_expires_at`
- `attempt_number`

这些字段可以放在任务表，也可以放在独立的执行表中。

租约过期后，系统需要检查外部任务是否仍在执行，再决定恢复轮询还是重新提交。

## 14. AutoDL Provider 设计

建议定义统一接口：

```python
from typing import Any, Protocol


class VideoProvider(Protocol):
    async def submit(self, payload: dict[str, Any]) -> str:
        """提交工作流，返回外部任务 ID。"""
        ...

    async def get_status(self, provider_task_id: str) -> dict[str, Any]:
        """查询状态并转换为内部统一格式。"""
        ...

    async def get_result(self, provider_task_id: str) -> dict[str, Any]:
        """获取生成结果信息。"""
        ...
```

内部统一状态结构示例：

```json
{
  "status": "running",
  "progress": null,
  "video_url": null,
  "error_code": null,
  "error_message": null
}
```

实际映射应以 AutoDL API 的真实响应为准。

Provider 负责：

- 认证。
- HTTP 超时。
- 请求提交。
- 状态查询。
- 结果获取。
- 错误转换。
- 必要的响应校验。

Provider 不负责：

- 直接向前端返回服务商原始响应。
- 随意修改数据库业务状态。
- 保存业务层唯一任务记录。

## 16. 安全设计

- AutoDL Token 只保存在后端环境变量或密钥管理服务中。
- 不将密钥提交到 Git。
- 不向前端返回 Authorization 头。
- 图片 URL 应限制来源，避免 SSRF。
- 对上传文件类型、大小和内容进行校验。
- 限制提示词长度和任务并发数。
- 错误信息应脱敏。
- 对用户任务进行访问权限校验。
- 对重试、取消等写操作增加权限和状态检查。
- 线上接口应配置 HTTPS 和适当的限流策略。

## 17. 验收测试

- [ ] 缺少必要参数时返回明确的校验错误。
- [ ] 正常创建任务后返回本系统任务 ID。
- [ ] 创建接口不会同步等待视频生成完成。
- [ ] 任务状态能够持久化。
- [ ] 重复轮询不会重复创建结果。
- [ ] 外部调用超时能够被正确处理。
- [ ] 失败任务不会无限重试。
- [ ] 重复提交有幂等保护。
- [ ] 多 Worker 领取任务时不会无保护地重复执行。
- [ ] Redis 关闭后核心流程仍可运行。
- [ ] SQLite 配置可正常使用。
- [ ] 线上数据库迁移经过验证。
- [ ] 视频结果地址不会因容器重启而失效。
- [ ] API Token 不会出现在前端或普通日志中。

## 18. 设计总结

后端架构的核心是：

**数据库保存业务事实，Provider 隔离外部模型服务，Worker 负责耗时执行，Redis 按需提供队列能力。**

这套设计既能满足本地快速开发，也能为后续微信云托管和多实例部署预留空间。
