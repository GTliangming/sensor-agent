# 03 分阶段开发任务与验收标准

**项目：** Annotation Ops Agent
**版本：** V1.0（定稿）
**日期：** 2026-11-02
**关联文档：** 《01 业务需求与功能清单》《02 系统技术架构设计》

---

## 0. 总则

### 0.1 交付原则

1. 每个版本必须是**能运行、能验证**的完整功能，不以“代码写完”为完成。
2. 每个版本独立可启动、可回滚，不提前实现后续阶段的复杂能力。
3. 先跑通最短链路，再补能力：真实数据 → 单 Agent → 工具 → 编排 → 知识 → 记忆 → 诊断 → 多 Agent → 评测。
4. 任何阶段都不开放业务写操作。
5. 所有真实接口路径、字段、鉴权必须在文档中可追溯，不允许猜测。

### 0.2 每阶段必须交付

- 需求说明（本阶段目标与非目标）
- 技术设计与关键决策
- 实现代码
- 单元测试 + 必要的集成测试
- 验收记录（实际执行结果，不只是清单打勾）
- 已知问题与下一阶段输入

### 0.3 完成定义（DoD）

- [ ] 功能符合验收标准
- [ ] 代码通过 lint / type check
- [ ] 关键逻辑有单元测试
- [ ] 日志含 request_id，敏感字段已脱敏
- [ ] 文档已更新
- [ ] 无新增写接口、无直连业务库
- [ ] 演示脚本可复现

## 2. V0.1 项目基础架构

### 2.1 目标

搭建独立项目骨架，打通“前端登录 → 后端 API → 模型调用 → 对话落库”的最短链路。

### 2.2 非目标

- 不接 Go API
- 不做工具调用
- 不做 RAG / Memory / 多 Agent

### 2.3 任务

- [ ] 创建独立 Git 仓库与目录结构（见《02》§17）
- [ ] 初始化 React 19 + Vite + Ant Design + React Router
- [ ] 登录页、主布局、对话页骨架
- [ ] 初始化 FastAPI + Pydantic Settings + SQLAlchemy + SQLite
- [ ] `users` 表 + 轻量登录（密码哈希）+ JWT
- [ ] `conversations` / `messages` / `agent_runs` 基础表
- [ ] DeepSeek 客户端封装 + `/api/health` 探活
- [ ] 统一错误体、request_id 中间件、结构化日志
- [ ] 前端 Axios 封装（JWT 注入、401 跳转、错误提示）
- [ ] 基础对话接口：问题 → 模型 → 回答 → 落库
- [ ] `.env.example`、README、启动脚本

### 2.4 验收标准

- [ ] 前端可启动、可登录、可登出
- [ ] 未登录访问受保护页面会跳转登录
- [ ] 后端可启动，`/api/health` 正常
- [ ] 能成功调用 DeepSeek 并返回回答
- [ ] 对话与消息正确落库，刷新后可恢复
- [ ] 每次请求有 request_id，前后端日志可关联
- [ ] 仓库中不含任何密钥
- [ ] 无 Go API 调用、无写操作

### 2.5 交付物

可演示的登录 + 单轮对话；README 启动说明；第一版 `.env.example`。

## 13. 评测体系

### 13.1 数据集

| 类型 | 数量 | 说明 |
|---|---|---|
| 规范检索 | 30–50 | 问题 + 标准条款 + 标准引用 |
| 业务查询 | 20–30 | 问题 + 权限上下文 + 预期工具 + 关键字段 |
| 异常诊断 | 20 | 问题 + 预期异常 + 证据 |
| 多步骤任务 | 10–20 | 跨工具、跨对象 |
| 安全/Prompt Injection | 10 | 期望拒绝或降级 |

每条样本保存：问题、权限上下文、预期工具、预期字段、标准证据、可接受答案范围、禁止行为。评测集版本化。

### 13.2 指标

| 维度 | 指标 |
|---|---|
| 意图 | Intent Accuracy |
| 工具选择 | Tool Selection Accuracy |
| 参数 | Argument Validity / Exact Match |
| 执行 | Tool Success Rate |
| 数据 | Data Grounded Accuracy |
| 检索 | Recall@K、MRR、nDCG、Citation Accuracy |
| 诊断 | Finding Precision/Recall、Evidence Coverage |
| 工作流 | Task Completion Rate、平均步骤数 |
| 安全 | Unauthorized Tool Call Rate、Unsafe Action Rate |
| 成本 | Token、调用次数、平均延迟 |

不能只用另一个 LLM 当裁判；必须有人工标准答案 + 程序断言 + 专家抽检。

### 13.3 错误分类

API 数据不完整、字段理解错误、工具描述不清、选错工具、参数错误、口径错误、召回失败、排序失败、版本冲突、反思循环不合理、权限拦截失败、结论夸大。

先定位瓶颈，再决定改代码 / 工具 / Prompt / RAG / 微调。

|---|---|---|
| 1 | V0.1 + V0.2 | 可登录、可对话、图能跑 |
| 2 | V0.3 + Go API 盘点 | Mock 工具 + API Mapping |
| 3 | V0.4 | 真实查询 Agent |
| 4 | V0.5 | 多步分析 + 报告 |
| 5 | V0.6 前半 | 解析、切片、向量检索 |
| 6 | V0.6 后半 | 混合检索、Rerank、评测 |
| 7 | V0.7 | Memory + 审核 |
| 8 | V0.8 前半 | 规则与异常 |
| 9 | V0.8 后半 + V0.9 | 多 Agent + 可观测 |
| 10 | V1.0 | 评测、加固、演示 |

若某阶段未通过验收，顺延，不压缩测试与评测。

## 16. 风险检查清单

- [ ] Go `/agent/v1` 是否按期可用？
- [ ] 绑定数据是否完整、可维护？
- [ ] 接口字段是否冻结、有契约测试？
- [ ] 是否存在任何写路径？
- [ ] 统计口径是否被业务确认？
- [ ] 规范版本是否可追溯？
- [ ] 是否有 Prompt Injection 测试？
- [ ] 是否有越权测试？
- [ ] 日志是否脱敏？
- [ ] 是否能在中断后恢复？
- [ ] 是否有可复现的评测集？
- [ ] 是否具备回滚能力？
