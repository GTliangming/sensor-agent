# 语音标注平台 Agent 项目整体分析报告

- 分析对象：`speech-mark-agent-platform` 与《企业级 Agent 实战开发手册：语音标注平台》
- 分析日期：2026-10-22
- 报告目的：说明项目目标、架构和当前代码真实能力，识别与手册规划的差距，并给出后续实施顺序
- 分析边界：依据项目源代码阅读结果、README、架构文档、接口契约、交付验证记录及实战手册；本报告不代表本次重新运行了服务或测试

## 1. 执行摘要

项目面向语音标注团队，目标是让用户通过自然语言查询标注项目、任务和质量数据，检索 SOP，并在后续阶段生成质量分析草稿、进入人工审批。项目采取 React 前端、Go 业务控制面、Python Agent 运行面的拆分，已经具备基础的跨服务 Run 创建、执行、查询和 Trace 展示骨架。

当前实现应定位为“可本地演示和继续迭代的 Agent 平台骨架”，而不是已接入真实语音标注业务的企业级 Agent。默认工作流是关键词驱动的演示逻辑；启用 DeepSeek 后也只有一个本地示例 SOP 工具。业务 API、鉴权、真实检索、审批恢复、可靠异步执行、工作流持久化和生产级评测等能力尚未形成完整闭环。

综合判断：

- **架构方向合理**：Go 控制业务事实和权限，Python 负责模型、工具和工作流；Run ID 作为跨服务关联标识。
- **最小调用骨架已经存在**：React → Go → Python 的请求链路可从代码中追踪，Go 侧将 Run、Trace、Approval 写入 SQLite。
- **业务 Agent 尚未落地**：当前没有真实项目、任务、质检业务 API，也没有生产知识库。
- **可恢复性不足**：Go 通过 goroutine 调度，Python 同步执行且将运行状态保存在内存；没有队列、检查点或跨服务恢复。
- **企业安全能力尚未落地**：未形成用户认证、资源级授权、租户隔离和服务间认证。
- **实施策略应继续遵循手册原则**：先完成少量只读业务工具和可测试的单 Agent 闭环，再做工作流、RAG、审批和可靠性，不应先堆多 Agent 或基础设施。

## 2. 目标业务与产品边界

手册将产品命名为 Speech Mark Agent Hub，面向标注项目管理、任务查询、质量分析和业务知识检索。第一版优先支持只读请求，例如查询项目、待质检任务数、时间段质检统计、错误判定标准，以及结合项目数据和 SOP 生成分析草稿。手册明确第一版不接生产数据库、不执行任意 SQL、不直接修改真实业务数据，也不接真实审批或发布动作。

这条边界很重要：Agent 的价值不在于“能调用模型”，而在于它能否在权限约束内调用可信业务能力、带着证据回答，并留下可检查的执行记录。模型负责语言理解、候选工具选择和基于证据的总结；确定性代码负责权限、统计、校验、超时、幂等和事务。RAG 提供知识证据，但不替代业务查询，也不保证证据天然正确。

手册同时强调前端不是安全边界，Python Agent 不应绕过 Go 直接访问业务数据库；Go 是权限和业务事实的最终控制边界。项目的架构文档采用了相同方向。

## 3. 架构和职责

```text
React 管理界面
  │ /api/*
  ▼
Vite 开发代理 / Nginx 生产代理
  │ 改写为 /api/v1/*
  ▼
Go Gin API ─── SQLite（Run、Trace、Approval）
  │ HTTP 内部调用
  ▼
Python FastAPI Agent
  ├── 确定性演示工作流
  └── 可选 DeepSeek + LangChain Agent
```

### React 前端

前端负责对话输入、运行列表和详情、Trace 展示及平台管理页。路由包括工作台、助手、运行记录、运行详情、审批、知识库和系统配置。Vite 将 `/api` 转发至 Go 并改写 API 前缀；部署 Nginx 也承担相同路径改写职责。

技术实现是 React、Vite、Ant Design 和 Axios；这与手册中建议的 Vue 3、Element Plus 不同。这属于实现选型差异，不是本身的缺陷，后续应以现有代码栈为准，避免为了追求手册目录一致而重写 UI。

### Go 业务控制面

Go 使用 Gin、GORM 和 SQLite，提供健康检查、dashboard、Run 创建/列表/详情/Trace/取消、审批列表和决策、知识列表与搜索等 API。SQLite 当前由 GORM 启动时 AutoMigrate，主要模型为 `AgentRun`、`TraceEvent` 和 `Approval`。

Go 侧的 Run 编排、状态更新和 Agent 调用主要放在 Handler 中；Repository 目前主要服务 Run，Service 层仍为空壳。这意味着概念上的分层已经出现，但实现尚未完全按分层职责组织。

### Python Agent 运行面

Python 使用 FastAPI 提供 `/v1/runs`、Run 查询和 Trace 查询接口。运行服务根据 `MODEL_ENABLED` 选择演示工作流或模型工作流。模型路径通过 `ChatOpenAI` 的 OpenAI 兼容接口调用 DeepSeek，并以 LangChain Agent 绑定工具。Python 运行记录与 Trace 使用进程内存结构保存。

当前注册的工具只有本地 `search_annotation_sop` 示例工具。工具不访问 Go 业务 API、真实知识库或生产数据。

## 4. 一次请求的实际执行过程

1. 用户在助手页提交输入和运行模式。
2. React 请求 `POST /api/agent/runs`。
3. Vite 或 Nginx 将请求映射到 Go 的 `POST /api/v1/agent/runs`。
4. Go 校验输入和 `fast`、`balanced`、`careful` 模式，生成 Run ID，在 SQLite 中建立 `queued` Run 并写入创建 Trace。
5. Go 启动后台 goroutine，立即向前端返回 Run ID 和 `queued` 状态。
6. 后台将 Go 侧 Run 更新为 `running`，以 HTTP 调用 Python `POST /v1/runs`。
7. Python 在内存登记运行状态，同步执行演示逻辑或 DeepSeek Agent，生成答案和 Python 侧 Trace。
8. Python 返回后，Go 更新 SQLite 中的答案、状态、耗时等字段，并记录完成或失败事件。
9. 前端使用 Go API 查询 Run 和 Trace，展示结果。

需要注意：Go 对前端表现为异步接受任务，但 Go 到 Python 的调用是同步等待；Python 的任务本身也同步执行。当前没有消息队列或独立 Worker。Go 数据库与 Python 内存状态不是一个共享或事务化的存储系统。

| 手册阶段 | 目标 | 项目现状判断 |
|---|---|---|

### 最主要的架构差距

1. **业务工具断层**：手册要求 Python 工具通过 Go API 读取业务数据，实际没有这层调用，因此 Agent 不能回答真实项目和质量问题。
2. **持久化边界不完整**：Go 与 Python 各有状态，但 Python 是内存状态；跨服务执行无法可靠恢复，也没有统一事件事实源。
3. **工作流复杂度与可观测性不匹配**：当前 Trace 结构存在，但缺少完整的节点/工具调用关联、持久化、回放和断线恢复。
4. **安全约束尚停留在设计文档**：API 契约和架构文档要求认证、授权和服务身份校验，但代码骨架尚未落地这些控制。
5. **审批 UI/API 超前于执行模型**：存在审批页面和决策接口，但未看到 Agent 在受控动作前暂停、待审批状态持久化、批准后恢复并审计结果的闭环。

## 7. 主要风险与影响

### P0：不能把当前系统接入真实生产业务

鉴权、资源授权、租户隔离、服务间认证、操作审计等尚未完成。Go 和 Python 的网络调用不能仅以“内部服务”作为信任依据。若接入真实用户或业务数据，应先补齐身份和授权边界，并将模型与工具权限隔离。

### P1：任务生命周期不可靠

Go goroutine 不是可持久化队列。Go 进程重启时任务可能丢失；Python 同步执行若超时、进程退出或网络断开，Go 与 Python 状态可能不一致。取消接口只改 Go 状态而不停止 Agent 执行，状态语义容易误导用户。

### P1：审计和 Trace 不能作为完整执行证据

Go 侧 Trace 与 Python 侧 Trace 分别生成，Python Trace 为内存数据。事件未形成可靠统一序列，故障时可能缺失；工具参数/结果也需要按手册要求做摘要、大小限制和敏感信息脱敏。

### P1：演示回答可能被误认为真实业务结论

默认演示模式和示例 SOP 工具只做固定规则/文本匹配。虽然提示和回答有说明示例数据，但产品界面和调用方仍需显著标注 demo/model 模式及数据来源，避免误用。

### P2：开发验证证据不足

交付验证文档说明 React/Python 做过语法检查、Compose YAML 可解析，但 Go 编译、pytest、前端完整构建和 `docker compose up --build` 未完成，原因是当时依赖下载和环境受限。静态语法检查不能证明接口契约兼容或运行链路成功。

### P2：文档与代码存在演进差异

手册建议 Vue 3，项目已使用 React；手册建议初期内存模拟业务数据，项目的 SQLite 主要用于 Agent 平台运行记录；架构文档将一些企业能力描述为职责原则，而不是当前已经具备的实现。应继续把目标能力标为待办，不应仅凭文档措辞认定已完成。

## 8. 推荐实施顺序

遵循“先最小真实闭环，再增强可靠性”的路线。每一步都有明确验收，避免并行铺开 RAG、多 Agent、审批和生产基础设施。

### 第一步：固定契约并补齐一个只读业务闭环

- 选择一个范围小、价值清晰的查询，例如“查询项目待质检任务数量”。
- 在 Go 中实现确定性的业务 API 和模拟数据，定义输入校验、分页/过滤、错误码及权限上下文。
- 在 Python 中封装带 schema 的只读工具，通过 Go API 获取结果；不允许 Agent 直接连业务数据库。
- 先对工具参数、业务结果和错误处理做单元/API 测试，再验证模型工具调用和最终答案。
- 验收标准：对无效参数、无权限、空结果和正常结果都有可预测行为；回答引用工具结果，不能编造数据。

### 第二步：把 Run 与 Trace 做成一致、可查询的执行事实

- 统一 Go/Python 的 Run、事件字段、状态语义和错误模型。
- 为 Run 创建、开始、工具调用、工具结果、完成/失败建立稳定的关联 ID 和序号。
- 明确哪一侧是 Run/Trace 的权威存储，避免两个服务各自维护互相矛盾的状态。
- 限制并脱敏 Trace 中的输入、工具参数和结果；禁止记录密钥或隐藏推理链。
- 验收标准：重启、超时和 Agent 失败场景下，用户仍能通过 Go 查询可信状态及已发生事件。

### 第三步：补可靠执行、取消和权限边界

- 在引入更复杂工作流前，先定义任务投递、超时、重试、幂等和失败恢复语义。
- 取消必须传播到 Agent 执行端，并定义“取消成功、不可取消、已完成”等返回结果。
- 接入身份、资源授权和服务间身份校验；每个工具调用都带有可验证的用户/租户上下文。
- 写操作先不接生产；如后续实现，强制采用审批、幂等、审计和服务端二次授权。

### 第四步：再引入 LangGraph、RAG 和人工介入

- 当单 Agent 工具闭环和事件模型稳定后，再将复杂流程拆成明确节点、条件边和状态。
- RAG 增加文档版本、来源、访问控制、检索证据和答案引用；评估检索质量，不只看生成流畅度。
- Checkpoint 与审批应以可恢复状态机实现：暂停、审批决定、授权复核、继续/拒绝及最终审计。
- 多 Agent 只有在可量化地改善并行、专业隔离或质量时才考虑。

### 第五步：完善测试、部署与运营

- 建立 Python 工具/Agent/图测试，Go handler/service/repository 测试，前端关键交互测试和真实跨服务集成测试。
- 准备固定评测集，检查工具选择、参数正确率、业务结果正确性、拒答/权限行为、延迟与 token 成本。
- 运行依赖解析、Go 编译、pytest、前端构建和 Docker Compose 集成启动；保存可复现的验收记录。
- 需要生产运行时再评估数据库、任务队列、指标/追踪、告警、密钥管理和部署拓扑，不以“企业级”名义提前堆基础设施。

## 9. 测试与验收建议

建议将验收从“接口返回 200”提升为业务行为矩阵：

| 测试层 | 核心验证 |
|---|---|
| Go 业务 API | 参数校验、权限拒绝、过滤分页、错误码、幂等和状态迁移 |
| Python 工具 | schema、HTTP 超时、错误映射、空结果、敏感信息处理 |
| Agent | 工具选择、参数准确性、工具结果忠实性、无证据时的边界表达 |
| 工作流 | 正常路径、工具失败、模型失败、超时、取消、审批暂停/恢复 |
| 前端 | Run 创建、状态刷新、Trace 时间线、失败态、取消和审批操作反馈 |
| 集成 | Go/Python 协议一致、Request ID/Run ID 关联、进程重启后行为 |
| 评测 | 业务正确率、工具调用精度、权限安全、成本、延迟和稳定性 |

验收证据应包括命令、环境版本、结果、失败原因、截图或报告，并明确哪些依赖未能下载/构建。现有交付验证记录已经指出 Go、pytest、前端完整构建和完整 Compose 构建尚未完成，这些项目应在后续有依赖访问条件时补跑。

## 10. 当前结论与建议决策

项目已有合适的学习和演进基础：服务边界清楚，Run/Trace 概念已进入接口设计，默认演示模式降低了开发门槛。当前首要工作不是增加 Agent 数量或马上上向量数据库，而是实现一个真实、只读、可测试的 Go 业务 API，并由 Python 工具受控调用它；同时把状态、Trace 和错误语义统一起来。

在完成只读业务闭环、身份授权、可靠执行和测试验收前，不应将它描述为生产可用，也不应接真实敏感数据或允许模型触发真实写操作。前端 React 技术栈可以继续使用；手册更适合作为目标和阶段验收依据，而不是要求把现有项目改写成手册示例目录。
