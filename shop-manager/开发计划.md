## 1. 开发原则

1. 每一步都是完整功能:能启动、能玩、能验收,并保留前面步骤的全部成果。
2. 配置驱动:商品、设备、事件、主题、等级门槛放在 `assets/data/`,不写死在逻辑里(Python 类比:数据放 `config.py`,逻辑只读它)。
3. 规则与表现分离:经营规则(库存、金币、满意度、事件判定)写成不依赖渲染的纯 TypeScript,可以用 `node` 直接跑测试;3D 场景只负责显示和输入。
4. 每步开工前先固定验收标准;每步结束交付:改了哪些文件、怎么运行、已验证什么、未验证什么。
5. 输入只表达意图(移动、点击),不直接改经营数据,方便 PC 模拟器与真机共用。

## 2. 技术选型

### 2.1 结论

- 引擎:Cocos Creator 3.8 LTS 系列,语言 TypeScript(严格模式)。具体小版本安装时以官网为准。
- 经营规则层(库存、金币、满意度、事件判定):纯 TypeScript,不引用任何引擎接口,可以直接用 node 跑单元测试。
- 配置:JSON 文件,放 `assets/data/`。
- 平台能力(存档、广告、输入):统一封装成接口,微信里用 `wx` 实现,编辑器预览用 mock 实现。

### 2.2 为什么不继续手写 three.js

已核实的事实:

- 微信官方限制:主包不超过 4MB,整个小游戏(主包加分包)不超过 30MB,单个普通分包不限大小(来源:微信开放文档「分包加载」「代码包」)。
- three.js 能通过 weapp-adapter 在小游戏里运行,但社区资料显示需要自己给适配层打补丁(如 `createElementNS`、`addEventListener`),而且渲染循环、资源管线、分包、UI、粒子、音频都得自己搭。
- Cocos Creator 自带可视化编辑器、AssetBundle 分包、微信构建发布,并支持 3D、UI、粒子、动画、音频。第三方资料称"引擎运行时可以不占主包体积",**实测与官方文档都证明这不成立**:Cocos 官方文档明确写明启用"分离引擎"(微信引擎插件)后引擎代码仍计入首包。引擎代码(约 2.9MB)必须靠功能裁剪来压缩。

我的判断:本项目有 16 步、十几类面板、摆放系统、NPC、事件特效,手写引擎基础设施会吃掉大部分精力。现有代码只有 7 个验证文件,现在迁移成本最低。

### 2.3 代价与对策

- 场景和预制体要在编辑器里用鼠标拼装,我在这里没法替你操作编辑器。对策:前期店铺场景由 TypeScript 按配置程序化生成(基础几何体),编辑器里只放一个入口节点;换正式模型时再用编辑器。
- 需要安装 Cocos Dashboard 与编辑器,macOS Apple Silicon 的支持情况开工前确认。
- 构建产物还要再导入微信开发者工具,流程多一层。
- 物理引擎与 wasm 模块会增加包体:默认不启用物理引擎,碰撞用格子和包围盒自己做,步骤 1 实测后再决定。
- 其他备选(LayaAir、Unity 团结引擎):国内资料较少或迁移成本更高,本项目不选。

### 2.4 决策门

步骤 1 实测真机帧率、主包与总包体积、编辑器预览与微信开发者工具的表现。不达标先降低场景复杂度;仍不达标再回到本节重新评估(包括回到手写 three.js),并记录原因。

首次构建实测(2026-10-26,默认配置):微信开发者工具预览上传报错 `source size 5897KB exceed max limit 4MB`,主包超限约 1.8MB。构成:引擎代码 `_virtual_cc.js` 2.9MB;bullet 与 spine 的 wasm 及胶水代码约 0.8MB;天空盒贴图约 0.8MB;`internal` 与 `resources` 两个 bundle 的 Effect 数据各约 0.6MB。压缩方向:关闭用不到的引擎模块(物理、spine、dragonbones、粒子、视频、webview 等)、开启"引擎原生代码分包"、去掉天空盒。每次构建后记录体积到此处。
- 第二次构建(关闭物理/Spine/DragonBones/粒子/视频/WebView/骨骼动画/地形/光照探针,去掉天空盒):`build/wechatgame` 共 2.6MB,其中 `cocos-js` 1.6MB、`assets` 0.9MB,低于 4MB 主包上限,约有 1.4MB 余量。后续每加一类系统(尤其是动画、模型、音频)都要重新测量。

## 3. 架构与目录

### 3.1 分层(依赖只能从上往下)

- `view` / `ui`:Cocos 组件与界面,负责显示和输入,读取 core 的状态,向 core 发命令。
- `core`:纯 TypeScript 的状态、规则、系统。禁止 `import 'cc'`。
- `data`:JSON 配置。
- `platform`:接口加 `wx` / mock 两套实现。

Python 类比:`core` 像一个不依赖 GUI 的业务库,`view` 只是它的一个前端。

### 3.2 为扩展而定的关键设计

1. 单一可序列化状态:存档就是状态的 JSON,带 `schema_version` 和迁移函数。
2. 命令模式:玩家和员工都通过同一批命令改状态(上架、下单、结账等),命令返回成功或失败原因。步骤 14 的员工直接复用,测试也直接调用命令。
3. 系统注册:每个系统(时钟、订单、顾客、事件、员工……)实现 `update(dt)` 与序列化接口;新增功能是新增系统并注册,不改旧代码。
4. 强类型事件总线:系统之间用事件通信(如订单到货、一天结束),不互相直接调用。
5. 配置驱动:商品、设备、等级、事件、主题用字符串 id 互相引用,配一个 node 校验脚本检查引用是否完整。
6. 格子世界:店内用格子坐标。摆放吸附(步骤 8)、通道检测(步骤 11)、顾客寻路(步骤 5)、扩建(步骤 9)共用同一张格子图,寻路自己写 A*(Cocos 内置导航是否可用我未核实,不依赖)。
7. 可设种子的随机数:客流和事件可复现,便于测试。
8. 资源按功能域拆 AssetBundle(店铺、顾客、事件特效、主题);音频和大图走远程加载;模型共用调色板贴图,控制包体。

### 3.3 目录

```

  assets/

      view/        player(第一人称、摇杆)、world(店铺、货架、货车)、npc 表现

    prefabs/  scenes/  models/  audio/

```

### 3.4 工具链与迁移

- 测试:`tests/` 用 node 跑 core;每个经营规则先写测试再接界面。
- 版本管理:`.gitignore` 按 Cocos 官方推荐忽略 library、temp、build 等生成目录。
- 迁移:早期验证文件已删除。其中 `GameState` 的字段设计(金币、满意度、等级、游戏日、是否营业)保留为 `core/state` 的起点。
- 下文步骤里的文件路径沿用逻辑模块名(如 `runtime/clock.js`),实际落在 3.3 的目录里,扩展名为 `.ts`。

- 验收:开发者工具与真机都能连续走动 10 分钟无崩溃;不穿主要墙体;记录真机帧率与包体数据并写回第 2 节。

- 目标:小店有"一天"的节奏,可以手动开门/打烊,进度能保存。

- 验收:一天走完自动进入下一天;打烊状态下不会有顾客逻辑被触发(留接口);存档损坏时能回退到新档而不崩溃。

- 进度:
  - 已完成并验证(自动化):core 层时间/会话/存档/昼夜曲线,共 39 个单元测试通过(含存档损坏、版本过新、写入失败、读档归一化等边界);全部源码通过 strict 类型检查。

### 步骤 3:店长电脑与采购下单

### 步骤 4:送货、卸货与分类理货

- 目标:货到店门口后,玩家亲手搬运并按规则摆上货架,完成"采购→上架"。
- 玩家能做:拾取门口纸箱、抱着缓慢移动、到货架/冷柜旁开箱、逐个放入格子;随时拿起商品调换位置;清理过期商品。
- 主要工作:货车到达与卸货区(`world/`);拾取/搬运/放置交互;`runtime/inventory.js`(货架格子、容量上限);规则:雪糕生鲜只能进冷柜、糕点进玻璃展柜、放错位置顾客不拿取。
- 验收:一笔采购能正确变成货架上的库存;放错容器有明确提示;货架满了放不进去;库存数字与视觉摆放一致。
- 依赖:步骤 3。
- 已定规则(2026-10-26,可改):
  - 订单送达后,卸货区(店门外街道上的黄色区域)生成一个纸箱,旁边出现一辆简易货车(纯视觉,没有碰撞)。手上最多抱一个纸箱,抱着时移动速度降到 60%。
  - 商品必须放进对应容器:雪糕/生鲜 -> 冷柜,糕点 -> 玻璃展柜,其余 -> 普通货架。**放错时直接拒绝并说明原因**(与原文档"放错不售卖"略有不同,更清晰,不会让玩家困惑为什么没人买;如要改回"允许放但顾客不拿",在 `stockContainer` 改)。
  - 容量按格子数算:货架 24 格、冷柜 18 格;水饺等每件占 2 格的商品更占地方。放不下的留在纸箱里,可换个货架继续放。
  - 设备纸箱只能"收进仓库",摆放进店里是步骤 8。
  - 玩家可以把货架上的商品拿起来换位置(同种商品会合并进手上的纸箱)。
  - 暂缓:"清理过期商品"要等有了保质期机制(步骤 10 的商品临期事件)才有意义,本步骤不做。
  - 存档升级到 v3(纸箱、货架库存、仓库设备),v2 旧存档里已送达未处理的订单自动变成卸货区纸箱。
- 进度:
  - 已完成并验证(自动化):纸箱生成、搬起/放回、上架、放错容器、容量上限(含多格商品)、库存守恒、拿起合并、设备收仓库、动作清单(按位置给出可做的动作)、v2->v3 迁移与校验,core 共 75 个单元测试通过;全部源码通过 strict 类型检查与 ES5 降级检查。
  - 已写但未在编辑器/真机运行:卸货区纸箱与货车、货架/冷柜上的商品方块、手上纸箱、右下角动作按钮、抱箱减速。
  - 未验证:商品方块在货架/冷柜上的位置是否贴合、动作按钮是否遮挡视野、纸箱体积对包体的影响(应很小,方块是共用网格)。

### 步骤 5:顾客与收银,跑通完整一天

- 目标:开门后顾客进店购物、排队,玩家手动收银赚金币,形成主线闭环(采购→上架→营业→收银→再投入)。
