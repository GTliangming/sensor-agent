# 一屋百年 — 数据结构设计文档

**文档版本：** v1.0
**文档状态：** 第一版设计基线
**项目名称：** 一屋百年
**游戏引擎：** Cocos Creator 3.8.8
**开发语言：** TypeScript
**配置格式：** JSON
**数据校验：** JSON Schema Draft 2020-12 + TypeScript 业务校验器

# 一、文档目标

本文件定义《一屋百年》第一版游戏的数据结构、配置规范、数据引用关系、运行时数据模型和校验规则。

本项目采用数据驱动的关卡设计方式。

游戏核心玩法由 TypeScript 实现，物件、场景、章节、关卡等内容通过 JSON 配置管理。

设计目标：

1. 新增普通物件时，主要通过物件配置和美术资源完成，不修改核心玩法代码。
2. 新增普通关卡时，通过新增关卡 JSON 完成，不修改核心玩法代码。
3. 新增章节时，可以复用现有场景、物件和关卡系统。
4. 所有配置在开发阶段能够自动校验。
5. 能够自动发现配置错误、引用错误、资源缺失和关卡不可完成问题。
6. 为后续关卡编辑器、批量关卡生产和数据后台预留扩展能力。

## 1.1 核心设计原则

- 物件基础信息全局维护，不在关卡中重复定义。
- 场景负责背景、区域和布局锚点。
- 章节负责组织关卡和解锁条件。
- 关卡负责物件实例、坐标、遮挡关系和玩法参数。
- TypeScript 负责游戏逻辑。
- JSON 负责提供游戏配置。
- JSON Schema 负责检查配置格式。
- TypeScript 业务校验器负责检查配置之间的关系和玩法规则。
- 关卡可完成性检查负责判断关卡是否能够正常通关。
- 已确认的玩法规则不得由开发工具擅自修改。

# 二、第一版已确认的玩法规则

以下规则作为第一版数据设计的依据。

| 规则                   | 正式定义                       |
| ---------------------- | ------------------------------ |
| 正确物件               | 匹配目标后立即清除             |
| 正确物件是否进入归位格 | 不进入                         |
| 目标匹配               | 按具体物件 ID 精确匹配         |
| 目标计数               | 同一种物件累计计数             |
| 找寻格显示             | 一个目标物件类型占一个格子     |
| 数量显示               | 剩余数量 / 初始总数量          |
| 错误物件               | 占用归位格                     |
| 归位格满               | 暂停游戏，提供救场或重开       |
| 遮挡关系               | 手动配置 + 程序检查            |
| 物件布局               | 手动摆放 + 锚点辅助            |
| 广告                   | 第一版模拟，不接入真实广告 SDK |
| 坐标                   | 设计分辨率像素坐标             |

## 2.1 目标匹配规则

第一版采用具体物件 ID 精确匹配。

例如：

| 物件 ID    | 名称   | category    |
| ---------- | ------ | ----------- |
| headphones | 耳机   | electronics |
| phone      | 手机   | electronics |
| charger    | 充电头 | electronics |
| milk_tea   | 奶茶杯 | drinkware   |

如果关卡目标是：

- 耳机 × 3
- 手机 × 2

那么只有 `headphones` 可以增加耳机目标进度，只有 `phone` 可以增加手机目标进度。

即使充电头和耳机都属于 `electronics`，也不能相互替代。

`category` 仅用于物件分类、图鉴、筛选和后台管理，不参与第一版目标匹配。

目标匹配代码：

```
const isCorrect = itemInstance.itemId === objective.itemId;
```

## 2.2 正确物件拾取流程

玩家点击场景物件：

1. 检查物件是否存在。
2. 检查物件是否处于可点击状态。
3. 检查物件是否被其他物件遮挡。
4. 判断物件是否符合当前目标。
5. 如果正确：
   - 将物件状态设置为 `pending_pickup`。
   - 防止重复点击。
   - 结算目标进度，增加 1。
   - 播放飞向目标格的动画。
   - 动画结束后移除场景节点。
   - 将运行时物件状态设置为 `removed`。
   - 更新目标格剩余数量。
   - 检查是否完成全部目标。
6. 如果错误：
   - 检查归位格是否有空位。
   - 将物件放入归位格。
   - 将物件状态设置为 `in_collection`。
   - 归位格占用数量增加 1。
   - 不增加目标进度。

正确物件不进入归位格，错误物件才占用归位格。

**重要：** 目标进度应在拾取成功时结算，不能依赖动画回调重复结算。动画只负责表现，不能成为重复增加进度的入口。

## 2.3 归位格满的处理

当错误物件占满归位格：

1. 暂停游戏交互。
2. 显示失败/救场界面。
3. 提供救场和重开入口。
4. 玩家选择后再继续对应流程。

第一版只定义状态和入口，不在本数据结构中提前固定救场消耗、广告奖励或具体清理方式。

# 四、通用数据规范

## 4.1 ID 命名规则

所有配置 ID 使用英文小写和下划线。

推荐：

```
headphones
medicine_bottle
charging_cable
chapter_01
scene_rental_room
level_001
instance_headphones_001
```

不推荐：

```
耳机
Headphones
HeadPhones01
物件1
```

## 4.2 ID 唯一性

| 数据类型               | 唯一性要求          |
| ---------------------- | ------------------- |
| Item.id                | 全局唯一            |
| ItemVariant.id         | 在所属 Item 内唯一  |
| Scene.id               | 全局唯一            |
| SceneZone.id           | 在所属 Scene 内唯一 |
| SceneAnchor.id         | 在所属 Scene 内唯一 |
| Chapter.id             | 全局唯一            |
| Chapter.chapterNumber  | 全局唯一            |
| Level.id               | 全局唯一            |
| Level.itemInstances.id | 在所属 Level 内唯一 |

## 4.3 坐标规范

第一版使用设计分辨率像素坐标。

设计分辨率暂定：

```
{
  "width": 1080,
  "height": 1920
}
```

坐标定义：

- 原点位于画布左下角。
- X 轴向右增加。
- Y 轴向上增加。
- 物件 position 表示物件节点的锚点位置。
- 物件实际显示尺寸由 Item.size × Instance.scale 决定。
- 物件旋转使用角度制。
- 物件缩放使用正数比例。

注意：Cocos Creator 的节点坐标系和 JSON 设计坐标系可能存在转换差异。坐标转换统一由布局模块处理，不允许不同模块自行转换。

## 4.4 美术资源路径

配置中只记录资源相对路径，不记录本机绝对路径。

例如：

```
{
  "image": "items/headphones/headphones_black"
}
```

资源加载模块负责将路径转换为 Cocos Creator 对应的资源加载路径。

资源路径不包含文件扩展名，第一版统一使用项目约定的资源路径格式。

# 五、物件配置 item.schema.json

## 5.1 设计目的

物件配置定义游戏中所有可以被寻找、点击和收集的基础物件。

例如：

- 耳机
- 手机
- 奶茶杯
- 快递盒
- T 恤
- 数据线
- 充电头
- 遥控器

同一种物件可以有不同外观变体。

物件基础数据只维护一份，关卡通过 `itemId` 引用。

## 5.2 字段定义

| 字段             | 类型   | 必填 | 说明               |
| ---------------- | ------ | ---- | ------------------ |
| id               | string | 是   | 物件唯一 ID        |
| name             | string | 是   | 物件名称           |
| category         | string | 是   | 物件分类           |
| description      | string | 否   | 物件描述           |
| size             | object | 是   | 默认尺寸           |
| variants         | array  | 是   | 外观变体           |
| defaultVariantId | string | 是   | 默认变体 ID        |
| allowedZoneTags  | array  | 是   | 允许出现的区域标签 |
| hitArea          | object | 否   | 点击区域           |
| tags             | array  | 是   | 物件标签           |

**设计说明：**

使用 `allowedZoneTags`，不直接绑定某个场景的具体 zone ID。

例如：

- `desktop`
- `bedside`
- `storage`
- `floor`
- `sofa`

具体场景中的 Zone 可以拥有对应标签。这样全局物件库不会依赖某一个场景的区域命名。

## 5.5 物件业务校验

1. Item ID 全局唯一。
2. 同一个 Item 内 Variant ID 唯一。
3. defaultVariantId 必须存在于 variants。
4. 物件图片资源必须存在。
5. size.width 和 size.height 必须大于 0。
6. hitArea 的宽高必须大于 0。
7. allowedZoneTags 必须使用项目统一的标签规范。
8. 不允许出现重复标签。

# 六、场景配置 scene.schema.json

## 6.1 设计目的

场景负责定义：

- 场景背景。
- 设计分辨率。
- 可摆放区域。
- 区域边界。
- 布局锚点。

同一个场景可以被多个关卡复用。

例如第一章多个关卡都可以使用出租屋卧室背景，但每关的物件实例和遮挡关系不同。

## 6.2 字段定义

| 字段             | 类型   | 必填 | 说明         |

| background       | string | 是   | 背景资源路径 |
| designResolution | object | 是   | 设计分辨率   |
| zones            | array  | 是   | 场景区域     |
| anchors          | array  | 否   | 布局辅助锚点 |

```
    }
  ]
}
```

## 6.5 场景业务校验

1. Scene ID 全局唯一。
2. Zone ID 在所属场景内唯一。
3. Anchor ID 在所属场景内唯一。
4. 背景资源必须存在。
5. Zone bounds 不能超出设计画布。
6. Anchor position 不能超出设计画布。
7. 所有 Zone 必须有合法 tags。
8. 关卡引用的 sceneId 必须存在。
9. 关卡物件实例的 zone 必须存在于对应场景。
10. Item.allowedZoneTags 与 Zone.tags 必须至少存在一个匹配项；若不匹配，应报错或按明确配置策略处理。

# 七、关卡配置 level.schema.json

## 7.1 设计目的

每个关卡使用独立 JSON 文件管理。

关卡配置负责定义：

- 关卡基础信息。
- 所属章节。
- 使用场景。
- 难度。
- 目标物件。
- 场景物件实例。
- 物件位置。
- 物件遮挡。
- 找寻格。
- 归位格。
- 广告模拟配置。
- 特殊机制。
- 提示配置。
- 通关条件。

关卡不重复定义物件的基础属性。

## 7.2 字段定义

| 字段             | 类型    | 必填 | 说明           |
| ---------------- | ------- | ---- | -------------- |
| id               | string  | 是   | 关卡 ID        |
| chapterId        | string  | 是   | 所属章节       |
| levelNumber      | integer | 是   | 章节内关卡序号 |
| name             | string  | 是   | 关卡名称       |
| sceneId          | string  | 是   | 使用的场景     |
| difficulty       | number  | 是   | 难度值         |
| designResolution | object  | 是   | 设计分辨率     |
| objectives       | array   | 是   | 寻找目标       |
| itemInstances    | array   | 是   | 场景物件实例   |
| gridConfig       | object  | 是   | 格子配置       |
| mechanicConfig   | object  | 是   | 机制配置       |
| hintConfig       | object  | 是   | 提示配置       |
| completionConfig | object  | 是   | 通关配置       |

## 7.3 Objective 目标配置

第一版按照具体 itemId 匹配。

一个目标类型占用一个找寻格。

例如：

```
{
  "objectives": [
    {
      "itemId": "headphones",
      "requiredCount": 3,
      "displayVariant": "black"
    },
    {
      "itemId": "medicine_bottle",
      "requiredCount": 2
    }
  ]
}
```

表示：

- 耳机需要找到 3 个。
- 药瓶需要找到 2 个。
- 耳机占一个找寻格。
- 药瓶占一个找寻格。

`requiredCount` 是同一目标物件类型需要找到的数量。

`displayVariant` 是目标格展示使用的物件变体，可选；不填写时使用 Item.defaultVariantId。

## 7.4 ItemInstance 物件实例

同一个物件可以在同一关卡出现多次。

例如三个耳机：

```
[
  {
    "id": "instance_headphones_001",
    "itemId": "headphones",
    "variantId": "black"
  },
  {
    "id": "instance_headphones_002",
    "itemId": "headphones",
    "variantId": "white"
  },
  {
    "id": "instance_headphones_003",
    "itemId": "headphones",
    "variantId": "black"
  }
]
```

每一个实例拥有独立 ID、位置、层级和遮挡关系。

## 7.5 遮挡关系定义

`blocking` 表示当前物件被哪些物件遮挡。

例如：

```
{
  "id": "instance_book",
  "blocking": [
    "instance_phone",
    "instance_cup"
  ]
}
```

表示：

- 手机遮挡书本。
- 奶茶杯遮挡书本。
- 手机和奶茶杯都被移除后，书本才能点击。

程序检查时必须确保：

1. blocking 中的实例 ID 存在。
2. 不允许自身遮挡自身。
3. 不允许循环遮挡。
4. 所有遮挡关系能够最终解除。
5. 被遮挡物件只有在所有遮挡者移除后才能点击。

## 7.6 找寻格规则

第一版正式定义：

**一个目标物件类型占一个找寻格。**

格子内显示：

- 目标物件图片。
- 目标物件名称（是否展示由 UI 设计决定）。
- 剩余数量。
- 初始总数量。
- 完成状态。

数量显示格式：

```
剩余数量 / 初始总数量
```

例如：

```
3/3
2/3
1/3
0/3
```

当剩余数量为 0：

- 该目标标记为 completed。
- 找寻格显示完成状态。
- 不再接受该目标的进度更新。

## 7.7 找寻格容量

| 字段                  | 含义                         |
| --------------------- | ---------------------------- |
| baseCount             | 初始可显示的目标格数量       |
| maxCount              | 最多可显示的目标格数量       |
| unlockableTargetSlots | 可通过广告模拟解锁的额外槽位 |

例如：

```
{
  "targetSlots": {
    "baseCount": 3,
    "maxCount": 5
  }
}
```

表示：

- 初始最多显示 3 个目标格。
- 扩展后最多显示 5 个目标格。
- 如果目标种类超过初始容量，需要按确定的扩展规则显示剩余目标。
- 第一版广告仅模拟，不接入真实广告。

**重要规则：**

找寻格容量不能导致目标无法显示或关卡无法完成。

必须通过关卡业务校验确保：

- 目标类型总数不超过 maxCount。
- 如果目标类型超过 baseCount，必须存在合法的扩展路径。
- 未解锁目标不得丢失。
- 不允许出现无法继续操作的关卡状态。

## 7.8 归位格规则

归位格只存放错误物件。

字段：

| 字段     | 含义         |
| -------- | ------------ |
| capacity | 归位格总容量 |

当归位格占满：

- 游戏暂停。
- 进入失败救场流程。
- 玩家可以选择救场或重开。

救场的具体规则由后续产品设计确定，不在本 Schema 中提前固定。

## 7.11 关卡业务校验

1. Level ID 全局唯一。
2. levelNumber 必须大于等于 1。
3. itemInstances 实例 ID 在当前关卡内唯一。
4. objectives 中的 itemId 必须存在。
5. itemInstances 中的 itemId 必须存在。
6. variantId 必须属于对应 Item。
7. displayVariant 必须属于目标 Item 的 variants。
8. 同一个 itemId 在 objectives 中不能重复定义，数量应合并到一个目标项。
9. 目标物件数量必须满足 requiredCount。
10. blocking 引用必须存在。
11. blocking 不允许自引用。
12. blocking 不允许形成循环。
13. zone 必须存在于对应场景。
14. 物件坐标不能超出设计画布，除非明确允许。
15. 物件应满足所在区域的允许标签要求。
16. targetSlots.maxCount 必须大于或等于 baseCount。
17. objectives.length 不能超过 maxCount。
18. 当 objectives.length 超过 baseCount 时，必须配置合法的扩展槽位。
19. unlockableTargetSlots 必须大于 baseCount 且不超过 maxCount。
20. nextLevelId 必须指向有效关卡。
21. 关卡设计分辨率必须与场景分辨率一致。
22. 目标物件必须能够通过合法点击顺序被获取。
23. 归位格满的处理必须符合已确认的失败流程。

# 十一、运行时数据结构

配置数据是静态数据，运行时数据是玩家操作过程中不断变化的数据。

两者必须分开。

不能直接修改原始 JSON 配置来记录玩家的操作进度。

## 11.1 目标进度

```
export interface ObjectiveProgress {
  itemId: string;
  requiredCount: number;
  collectedCount: number;
  remainingCount: number;
  completed: boolean;
}
```

例如：

```
const objectiveProgress: ObjectiveProgress = {
  itemId: 'headphones',
  requiredCount: 3,
  collectedCount: 1,
  remainingCount: 2,
  completed: false,
};
```

## 11.2 物件实例运行时状态

```
export type ItemInstanceStatus =
  | 'available'
  | 'pending_pickup'
  | 'removed'
  | 'in_collection';

export interface RuntimeItemInstance {
  id: string;
  itemId: string;
  variantId: string;
  status: ItemInstanceStatus;
}
```

状态说明：

| 状态           | 说明                       |
| -------------- | -------------------------- |
| available      | 可点击                     |
| pending_pickup | 正在结算拾取，防止重复点击 |
| removed        | 已经从场景移除             |
| in_collection  | 错误物件，已经进入归位格   |

# 十二、配置加载和校验系统

## 12.1 设计目标

所有配置在进入游戏运行时之前，都必须经过校验。

开发阶段需要支持：

- 一键检查全部 JSON。
- 输出具体错误文件。
- 输出字段路径。
- 输出错误原因。
- 校验跨文件引用。
- 校验美术资源。
- 校验关卡可完成性。

## 12.2 校验流程

```
读取 JSON 配置
      |
      v
JSON 解析
      |
      v
JSON Schema 校验
      |
      v
ID 唯一性校验
      |
      v
跨文件引用校验
      |
      v
美术资源路径校验
      |
      v
关卡业务规则校验
      |
      v
遮挡关系检查
      |
      v
关卡可完成性检查
      |
      v
输出校验报告
```

任何阻断级错误都必须导致校验失败。

## 12.3 推荐校验工具

推荐使用 Ajv，支持 JSON Schema Draft 2020-12。

安装：

```
npm install ajv ajv-formats
```

注意：需要确保项目使用支持 Draft 2020-12 的 Ajv 实例和对应配置。

建议开发命令：

```
npm run validate:configs
```

如果当前 Cocos 项目无法直接运行独立 TypeScript 校验脚本，可以将校验器放在项目根目录下的独立 Node.js 工具目录中，不必强行放进 Cocos 运行时。

## 12.4 校验器职责

### SchemaValidator.ts

- 加载四份 Schema。
- 使用 Ajv 校验 JSON。
- 输出文件名、字段路径和错误信息。

### ConfigValidator.ts

- 组织全部校验流程。
- 汇总校验结果。
- 输出最终报告。

### ReferenceValidator.ts

- 检查 Item ID。
- 检查 Scene ID。
- 检查 Chapter ID。
- 检查 Level ID。
- 检查 Variant ID。
- 检查 Zone ID。
- 检查 Anchor ID。

### ResourceValidator.ts

- 检查物件图片资源。
- 检查场景背景资源。
- 检查章节封面资源。
- 检查资源路径是否合法。

### LevelValidator.ts

- 检查目标数量。
- 检查实例数量。
- 检查格子容量。
- 检查坐标边界。
- 检查物件区域合法性。

### BlockingValidator.ts

- 检查遮挡引用。
- 检查自引用。
- 检查循环遮挡。
- 检查遮挡关系是否可以解除。

### PlayabilityValidator.ts

- 检查关卡是否能够完成。
- 检查目标物件是否可达。
- 检查是否存在永久遮挡。
- 检查目标数量是否足够。
- 检查合法点击顺序。

# 十三、关卡可完成性检查

关卡可完成性检查是本项目的重要功能。

JSON Schema 只能检查字段格式，不能判断玩家能不能通关。

## 13.1 目标数量检查

假设目标：

```
{
  "itemId": "headphones",
  "requiredCount": 3
}
```

那么关卡中至少需要存在 3 个有效的 headphones 实例。

如果只有 2 个，必须报错。

## 13.2 遮挡关系检查

合法示例：

```
A 被 B 遮挡
B 被 C 遮挡
C 没有遮挡
```

玩家可以：

1. 点击 C。
2. C 移除。
3. 点击 B。
4. B 移除。
5. 点击 A。

非法示例：

```
A 被 B 遮挡
B 被 A 遮挡
```

形成循环遮挡，必须报错。

## 13.3 可完成性模拟

第一版先实现基础静态检查：

- 所有目标实例数量足够。
- 所有遮挡引用存在。
- 遮挡关系无循环。
- 目标物件最终可以解除遮挡。
- 目标格容量和扩展规则合法。

后续升级为完整状态搜索或模拟器：

- 根据当前可点击物件模拟点击。
- 正确物件移除。
- 更新目标进度。
- 更新遮挡状态。
- 错误物件占用归位格。
- 检查是否存在至少一条通关路径。

需要注意：如果错误物件可能由玩家主动点击，不能简单地将所有错误物件都当作必然拾取。可完成性检查要区分“关卡数据必然死局”和“玩家误操作导致失败”。

# 十八、最终设计结论

《一屋百年》第一版采用：

**全局物件库 + 场景配置 + 章节配置 + 独立关卡 JSON + 自动校验系统。**

核心规则：

1. 物件基础信息全局维护。
2. 场景负责背景、区域和锚点。
3. 章节负责组织关卡和解锁。
4. 关卡负责目标、实例、位置和遮挡。
5. 目标通过具体 itemId 精确匹配。
6. 一个目标物件类型占用一个找寻格。
7. 找寻格显示剩余数量 / 初始总数量。
8. 正确物件匹配后立即清除。
9. 错误物件进入归位格。
10. 归位格满后暂停并进入救场/重开流程。
11. JSON Schema 负责格式校验。
12. TypeScript 业务校验器负责引用和规则校验。
13. 可完成性检查负责验证关卡是否能够通关。

最终目标：

**普通关卡可以通过 JSON 配置持续生产，新增普通物件和普通关卡不需要反复修改游戏核心代码。**

本设计先以第一章 10 关为验证范围。第一章完整跑通后，再逐步扩展到后续章节、更多物件和关卡编辑工具。

## 19.2 玩法规则

1. **归位格**：第一章统一 4 格。归位格填满即暂停，进入救场面板。
2. **救场**：看模拟广告后清空归位格（格内物件直接丢弃），每关限一次；也可以重开或放弃（放弃即失败）。
3. **提示**：两种都保留。一是无操作达到 `autoHintSeconds`（第 6 关 8 秒，其余 12 秒）后自动提示，不消耗次数；二是每局 3 次主动提示。提示优先选能直接点的目标，目标都被压住时提示压在目标上方、当前可点的物件；有多个候选时选离上一次提示最远的。
4. **星级**：每关有“必要失误”数（`requiredWrong`）。只统计超出它的失误：没有多余失误 3 星，多 1–2 次 2 星，更多为 1 星；用过救场固定 1 星。
5. **存档**：`{version: 1, chapterId, unlockedLevel, completedLevels, stars, settings: {soundEnabled}}`，读取失败或版本不符时恢复默认；星级保留历史最好成绩。
6. **切后台**：页面切到后台（来电、切 App）自动暂停。
7. **音效与震动**：拾取、完成一种目标、放错、点到被压住的物件、提示、通关、归位格满都有短音效，放错/压住/通关/失败附带震动；可在选关页和暂停面板里统一开关（`settings.soundEnabled`）。
8. **新手引导**：第 1 关首次游玩时，用手指指向一个可点的目标；第一次拾取后提示归位格的规则，再拾取一次后引导消失。
9. **最后一个定位**：某种目标只差最后 1 个时，找寻格上出现放大镜，点一下免费高亮它（被压住时高亮压在它上面、当前可点的物件），不消耗提示次数。参考同类游戏玩家最常见的抱怨“最后一个怎么也找不到”。
10. **归位格危险提示**：归位格只剩 1 格时，标签变红并提示“再放错就满了”，空格闪烁。
11. **公平说明**：救场和失败面板写明“本关一定有解，最少只需放错 N 次，不需要看广告”，避免《羊了个羊》式“故意做成死局逼人看广告”的观感。
12. **进度感**：选关页和通关面板显示章节进度（已通关数、总星数）。

## 19.3 遮挡、图标轮廓与贴图

- 遮挡关系由生成脚本按图标真实轮廓计算：上层图标本体实际盖住下层图标本体至少 3 个采样点（48×48 轮廓）才算遮挡。
- `npm run export:icons` 用浏览器把占位图标烘焙成贴图 `web/public/sprites/<物件>__<变体>.webp`（多变体物件按变体颜色着色），同时导出轮廓 `web/src/data/item_masks.json`。游戏运行时只加载贴图，不现场绘制，所以任何设备上看到的图标都与轮廓一致。
- 关卡生成、`npm run validate:configs`、运行时点击判定都读同一份轮廓；校验器会检查 `blocking` 与轮廓完全一致。

## 19.4 屏幕适配

- 设计宽度固定 1080，高度随屏幕比例在 1920～2400 之间变化，手机上铺满整屏，并避开刘海和底部手势条的安全区；桌面浏览器按 9:16 居中显示。
- 关卡按主流全面屏 1080×2340 的物品区生成（`SCENE_RECT = {x:30, y:450, w:1020, h:1435}`）；屏幕更矮时整堆物件等比缩小放进可用区域，等比缩放不改变遮挡关系。
- 画面只在有变化时重绘（动画、提示闪烁、状态变化），静止时不耗电。

## 19.5 第一章数据规模

- 物件数 32–66 个/关（原规划 12–24 个铺不满整块物品区），按 32、39、39、50、50、59、65、66、63、62 逐步增加，避免难度突然陡增；第 1–6 关 2 层，第 7–10 关 3 层。
- 每关 14 种干扰物；被压住的目标比例随关卡递增；目标分布在物品区 3×3 宫格中至少 5 格。
- 每关具体数据见《关卡设计数据库》第 6 节。
