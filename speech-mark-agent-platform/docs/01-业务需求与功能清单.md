# 01 业务需求与功能清单

**项目：** Annotation Ops Agent（语音标注智能运营分析平台）
**版本：** V1.0（定稿）
**日期：** 2026-11-02
**依据：** 《语音标注智能运营分析平台总体设计方案》V2.0；《annotation_ops_agent_plan_v1_1》工程细节；2026-11-02 已确认的四项架构决策

---

## 1. 背景与目标

### 1.1 背景

现有语音标注平台（speech-mark）已经具备完整业务能力：项目、任务、题包、题目、标注、审核、人员、工作组、统计与导出。平台前端为 Vue3，后端为 Go，业务数据以 Go 平台为准。

本项目在现有平台之外建设一套**独立的、严格只读的 Agent 智能运营分析平台**，通过 HTTP 只读 API 对接现有平台。不修改现有 Go 业务代码的既有语义，不嵌入现有 Vue3 前端，不直连业务数据库。

### 1.2 项目定位

Agent 不是聊天机器人，而是一套能完成以下闭环的运营分析系统：

1. 理解用户提出的业务问题；
2. 自主规划需要查询的数据；
3. 调用一个或多个只读业务工具；
4. 获取真实业务数据；
5. 用确定性程序完成统计、分析和交叉验证；
6. 发现业务异常与潜在风险；
7. 给出有数据依据、可追溯的结论和建议；
8. 生成可复核的运营报告。

### 1.3 业务目标

| 目标 | 说明 | 衡量方式 |
|---|---|---|
| A. 解决真实运营问题 | 减少人工查数、统计、整理报告的成本 | 典型巡检任务从人工 1–2 小时降到分钟级 |
| B. 建立可验证的分析能力 | 每个结论可追溯到接口数据、计算口径和规范条款 | 报告证据覆盖率、人工复核通过率 |
| C. 形成 Agent 工程能力 | 工具调用、编排、RAG、记忆、评测、可观测性 | 各阶段验收标准全部通过 |

### 1.4 第一阶段成功标准

- 能查询真实 Go 平台数据，结果与原平台一致；
- 能完成跨任务、跨题包的多步骤分析；
- 每个异常结论都能给出数据范围、样本量、计算口径；
- 规范类结论必须带版本和条款引用；
- 无证据时明确表达不确定，不编造；
- 全链路只读，不存在任何写工具；
- 关键执行步骤、工具调用、数据来源可审计。

## 2. 用户角色与权限

| 角色 | 主要需求 | Agent 能力 |
|---|---|---|
| 平台管理员 | 全局生产监控、异常处理、调度 | 跨项目分析、异常报告、方案建议 |
| 项目管理员 | 项目进度、质量、规范管理 | 项目巡检、规范问答、返工建议 |
| 工作组管理员 | 组内任务、成员、产能管理 | 工作组生产分析、承接情况分析 |
| 质检员 / 审核员 | 复核问题、判断规范争议 | 争议检索、问题归因、复核摘要 |
| 标注员 | 理解规范、查看个人问题 | 规范解释、个人质量反馈（权限允许时） |

### 2.1 权限原则

1. **最终权限以 Go 平台为准**，Agent 只做范围收窄，不做权限放大。
2. Agent 平台使用独立轻量登录，但必须通过绑定表映射到 Go 平台用户。
3. 绑定关系由**管理员统一导入**，不允许用户自行填写工号冒用身份。
4. 未绑定或绑定失效时返回明确错误，不降级为全量可读。
5. 模型输出的 `user_id`、`project_id` 一律不能作为授权依据。

### 2.2 绑定模型

| 字段 | 说明 |
|---|---|
| agent_user_id | Agent 平台用户 ID |
| go_user_id | Go 平台用户 ID（优先）或工号 |
| go_user_name | 冗余展示名 |
| status | active / disabled |
| bound_by | 执行导入的管理员 |
| bound_at | 绑定时间 |

## 3. 范围与边界

### 3.1 第一阶段纳入

- Go 平台真实只读 API 接入；
- 项目、任务、题包、题目、标注记录、人员、工作组查询；
- 生产与质量指标计算；
- 异常候选识别（规则优先）；
- 标注规范 RAG 与引用；
- 单 Agent + LangGraph 编排；
- 纯函数工具层（MCP-ready，暂不接 MCP）；
- 对话、运行轨迹、证据展示；
- Agent 自身的用户、会话、运行、工具调用、报告存储；
- 基础评测与可观测性。

### 3.2 明确不做

- 不重做标注平台，不替换现有 Vue3 / Go；
- 不让 Agent 直接连接生产数据库；
- 不让 LLM 生成并执行 SQL；
- 不开放任何生产写操作（含领题、领包、投放、结包、打回、保存答案）；
- 不把业务状态复制到 Agent 数据库当作事实来源；
- 不在第一阶段引入多 Agent 群体、Redis、消息队列、Kubernetes；
- 不为了覆盖技术点而提前微调模型。

### 3.3 只读边界（硬约束）

1. Agent 不注册任何写工具；
2. Go 侧 `/agent/v1/*` 只注册 GET；
3. Agent 使用独立的服务凭证与绑定用户身份；
4. 不允许直连业务库；
5. 不允许通过脚本、SQL、任意 URL 绕过 API；
6. 外部请求白名单限制；
7. 查询数量、分页、执行时间受限；
8. 敏感字段脱敏。

安全必须在代码、凭证和服务端权限层实现，不能只靠 System Prompt。

### 3.4 数据最小化

- 不一次性把全部题目正文传给模型；
- 人员分析只取必要字段；
- 音频、原始文本、个人信息按最小字段读取；
- 工具优先返回摘要与引用 ID，详情按需二次读取；
- 真实数据不得用于公共评测集或第三方训练，除非获得明确授权。

## 4. 核心业务对象与统计口径

### 4.1 业务对象

| 对象 | 含义 | 与 speech-mark 的映射（候选） |
|---|---|---|
| Project | 标注项目 | MarkProject |
| Task | 任务 | MarkTask |
| Bundle | 题包 | MarkTaskBatch |
| Question | 题目 | MarkProjectTaskTopicDatum |
| Annotation | 标注答案 | MarkPageTopicAnswer |
| Review | 质检 / 审核 | 审核字段与质检相关表 |
| User | 平台用户 | MarkUser |
| WorkGroup | 工作组 | v2 workgroup |
| Guideline | 标注规范 | 需新建知识库，不依赖业务表 |

> 字段映射必须以真实 API 文档和实际响应为准，本文只给业务语义，不替代接口契约。

### 4.2 业务约束

- 题包分配给承接人后，题包下所有题目按现有规则进入该承接人的处理范围；
- “题包承接”与“单题领取”不是一回事，Agent 不得混用；
- 一个用户可管理多个工作组；一个用户最多属于一个工作组（以平台实际规则为准）；
- 工作组管理员与普通成员身份互斥；
- 以上约束以 Go 平台实现为准，Agent 只读并遵循。

### 4.3 统计口径（所有分析必须显式声明）

| 口径项 | 要求 |
|---|---|
| 时区 | 统一使用业务时区，存储统一，展示本地 |
| 时间范围 | `[start_time, end_time)` 左闭右开 |
| 状态范围 | 明确包含哪些业务状态 |
| 去重规则 | 按题目、答案版本还是最终审核记录 |
| 统计粒度 | 项目 / 任务 / 题包 / 题型 / 承接人 / 工作组 |
| 数据完整性 | 是否读完所有分页，是否存在延迟同步 |

口径不明确时，Agent 应先追问，或把口径作为报告的显式前提。

### 4.4 指标定义

**生产效率类**

- 题包分配数、承接数、题目完成数；
- 完成率 = 已完成题目数 / 应完成题目数；
- 待处理积压量、超时题包数；
- 平均处理时长、中位处理时长、P90；
- 人员负载分布。

每个指标必须明确分母、状态范围、时间窗口和去重口径。

**标注质量类**

- 审核通过率、退回率、复核一致率；
- 规范/格式检查通过率、必填字段错误率；
- 多人标注一致性（Cohen's Kappa、Fleiss' Kappa，按样本结构选择）；
- ASR 场景的 WER/CER、说话人分离的 DER、时间戳的边界偏差（需可信参考数据）。

没有 Ground Truth 时，不得把“模型判断正确率”包装成业务准确率。

## 5. 业务能力清单

优先级：P0 = 第一阶段必须；P1 = 第一阶段尽量；P2 = 后续阶段。

### 5.1 业务数据查询

| 编号 | 能力 | 说明 | 优先级 |
|---|---|---|---|
| BR-Q-01 | 查询可访问项目 | 只返回当前绑定用户有权访问的项目 | P0 |
| BR-Q-02 | 查询项目概览 | 任务数、题包数、完成率、时间范围 | P0 |
| BR-Q-03 | 查询任务列表/详情 | 支持状态、时间、项目筛选与分页 | P0 |
| BR-Q-04 | 查询题包列表/详情 | 含承接人、题量、完成数、状态 | P0 |
| BR-Q-05 | 查询题包下题目 | 分页，默认不返回完整正文 | P1 |
| BR-Q-06 | 查询题目标注/审核结果 | 摘要优先，敏感字段脱敏 | P1 |
| BR-Q-07 | 查询人员信息 | 授权范围内最小字段 | P1 |
| BR-Q-08 | 查询工作组与成员 | 组、管理员、成员关系 | P1 |
| BR-Q-09 | 查询历史流转/审核记录 | 用于追溯 | P2 |

### 5.2 业务统计分析

| 编号 | 能力 | 说明 | 优先级 |
|---|---|---|---|
| BR-S-01 | 任务维度统计 | 总量、完成数/率、延期、平均完成时间 | P0 |
| BR-S-02 | 人员维度统计 | 任务量、完成量、效率、审核通过率、负载 | P1 |
| BR-S-03 | 工作组维度统计 | 总量、完成率、效率、负载、审核情况 | P1 |
| BR-S-04 | 审核维度统计 | 审核量、通过率、退回率、耗时、退回原因分布 | P1 |
| BR-S-05 | 时间趋势对比 | 与上一周期/基线对比 | P1 |
| BR-S-06 | 自定义分组统计 | 按项目/题型/承接人/工作组 | P2 |

要求：统计一律由 Go 聚合接口或 Python 确定性代码完成，LLM 只负责理解问题和解释结果。

### 5.3 异常检测与诊断

| 编号 | 能力 | 说明 | 优先级 |
|---|---|---|---|
| BR-A-01 | 长期无进展题包 | 超过阈值未更新 | P0 |
| BR-A-02 | 低完成率/临期风险 | 截止前完成率低于阈值 | P0 |
| BR-A-03 | 审核退回率异常 | 相对历史基线明显上升 | P1 |
| BR-A-04 | 人员工作量异常 | 明显偏离同类任务基线 | P1 |
| BR-A-05 | 工作组效率下降 | 周环比/基线对比 | P1 |
| BR-A-06 | 流转时间异常 | 状态停留时间异常 | P2 |
| BR-A-07 | 多标注结果分歧 | 同一题多答案明显不一致 | P2 |
| BR-A-08 | 智能归因 | 结合数据与规范给出原因假设 | P2 |

规则必须支持按项目、题型、时间窗口配置，不能用一个阈值评价所有人和所有任务。

### 5.4 业务建议

| 编号 | 能力 | 说明 | 优先级 |
|---|---|---|---|
| BR-R-01 | 抽检建议 | 给出候选题包、抽样依据、样本量 | P1 |
| BR-R-02 | 返工建议 | 问题范围、返工对象、影响面 | P1 |
| BR-R-03 | 重新分配建议 | 结合负载、技能、历史质量 | P2 |
| BR-R-04 | 改善建议 | 问题、依据、原因、措施、待验证项 | P1 |

建议只生成，不执行。每条建议必须包含：发现了什么、数据依据、为什么是问题、建议措施、哪些结论需人工验证。

### 5.5 智能报告

| 编号 | 能力 | 说明 | 优先级 |
|---|---|---|---|
| BR-P-01 | 每日运营报告 | 指标、异常、原因、建议、口径 | P1 |
| BR-P-02 | 每周运营报告 | 趋势、对比、重点问题 | P1 |
| BR-P-03 | 项目进度报告 | 任务/题包进度与风险 | P1 |
| BR-P-04 | 人员/工作组效率报告 | 多维指标与样本说明 | P2 |
| BR-P-05 | 异常风险报告 | 异常清单与证据链 | P2 |
| BR-P-06 | 报告导出 | Markdown / PDF 或表格 | P2 |

报告结构必须包含：标题、统计周期、核心指标、图表、异常、原因分析、建议、数据来源与统计口径、局限性。

## 8. 典型业务场景

| 编号 | 用户表达 | 期望行为 |
|---|---|---|
| S-01 | “列出我能访问的语音标注项目” | 只返回有权限项目，标注数据时间 |
| S-02 | “项目 A 最近一天的任务情况” | 正确解析时间范围，返回任务与进度 |
| S-03 | “找出项目 A 还没完成的题包” | 正确理解“未完成”，分页读全 |
| S-04 | “题包 B 的承接人是谁？下面有多少题目？” | 多次工具调用并汇总 |
| S-05 | “最近一周各工作组效率，找出较低的和可能原因” | 多步查询 + 确定性统计 + 区分事实与假设 |
| S-06 | “这些异常有什么规范依据？” | 检索规范并给出条款、版本、引用 |
| S-07 | “给出返工建议，不要执行” | 只输出建议与影响面，不产生写操作 |
| S-08 | “当前数据完整吗？有没有没读完的分页？” | 明确返回 `partial` 与缺失说明 |
| S-09 | “这个结论哪些是事实，哪些是推测？” | 按四段式拆分回答 |
| S-10 | “我为什么看不了项目 C？” | 返回权限不足原因，不泄露数据 |

### 8.1 结论表达规范

所有诊断与建议必须区分：

- **facts**：平台数据或确定性程序支持的事实；
- **guideline_evidence**：规范原文、版本、条款；
- **hypotheses**：模型提出的原因假设；
- **missing_information**：当前证据无法确定的部分。

没有证据时必须写“当前知识库/数据未提供足够依据”，不得补写规则或编造数字。

## 9. 业务规则

1. 业务事实只以 Go 平台当前返回为准。
2. 统计由程序计算，LLM 不负责精确计数与比率。
3. 规范结论必须有版本和条款引用。
4. 人员评价必须展示样本量、时间范围、指标口径、对比基线和不确定性。
5. 产量高不等于质量高；样本少时不做确定性排名。
6. 异常不等于因果关系，假设必须标注为假设。
7. 建议只提出，不执行。
8. 任何写操作在 V1.0 之前不开放。
9. 工具返回不完整时必须显式标记，不得静默截断。
10. 权限不足时拒绝并记录，不返回部分敏感数据。
