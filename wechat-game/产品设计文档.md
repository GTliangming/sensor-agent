# 《一屋百年》游戏数据结构设计方案

- 文档版本：v1.2
- **项目名称：** 一屋百年
- **文档类型：** 游戏数据结构与配置规范
- **目标引擎：** Cocos Creator 3.8.8
- **开发语言：** TypeScript
- **配置格式：** JSON
- **当前开发范围：** 第一章前 10 关
- **文档状态：** 核心规则已确认，数据结构待 Schema 实现验证

# 一、文档目的

本文档用于定义《一屋百年》的统一游戏数据结构，为后续游戏开发、关卡制作、物件资产管理、配置校验和关卡编辑工具提供基础规范。

核心目标：

1. 建立统一的物件数据结构，避免每个关卡重复定义物件。
2. 建立统一的关卡数据结构，让关卡内容主要通过 JSON 配置。
3. 建立统一的章节和场景配置结构。
4. 支持物件多种外观变体，例如不同颜色、款式。
5. 支持物件层叠、遮挡和点击顺序。
6. 支持顶部目标格、底部归位格及广告模拟。
7. 支持手动布局和锚点辅助。
8. 支持程序自动检查配置错误和关卡可完成性。
9. 为未来扩展更多章节、关卡和特殊机制预留空间。

**核心原则：**

物件定义一次，关卡实例引用；玩法规则由程序实现，关卡内容由 JSON 配置；普通关卡不应该因为物件数量、位置或目标变化而修改游戏核心代码。

# 二、已确认的核心决策

以下 8 项是目前已经确定的产品规则，后续设计和开发必须遵守。

| 编号 | 决策项       | 最终选择               | 规则说明                             |
| ---- | ------------ | ---------------------- | ------------------------------------ |
| D01  | 正确物件拾取 | A：匹配后立即清除      | 正确物件不进入底部归位格             |
| D02  | 目标计数     | A：按品类计数          | 不同颜色、外观变体计入同一个物件目标 |
| D03  | 错误物件     | A：占用归位格          | 点击错误物件后进入底部归位格         |
| D04  | 归位格满     | C：暂停选择救场或重开  | 归位格满后暂停游戏，等待玩家选择     |
| D05  | 遮挡关系     | C：手动配置 + 程序检查 | 关卡设计者手动配置，程序负责检查     |
| D06  | 物件布局     | C：手动摆放 + 锚点辅助 | 人工控制最终位置，程序提供布局辅助   |
| D07  | 广告         | A：第一版模拟          | 第一版不接入真实广告 SDK             |
| D08  | 坐标         | A：设计分辨率像素坐标  | 关卡物件使用统一设计分辨率坐标       |

## 2.1 正确物件拾取规则

玩家点击正确物件后：

1. 检查物件是否可点击。
2. 检查物件是否属于当前目标。
3. 锁定当前物件，防止重复点击。
4. 播放拾取动画。
5. 增加对应目标的收集数量。
6. 从游戏场景中清除该物件。
7. 更新遮挡关系。
8. 检查目标是否全部完成。

正确物件不占用底部归位格。

## 2.2 目标计数规则

按照物件 ID 计数，不按照外观变体计数。

例如：

```
{
  "id": "headphones",
  "name": "耳机",
  "variants": [
    {
      "id": "black",
      "image": "items/headphones_black.png"
    },
    {
      "id": "white",
      "image": "items/headphones_white.png"
    },
    {
      "id": "blue",
      "image": "items/headphones_blue.png"
    }
  ]
}
```

如果当前关卡要求收集 3 个耳机：

- 黑色耳机可以计数。
- 白色耳机可以计数。
- 蓝色耳机可以计数。
- 三种颜色合计收集 3 个即可完成目标。

`variantId` 只决定物件外观，不影响目标匹配。

## 2.3 错误物件规则

玩家点击不属于当前目标的物件：

- 物件进入底部归位格。
- 归位格占用一个位置。
- 不增加任何目标进度。
- 该物件不再出现在原场景中。
- 归位格满后触发暂停和救场选择。

## 2.4 归位格满规则

归位格没有空位时：

- 暂停游戏交互。
- 弹出归位格满的处理界面。
- 玩家可以选择救场或重新开始。

救场的具体效果尚未最终确定，第一版先通过模拟按钮验证流程。

## 2.5 遮挡规则

采用手动配置与程序检查相结合的方式。

关卡设计者明确指定物件之间的遮挡关系，程序检查：

- 遮挡引用是否有效。
- 是否存在循环依赖。
- 是否存在无法解除的遮挡。
- 移除遮挡物后，被遮挡物能否正确解锁。

## 2.6 布局规则

采用手动摆放和锚点辅助：

- 关卡设计者决定物件最终位置。
- 锚点辅助吸附、对齐和排列。
- 程序检查画布越界、异常重叠和点击区域。
- 后续可以开发可视化关卡编辑工具。

## 2.7 广告规则

第一版不接入真实广告 SDK。

使用模拟广告服务验证广告入口、广告成功和失败等流程。

## 2.8 坐标规则

关卡物件使用设计分辨率像素坐标。

第一版建议统一使用：

- 设计宽度：1080
- 设计高度：1920

具体坐标原点、Cocos 节点坐标转换和不同屏幕适配规则，需要在技术实现前进一步确认。

# 三、整体数据结构架构

整个配置系统分为四类核心数据：

1. Item：物件定义。
2. Chapter：章节配置。
3. Scene：场景配置。
4. Level：关卡配置。

它们之间的关系：

```
Chapter（章节）
    │
    ├── Scene（场景）
    │
    └── Level（关卡）
           │
           ├── Item（物件定义）
           │      └── ItemVariant（物件外观变体）
           │
           ├── ItemInstance（关卡物件实例）
           │
           ├── Objective（目标配置）
           │
           ├── GridConfig（格子配置）
           │
           ├── MechanicConfig（机制配置）
           │
           └── HintConfig（提示配置）
```

数据关系说明：

- Item 定义一种物件。
- ItemVariant 定义物件的不同外观。
- ItemInstance 表示某个物件在具体关卡中的一个实例。
- Objective 定义玩家需要收集哪些物件及其数量。
- Scene 定义关卡使用的背景场景。
- Chapter 管理章节信息和关卡列表。
- Level 将以上配置组合成一关完整游戏。

# 五、Item：物件数据结构

## 5.1 设计目的

物件定义与关卡实例分离。

例如，耳机只需要在物件数据库中定义一次，后续任何关卡都可以引用它。

同一个物件可以有多个外观变体。

## 5.2 TypeScript 接口

```
interface Item {
  id: string;

  name: string;

  category: string;

  description?: string;

  size: {
    width: number;
    height: number;
  };

  variants: ItemVariant[];

  defaultVariantId: string;

  allowedZones: string[];

  hitArea?: {
    x: number;
    y: number;
    width: number;
    height: number;
  };

  tags: string[];
}

interface ItemVariant {
  id: string;

  image: string;

  displayName?: string;
}
```

## 5.3 字段说明

| 字段             | 类型     | 必填 | 说明                 |
| ---------------- | -------- | ---- | -------------------- |
| id               | string   | 是   | 全局唯一物件 ID      |
| name             | string   | 是   | 物件名称             |
| category         | string   | 是   | 物件所属分类         |
| description      | string   | 否   | 物件描述             |
| size.width       | number   | 是   | 物件设计宽度         |
| size.height      | number   | 是   | 物件设计高度         |
| variants         | array    | 是   | 外观变体列表         |
| defaultVariantId | string   | 是   | 默认变体 ID          |
| allowedZones     | string[] | 是   | 允许出现的场景区域   |
| hitArea          | object   | 否   | 自定义点击区域       |
| tags             | string[] | 是   | 搜索、筛选和扩展标签 |

## 5.4 JSON 示例

```
{
  "id": "headphones",
  "name": "耳机",
  "category": "electronics",
  "description": "日常使用的耳机",
  "size": {
    "width": 120,
    "height": 100
  },
  "variants": [
    {
      "id": "black",
      "image": "items/headphones_black.png",
      "displayName": "黑色耳机"
    },
    {
      "id": "white",
      "image": "items/headphones_white.png",
      "displayName": "白色耳机"
    }
  ],
  "defaultVariantId": "black",
  "allowedZones": [
    "desktop",
    "bedside",
    "sofa"
  ],
  "hitArea": {
    "x": 0,
    "y": 0,
    "width": 120,
    "height": 100
  },
  "tags": [
    "电子产品",
    "生活用品"
  ]
}
```

注意：

- `id` 全局唯一。
- `variant.id` 在同一个物件内部唯一。
- `defaultVariantId` 必须指向当前物件中存在的变体。
- `image` 必须指向真实存在的资源。
- 物件定义不包含关卡位置和遮挡关系。

# 六、Chapter：章节数据结构

## 6.1 设计目的

章节负责组织关卡，并提供章节展示信息。

例如：

第一章：出租屋的凌晨。

后续章节可以是其他年代的生活场景。

## 6.2 TypeScript 接口

```
interface Chapter {
  id: string;

  chapterNumber: number;

  name: string;

  description: string;

  coverImage: string;

  sceneId: string;

  levelIds: string[];

  unlockCondition: {
    type: "none" | "previous_chapter_completed";
    requiredChapterId?: string;
  };
}
```

## 6.3 字段说明

| 字段            | 类型     | 必填 | 说明           |
| --------------- | -------- | ---- | -------------- |
| id              | string   | 是   | 章节唯一 ID    |
| chapterNumber   | number   | 是   | 章节序号       |
| name            | string   | 是   | 章节名称       |
| description     | string   | 是   | 章节描述       |
| coverImage      | string   | 是   | 章节封面       |
| sceneId         | string   | 是   | 默认场景 ID    |
| levelIds        | string[] | 是   | 章节包含的关卡 |
| unlockCondition | object   | 是   | 章节解锁条件   |

## 6.4 JSON 示例

```
{
  "id": "chapter_01",
  "chapterNumber": 1,
  "name": "出租屋的凌晨",
  "description": "从一间杂乱的出租屋开始，整理生活中的琐碎物件。",
  "coverImage": "scenes/chapter_01_cover.png",
  "sceneId": "scene_rental_room",
  "levelIds": [
    "level_001",
    "level_002",
    "level_003",
    "level_004",
    "level_005",
    "level_006",
    "level_007",
    "level_008",
    "level_009",
    "level_010"
  ],
  "unlockCondition": {
    "type": "none"
  }
}
```

说明：

第一章当前先开发 10 关，后续增加关卡只需要扩展 `levelIds` 和对应关卡配置。

# 七、Scene：场景数据结构

## 7.1 设计目的

场景定义关卡使用的背景和场景基础信息。

一个场景可以被多个关卡复用。

## 7.2 TypeScript 接口

```
interface Scene {
  id: string;

  name: string;

  background: string;

  designResolution: {
    width: number;
    height: number;
  };

  zones: SceneZone[];

  anchors?: SceneAnchor[];
}

interface SceneZone {
  id: string;

  name: string;

  bounds?: {
    x: number;
    y: number;
    width: number;
    height: number;
  };
}

interface SceneAnchor {
  id: string;

  name: string;

  position: {
    x: number;
    y: number;
  };

  type: string;
}
```

## 7.3 字段说明

| 字段             | 类型   | 必填 | 说明           |
| ---------------- | ------ | ---- | -------------- |
| id               | string | 是   | 场景唯一 ID    |
| name             | string | 是   | 场景名称       |
| background       | string | 是   | 背景图片资源   |
| designResolution | object | 是   | 场景设计分辨率 |
| zones            | array  | 是   | 场景区域       |
| anchors          | array  | 否   | 布局辅助锚点   |

## 7.4 JSON 示例

```
{
  "id": "scene_rental_room",
  "name": "出租屋卧室",
  "background": "scenes/rental_room_bg.png",
  "designResolution": {
    "width": 1080,
    "height": 1920
  },
  "zones": [
    {
      "id": "desktop",
      "name": "桌面"
    },
    {
      "id": "bedside",
      "name": "床头柜"
    },
    {
      "id": "sofa",
      "name": "沙发"
    }
  ],
  "anchors": [
    {
      "id": "desktop_center",
      "name": "桌面中心",
      "position": {
        "x": 540,
        "y": 1000
      },
      "type": "center"
    }
  ]
}
```

说明：

- `zones` 用于限制物件允许出现的位置区域。
- `anchors` 用于辅助关卡布局。
- 锚点不负责自动决定所有物件的位置。
- 物件的最终坐标仍然由关卡配置决定。

# 八、Level：关卡数据结构

## 8.1 设计目的

Level 是整个数据系统的核心。

每一关通过 JSON 定义：

- 使用哪个场景。
- 玩家需要找什么物件。
- 场景中有哪些物件。
- 每个物件的位置。
- 物件之间的遮挡关系。
- 顶部找寻格数量。
- 底部归位格容量。
- 当前关卡使用的机制。
- 提示和通关规则。

## 8.2 TypeScript 接口

```
interface Level {
  id: string;

  chapterId: string;

  levelNumber: number;

  name: string;

  sceneId: string;

  difficulty: number;

  designResolution: {
    width: number;
    height: number;
  };

  objectives: Objective[];

  itemInstances: ItemInstance[];

  gridConfig: GridConfig;

  mechanicConfig: MechanicConfig;

  hintConfig: HintConfig;

  completionConfig: CompletionConfig;
}
```

## 8.3 Objective：目标配置

```
interface Objective {
  itemId: string;

  requiredCount: number;

  displayVariant?: string;
}
```

字段说明：

| 字段           | 类型   | 必填 | 说明                 |
| -------------- | ------ | ---- | -------------------- |
| itemId         | string | 是   | 目标物件 ID          |
| requiredCount  | number | 是   | 需要收集的数量       |
| displayVariant | string | 否   | 顶部目标栏显示的变体 |

注意：

- `requiredCount` 必须大于 0。
- 同一个关卡中，同一个 `itemId` 原则上只配置一条目标。
- `displayVariant` 只控制显示，不控制匹配。
- 目标匹配通过 `itemId` 完成。

## 8.4 ItemInstance：关卡物件实例

```
interface ItemInstance {
  id: string;

  itemId: string;

  variantId: string;

  position: {
    x: number;
    y: number;
  };

  rotation: number;

  scale: number;

  layer: number;

  zone: string;

  blocking: string[];
}
```

字段说明：

| 字段      | 类型     | 必填 | 说明                    |
| --------- | -------- | ---- | ----------------------- |
| id        | string   | 是   | 当前关卡内唯一实例 ID   |
| itemId    | string   | 是   | 引用物件定义            |
| variantId | string   | 是   | 引用物件外观变体        |
| position  | object   | 是   | 设计分辨率坐标          |
| rotation  | number   | 是   | 旋转角度                |
| scale     | number   | 是   | 缩放比例                |
| layer     | number   | 是   | 显示层级                |
| zone      | string   | 是   | 所属场景区域            |
| blocking  | string[] | 是   | 当前物件的遮挡者实例 ID |

重要约定：

`blocking` 表示遮挡当前物件的其他实例 ID。

例如：

```
{
  "id": "instance_headphones_001",
  "itemId": "headphones",
  "variantId": "black",
  "position": {
    "x": 520,
    "y": 900
  },
  "rotation": 0,
  "scale": 1,
  "layer": 1,
  "zone": "desktop",
  "blocking": [
    "instance_book_001"
  ]
}
```

含义：

耳机被书本遮挡。

只有书本被移除后，耳机才可以点击。

遮挡关系必须通过实例 ID 引用，不能通过物件 ID 引用，因为同一种物件可能在同一关卡中出现多次。

# 九、GridConfig：格子配置

## 9.1 设计目的

游戏中有两个独立的格子区域：

1. 顶部目标物件区，也叫找寻格。
2. 底部错误物件区，也叫归位格。

两者必须独立配置和管理。

## 9.2 TypeScript 接口

```
interface GridConfig {
  targetSlots: TargetSlotsConfig;

  collectionSlots: CollectionSlotsConfig;

  adConfig: GridAdConfig;
}

interface TargetSlotsConfig {
  baseCount: number;

  maxCount: number;
}

interface CollectionSlotsConfig {
  capacity: number;
}

interface GridAdConfig {
  enabled: boolean;

  simulated: boolean;

  unlockableTargetSlots: number[];
}
```

## 9.3 字段说明

| 字段                           | 类型     | 说明                           |
| ------------------------------ | -------- | ------------------------------ |
| targetSlots.baseCount          | number   | 初始找寻格数量                 |
| targetSlots.maxCount           | number   | 找寻格最大数量                 |
| collectionSlots.capacity       | number   | 归位格容量                     |
| adConfig.enabled               | boolean  | 是否启用广告流程               |
| adConfig.simulated             | boolean  | 是否使用模拟广告               |
| adConfig.unlockableTargetSlots | number[] | 可以通过广告模拟解锁的槽位数量 |

## 9.4 JSON 示例

```
{
  "targetSlots": {
    "baseCount": 2,
    "maxCount": 6
  },
  "collectionSlots": {
    "capacity": 3
  },
  "adConfig": {
    "enabled": true,
    "simulated": true,
    "unlockableTargetSlots": [
      3,
      4,
      5,
      6
    ]
  }
}
```

注意：

找寻格数量和归位格容量不是一回事。

顶部找寻格用于展示目标。

底部归位格用于存放错误物件。

# 十、MechanicConfig：特殊机制配置

## 10.1 设计目的

特殊机制统一放入 `mechanicConfig`。

普通关卡不需要每次增加新机制时修改 Level 的顶层结构。

第一版先使用一个可扩展的配置结构。

## 10.2 TypeScript 接口

```
interface MechanicConfig {
  enabled: boolean;

  mechanics: Mechanic[];
}

interface Mechanic {
  type: string;

  enabled: boolean;

  params?: Record<string, unknown>;
}
```

## 10.3 JSON 示例

```
{
  "enabled": true,
  "mechanics": [
    {
      "type": "layered_objects",
      "enabled": true,
      "params": {
        "allowMultiLayer": true
      }
    }
  ]
}
```

后续可以扩展：

- 限时机制。
- 特殊遮挡机制。
- 漂浮物件。
- 伪装物件。
- 特殊点击机制。
- 特殊关卡事件。

注意：

配置结构可以扩展，不代表所有机制都可以只通过 JSON 实现。

当增加新的玩法机制时，仍然可能需要编写对应的 TypeScript 逻辑。

# 十四、运行时数据结构

静态 JSON 配置和运行时状态必须分离。

JSON 负责描述关卡初始状态。

不能直接修改静态关卡配置来保存玩家操作状态。

## 14.1 目标进度


# 十五、核心游戏逻辑规则

## 15.1 点击处理流程

```
玩家点击物件
      │
      ▼
检查关卡是否处于 playing 状态
      │
      ├── 否：不处理
      │
      ▼
检查物件是否存在
      │
      ▼
检查物件是否可以点击
      │
      ├── 否：不处理
      │
      ▼
根据 itemId 判断是否属于目标
      │
      ├── 是正确物件
      │       │
      │       ▼
      │    状态变为 pending_pickup
      │       │
      │       ▼
      │    结算目标进度
      │       │
      │       ▼
      │    播放拾取动画
      │       │
      │       ▼
      │    状态变为 removed
      │       │
      │       ▼
      │    更新遮挡关系
      │       │
      │       ▼
      │    检查是否通关
      │
      └── 是错误物件
              │
              ▼
           检查归位格
              │
              ├── 有空位
              │     │
              │     ▼
              │   进入归位格
              │
              └── 没有空位
                    │
                    ▼
                 暂停游戏
                    │
                    ▼
                 弹出救场/重开界面
```

## 15.2 正确物件处理

正确物件匹配成功后：

1. 立即锁定物件。
2. 立即结算目标进度，避免动画回调重复计数。
3. 播放飞入目标区域的动画。
4. 动画结束后移除场景节点。
5. 更新遮挡状态。
6. 检查是否满足通关条件。

注意：

不能依赖动画结束回调来判断是否已经完成计数。

必须保证一个实例最多结算一次。

## 15.3 错误物件处理

错误物件：

1. 检查归位格容量。
2. 找到一个空位。
3. 将物件状态设置为 `in_collection`。
4. 将物件从原场景位置移除。
5. 播放移动到归位格的动画。
6. 更新归位格状态。

如果归位格没有空位：

- 不允许继续收集错误物件。
- 暂停玩家交互。
- 进入救场或重开流程。

## 15.4 遮挡更新

当一个物件被移除：

- 找到所有将它记录在 `blocking` 中的其他物件。
- 从这些物件的 `blocking` 数组中删除已移除实例 ID。
- 重新计算这些物件是否可点击。

例如：

原始状态：

```
{
  "id": "instance_A",
  "blocking": [
    "instance_B",
    "instance_C"
  ]
}
```

移除 `instance_B` 后：

```
{
  "id": "instance_A",
  "blocking": [
    "instance_C"
  ]
}
```

当 `blocking` 为空时，说明没有其他物件遮挡它。

## 15.5 通关判断

通关条件：

```
function isLevelCompleted(
  objectives: ObjectiveProgress[]
): boolean {
  return objectives.every(
    objective =>
      objective.collectedCount >= objective.requiredCount
  );
}
```

所有目标完成后：

- 停止游戏交互。
- 播放通关动画。
- 进入通关界面。
- 根据关卡配置进入下一关。

# 十七、JSON Schema 设计要求

JSON Schema 用于检查 JSON 文件是否符合数据结构定义。

第一版需要建立四份 Schema：

```
schema/
├── item.schema.json
├── level.schema.json
├── chapter.schema.json
└── scene.schema.json
```

## 17.1 Item Schema

必须检查：

- `id` 是否存在。
- `name` 是否存在。
- `category` 是否存在。
- `size.width` 是否大于 0。
- `size.height` 是否大于 0。
- `variants` 是否为非空数组。
- 变体 ID 是否重复。
- `defaultVariantId` 是否存在于 variants。
- `allowedZones` 是否为数组。
- `tags` 是否为数组。

## 17.2 Level Schema

必须检查：

- 关卡基础信息。
- 设计分辨率。
- objectives。
- itemInstances。
- gridConfig。
- mechanicConfig。
- hintConfig。
- completionConfig。

同时检查：

- 数量是否为合理正整数。
- 物件位置字段是否完整。
- rotation 是否为数字。
- scale 是否大于 0。
- blocking 是否为字符串数组。
- 实例 ID 是否重复。

## 17.3 Chapter Schema

必须检查：

- 章节 ID。
- 章节序号。
- 章节名称。
- 场景 ID。
- 关卡 ID 列表。
- 解锁条件。

## 17.4 Scene Schema

必须检查：

- 场景 ID。
- 背景资源。
- 设计分辨率。
- zones。
- anchors。

## 17.5 Schema 与业务校验的区别

必须区分两种检查：

**第一种：JSON Schema 格式校验**

检查数据结构是否合法。

例如：

- 缺少字段。
- 字段类型错误。
- 数量为负数。
- 数组格式错误。

**第二种：游戏业务校验**

检查数据之间的逻辑是否正确。

例如：

- itemId 是否引用了真实物件。
- variantId 是否属于对应物件。
- 目标数量是否超过场景中的物件数量。
- blocking 是否引用了不存在的实例。
- 是否存在遮挡循环。
- 关卡是否存在合法的完成路径。
- 关卡物件是否超出设计画布。

JSON Schema 不能代替业务校验器。

# 十八、关卡可完成性检查

这是第一版必须重点实现的功能。

不能只检查目标物件数量是否足够，还必须考虑遮挡关系。

例如：

目标需要收集 3 个耳机。

场景中确实存在 3 个耳机，但其中一个耳机被永久无法移除的物件遮挡。

这种关卡仍然不可完成。

## 18.1 检查内容

1. 目标物件是否存在。
2. 目标物件数量是否足够。
3. 遮挡关系是否引用有效实例。
4. 是否存在循环遮挡。
5. 是否存在无法解除的遮挡。
6. 是否存在目标物件永远无法点击的情况。
7. 是否存在其他导致关卡无法完成的逻辑问题。

## 18.2 推荐检查方式

使用模拟游戏过程的方式检查：

1. 复制一份关卡实例状态。
2. 找出当前所有可点击物件。
3. 模拟收集正确目标物件。
4. 模拟移除这些物件。
5. 更新遮挡关系。
6. 继续寻找可点击目标。
7. 直到所有目标完成或没有可行操作。

需要注意：

错误物件会进入归位格，可能导致容量不足。因此完整可完成性检查还需要考虑归位格容量和玩家操作策略。

第一版可以先实现基础遮挡可达性检查，再逐步扩展为完整的关卡求解检查。

# 二十三、后续扩展原则

未来增加普通关卡时，原则上只需要：

1. 准备场景资源。
2. 准备物件资源。
3. 在物件数据库中登记新物件。
4. 编写关卡 JSON。
5. 通过配置校验。
6. 在游戏中测试。

不应该为了增加普通关卡而修改核心游戏逻辑。

但是，如果未来增加全新的玩法机制，例如限时、漂浮物件、特殊交互等，仍然需要增加对应的 TypeScript 实现。

数据配置负责描述机制参数，程序负责实现机制行为。

# 二十七、最终设计原则

《一屋百年》的数据系统遵循以下原则：

**1. 物件定义与关卡实例分离**

物件只定义一次，关卡通过 ID 引用。

**2. 外观变体与目标计数分离**

不同颜色、款式的同类物件可以计入同一个目标。

**3. 静态配置与运行时状态分离**

JSON 保存初始关卡数据，TypeScript 管理实时游戏状态。

**4. 玩法逻辑与关卡内容分离**

玩法规则由程序实现，普通关卡内容通过 JSON 配置。

**5. 手动设计与自动检查结合**

关卡设计者控制布局和遮挡，程序负责发现配置问题。

**6. 配置校验与关卡可完成性检查分离**

JSON 格式正确不代表关卡一定可以完成。

**7. 预留扩展能力，但不提前过度设计**

第一版优先把核心玩法、数据结构和 10 关跑通。

**最终目标：**

建立一套稳定、可扩展、可校验的关卡生产体系。

第一章 10 关跑通后，后续普通关卡尽可能通过物件资源和 JSON 配置完成，而不是反复修改游戏核心代码。
