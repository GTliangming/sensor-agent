# 分层深入与升级路线

> 第一版把 RAG 链路跑通后，这篇文档告诉你**每一层该从哪里入手深入原理、怎么升级到生产级**。
> 用法：不要一次全看，挑一层，先理解"第一版怎么做的"，再看"原理要点"，然后做"升级动作"。

## 建议的深入顺序（先吃哪层）

对照目标岗位的价值，推荐这个顺序：

1. **分块（Chunking）** —— 投入小、对效果影响最大，性价比最高
2. **向量检索 + 重排（Retrieval + Rerank）** —— RAG 质量的核心
3. **Embedding** —— 理解向量化本质，决定检索上限
4. **Agent 编排（规划 / 工具 / 记忆）** —— 从"问答"升级成"会干活"，岗位最看重
5. **文档解析** —— 工业 PDF 表格/图是硬骨头，啃下来是亮点
6. **Prompt Engineering** —— 贯穿全程，边做边练
7. **部署** —— 把"真实可访问"这条硬门槛坐实
8. **大模型微调** —— 最后，投入大、门槛高，有余力再碰

---

## 层 1 · 分块（Chunking）

- **第一版怎么做的**：`RecursiveCharacterTextSplitter`，固定 chunk_size≈500、overlap≈50。
- **原理要点**：分块决定"检索的最小单位"。块太大→一个块混多个主题，检索不精准、塞进 Prompt 太长；
  块太小→语义被切碎，丢上下文。重叠（overlap）是为了避免答案正好被切在边界。
- **从哪入手深入**：
  - 对比不同 chunk_size / overlap 对同一批问题的检索命中率
  - 了解 **按语义分块**（semantic chunking）、**按文档结构分块**（按标题/章节）
  - 工业 datasheet 适合"按参数表/小节"结构化分块，而不是无脑按字数切
- **升级动作**：从固定长度 → 结构感知分块；给每个块加更丰富的元数据（章节、型号、参数类别）。
- **关键词**：recursive splitter、semantic chunking、parent-child / small-to-big retrieval。

## 层 2 · 向量检索 + 重排（Retrieval + Rerank）

- **第一版怎么做的**：问题向量在 Milvus 做相似度检索，取 top-k 直接用。
- **原理要点**：向量检索召回的是"语义相近"的片段，但"相近≠最该用"。**重排（rerank）**用一个更强的
  模型对召回的 k 个片段重新打分排序，把最相关的排前面，显著提升答案质量。
- **从哪入手深入**：
  - 先把 k 调大（如 20）召回，再用 rerank 模型（如 bge-reranker，SiliconFlow 也有）重排取前 4
  - 了解 **向量检索 + 关键词检索（BM25）混合**（hybrid search），工业术语/型号这类精确匹配很需要
  - 理解相似度度量（cosine / inner product）、Milvus 索引类型（IVF / HNSW）与召回率的关系
- **升级动作**：加入 rerank；加入 hybrid 检索；给检索加过滤（按型号/文档类型用元数据过滤）。
- **关键词**：rerank、cross-encoder、hybrid search、BM25、HNSW、MMR。

## 层 3 · Embedding（向量化）

- **第一版怎么做的**：bge-m3(SiliconFlow)，1024 维，文档和问题用同一个模型。
- **原理要点**：embedding 把文本映射到向量空间，语义相近的文本距离近。检索的上限由 embedding 质量决定——
  模型"听不懂"工业术语，再好的检索也白搭。
- **从哪入手深入**：
  - 理解为什么文档和问题必须用**同一个 embedding 模型**、维度为何必须一致
  - 对比不同 embedding 模型在你领域语料上的检索效果（bge-m3 / bge-large / 其他）
  - 了解 embedding 的本地部署（如用 Ollama / sentence-transformers 跑 bge，摆脱 API 依赖）
- **升级动作**：从 API embedding → 本地部署 embedding；在你的工业语料上评测/微调 embedding。
- **关键词**：sentence embedding、bi-encoder、向量维度、归一化、领域适配。

## 层 4 · Agent 编排（规划 / 工具调用 / 记忆）—— 重点

- **第一版怎么做的**：没有 Agent，只是"检索→作答"的单轮 RAG。
- **原理要点**：Agent = LLM 做"大脑"决定下一步做什么，可以调用工具、分多步完成任务、记住上下文。
  这是从"问答机器"到"会干活的助手"的质变，也是岗位最看重的能力。
- **从哪入手深入（用 LangGraph）**：
  - **工具调用**：给 Agent 加工具，比如"查某型号传感器参数""按采样定理算最小采样率""单位换算"
  - **任务规划**：复杂问题拆步（先检索手册→再调用计算工具→再汇总），用 LangGraph 画状态图
  - **记忆管理**：用 Redis 存会话历史，支持多轮对话；区分短期记忆（本轮对话）和长期记忆
- **升级动作**：把单轮 RAG 包成一个"检索工具" → 搭 LangGraph 图 → 加多工具 → 加 Redis 记忆 →
  前端把"思考过程 / 调了哪些工具"可视化出来（你的前端优势在这里能放大）。
- **关键词**：ReAct、tool calling、function calling、LangGraph、state graph、short/long-term memory。

## 层 5 · 文档解析（工业 PDF 的硬骨头）

- **第一版怎么做的**：多格式分别用解析库（PDF/Word/Excel/TXT/MD）抽成纯文本入库；**预览走原始文件渲染**，与抽取分离。表格结构在抽取时大概率丢失。
- **原理要点**：注意区分两件事——**预览**是前端渲染原文件（排版完整，用户看着舒服），**RAG 抽取**是把内容降维成纯文本（给机器检索）。
  工业 datasheet 大量信息在**参数表格、引脚图、曲线图**里，纯文本抽取会丢掉表格的行列关系，
  导致"某型号某参数是多少"这类问题答不准。
- **从哪入手深入**：
  - 了解专门的 PDF 解析方案（表格抽取、版面分析 layout analysis）
  - 把表格转成结构化文本（如 Markdown 表格）再分块，保留行列语义
  - 扫描型 PDF / 图片 → 引入 OCR 才能纳入检索
  - 多模态方向：图/曲线用视觉模型理解（进阶）
- **升级动作**：引入更强的解析器处理表格；对参数表单独建结构化索引；补 OCR 覆盖扫描件。
- **关键词**：PDF layout parsing、table extraction、OCR、多模态文档理解。

## 层 6 · Prompt Engineering

- **第一版怎么做的**：一个简单的"依据资料作答、标注出处、不知道就说不知道"的系统提示。
- **原理要点**：Prompt 决定模型如何使用检索到的资料、如何控制幻觉、如何输出结构。RAG 场景里，
  "忠于资料"的约束和引用格式是重点。
- **从哪入手深入**：
  - 系统学习 Prompt 结构（角色、指令、约束、few-shot 示例、输出格式）
  - 对比不同提示对幻觉率、引用准确性的影响；加入"先列证据再给结论"的思维引导
  - 结构化输出（要求返回 JSON，便于前端渲染引用）
- **升级动作**：Prompt 模板化、版本化；针对工业问答设计 few-shot；输出结构化。
- **关键词**：system prompt、few-shot、CoT、structured output、grounding、anti-hallucination。

## 层 7 · 部署（坐实"真实可访问"这条硬门槛）

- **第一版怎么做的**：只在本机 localhost 跑。
- **原理要点**：岗位明确要"真实上线、可访问"。需要把前端（静态）和后端（含 Milvus/Redis，用 Docker）
  分别部署，并处理 HTTPS、CORS、域名。
- **从哪入手深入**：
  - 前端静态产物可放 GitHub Pages；**后端 + Milvus + Redis 必须放能跑 Docker 的云服务器**
    （GitHub Pages 跑不了后端/容器/数据库）
  - 处理三个坑：HTTPS（避免 mixed content）、CORS 跨域、GH Pages 子路径（Vite base）
  - 用 docker-compose 编排后端全套，Nginx 做反代 + TLS
- **升级动作**：容器化 → 云服务器部署 → 配域名和证书 → 前端指向线上后端。
- **关键词**：docker-compose、Nginx、TLS、CORS、reverse proxy、CI/CD。

## 层 8 · 大模型微调（最后再碰）

- **第一版怎么做的**：不涉及，直接用 DeepSeek API。
- **原理要点**：微调是在特定数据上继续训练模型，让它更懂你的领域/风格。投入大、门槛高（数据、算力），
  且很多场景 RAG + 好 Prompt 已够用。岗位说"至少一个方向"，前面做扎实已达标。
- **从哪入手深入**：
  - 先搞清楚"什么时候该微调、什么时候 RAG 就够"（多数检索类需求不需要微调）
  - 从轻量微调（LoRA / QLoRA）入门，用小模型 + 少量工业问答对练手
  - 了解部署开源模型（如用 vLLM / Ollama 托管）
- **升级动作**：造领域问答数据集 → LoRA 微调一个开源小模型 → 评测对比 → 本地部署。
- **关键词**：LoRA、QLoRA、SFT、instruction tuning、vLLM、Ollama、模型量化。

## 一张总览：每层的"第一版 → 目标态"

- **分块**：固定长度 → 结构感知 + 丰富元数据
- **检索**：纯向量 top-k → 大召回 + rerank + hybrid + 元数据过滤
- **Embedding**：API 调用 → 本地部署 + 领域评测
- **Agent**：单轮 RAG → LangGraph 多工具 + 规划 + Redis 记忆 + 过程可视化
- **解析**：纯文本 → 表格结构化 + 多模态
- **Prompt**：简单约束 → 模板化 + few-shot + 结构化输出
- **部署**：localhost → 前端(GH Pages) + 后端(云服务器 Docker) 真实可访问
- **微调**：不做 → LoRA 微调开源模型 + 本地部署

> 心法：**先横向跑通（第一版），再纵向深入（挑一层啃透），每深入一层都在真实项目上改出效果**。
> 这样你积累的不是"学过的知识点"，而是"做过的、能讲清楚的工程经验"——这正是岗位要的。
