# AI Video Studio：总体设计与开发计划

## 1. 项目概述

### 1.1 项目目标

构建一个可逐步扩展的 AI 视频生成工作台。用户通过网页提交参考图片、视频主题、提示词和生成参数，后端调用部署在 AutoDL.Art GPU 实例中的 ComfyUI 工作流，最终生成适合微信视频号发布的短视频。

项目采用分阶段开发方式，先跑通单个视频生成流程，再逐步完善任务管理、前端交互、Agent 工作流、文件存储、数据库切换和线上部署能力。

### 1.2 第一阶段目标

- 支持输入参考图片、正向提示词和负向提示词。
- 支持竖屏视频生成，默认画幅为 9:16。
- 视频目标时长为 10–15 秒，实际时长以工作流能力为准。
- Python 后端调用 AutoDL.Art 上的 ComfyUI 工作流。
- 使用已经部署的 MiniMax H3 图生视频能力。
- 支持任务创建、任务状态查询、失败提示和结果播放。
- 保存任务历史，服务重启后仍然可以查询历史记录。
- 支持本地 SQLite 开发。
- 通过配置切换到线上关系型数据库。
- Redis 可以启用，也可以关闭。
- 后续可以接入微信云托管、对象存储和独立任务执行服务。

### 1.3 第一阶段暂不实现

- 不在业务后端直接加载视频生成模型。
- 不要求本地电脑具备运行视频模型的 GPU 能力。
- 不一开始就引入复杂的多 Agent 架构。
- 不把所有任务状态只保存在 Python 内存中。
- 不将临时容器磁盘作为线上永久存储。
- 不在没有实际测试前假设 AutoDL 接口的所有字段和返回结构。
- 不提前引入 Kubernetes 等不必要的部署复杂度。

## 2. 技术栈

| 模块 | 技术 | 主要职责 |
|---|---|---|
| 前端 | React + Vite | 生成表单、任务列表、视频预览 |
| 后端 | Python 3.12 + FastAPI | HTTP API、参数校验、业务逻辑 |
| 数据校验 | Pydantic 2 | 请求参数、响应结构校验 |
| ORM | SQLAlchemy 2.x | 统一数据库访问 |
| 本地数据库 | SQLite | 本地开发和单机验证 |
| 线上数据库 | PostgreSQL 等 | 线上持久化数据 |
| 数据库迁移 | Alembic | 管理表结构版本 |
| 任务编排 | 首期普通 Python 服务层 | 先实现可验证的业务闭环 |
| 后续流程编排 | LangGraph | 多步骤、分支、重试和人工审核 |
| 可选队列/缓存 | Redis | 任务队列、缓存和分布式协调 |
| 视频生成 | ComfyUI + MiniMax H3 | 执行图生视频工作流 |
| GPU 环境 | AutoDL.Art | 承载视频生成模型和工作流 |
| 文件存储 | 本地目录 / 对象存储 | 保存输入图片和输出视频 |
| 部署 | 微信云托管或其他支持 Python 服务的平台 | 承载业务 API 和任务执行器 |

依赖版本应在项目初始化时选择互相兼容的稳定版本，并通过依赖锁定文件固定。不要将未验证的“最新版本”当作长期固定版本。

## 4. 核心设计原则

### 4.1 模型运行与业务服务分离

视频生成模型运行在 AutoDL.Art GPU 环境中。

业务后端只负责：

1. 接收用户请求。
2. 校验输入。
3. 创建本系统任务记录。
4. 调用 AutoDL 工作流 API。
5. 查询外部任务状态。
6. 获取并保存生成结果。
7. 向前端提供任务状态和结果地址。

这样可以独立升级业务后端，不需要每次都重新部署模型。

### 4.2 任务创建与视频生成分离

视频生成可能需要较长时间，因此创建任务接口只负责受理请求和创建任务，不应一直等待到视频生成完成。

建议流程：

```text
用户点击生成
    ↓
FastAPI 校验参数
    ↓
数据库创建任务
    ↓
接口返回 task_id
    ↓
Worker 提交外部工作流
    ↓
Worker 轮询生成状态
    ↓
保存结果
    ↓
前端查询任务并播放视频
```

### 4.3 数据库负责保存事实记录

数据库保存任务状态、输入参数、外部任务 ID、生成结果信息和错误信息。

Redis 不能替代数据库成为唯一任务记录来源。

如果 Redis 暂时关闭，系统仍然应该能够完成核心视频生成流程，只是使用更简单的单机任务执行机制。

### 4.4 外部服务统一封装

AutoDL 的请求地址、认证方式、请求参数和返回结构全部封装在独立 Provider 中。

业务服务不能到处直接拼接 AutoDL API 请求。

未来如果更换视频生成服务商，只需要增加新的 Provider，并保持内部接口尽量一致。

### 模块职责

- `api/routes`：HTTP 接口层，不承载复杂业务逻辑。
- `schemas`：请求和响应结构校验。
- `models`：数据库 ORM 模型。
- `repositories`：封装数据读写。
- `services`：任务创建、状态流转、重试等业务逻辑。
- `providers`：封装外部模型平台。
- `storage`：统一文件保存、读取和访问地址生成。
- `workers`：执行耗时任务和同步任务状态。
- `migrations`：管理数据库表结构变化。
- `frontend/src/api`：集中管理前端 API 请求。

## 6. 视频生成任务状态设计

建议使用以下状态：

| 状态 | 含义 |
|---|---|
| `pending` | 任务已创建，等待执行 |
| `submitted` | 已向外部服务提交任务 |
| `running` | 外部工作流正在运行 |
| `succeeded` | 生成成功 |
| `failed` | 生成失败 |
| `cancelled` | 任务已取消或不再继续执行 |

状态流转：

```text
pending
   |
   ▼
submitted
   |
   ▼
running
   |
   ├── succeeded
   └── failed

pending ──> failed
```

`cancelled` 只应在本系统确认取消语义后使用。如果外部 GPU 任务不支持取消，不能因为用户关闭页面就宣称模型任务已经停止。

所有状态变更必须经过统一的业务逻辑校验，不能允许旧的轮询结果覆盖更新后的终态。

## 7. Agent 与 LangGraph 的设计

### 7.1 第一阶段为什么不急着引入多 Agent

首期的生成流程比较固定：

```text
校验参数
  ↓
创建任务
  ↓
提交工作流
  ↓
轮询状态
  ↓
获取结果
```

普通 Python 服务层更容易调试，也更容易验证每个步骤。

不要为了使用 Agent 而把简单的 HTTP 调用强行包装成多个 Agent。

### 7.2 后续可扩展的 Agent

后续可按业务职责逐步拆分：

1. **需求解析模块**：把用户的自然语言需求整理成结构化视频生成参数。
2. **提示词优化模块**：优化人物、镜头、动作、环境和风格描述。
3. **工作流选择模块**：根据输入素材和生成目标选择合适的 ComfyUI 工作流。
4. **生成执行模块**：调用视频生成 Provider。
5. **质量检查模块**：检查视频是否存在、时长和画幅是否符合预期。
6. **任务恢复模块**：识别可恢复错误并安排有限重试。

早期可以把这些能力实现为普通函数或服务；当出现复杂分支、状态持久化、人工审核和中断恢复需求时，再用 LangGraph 进行编排。

## 8. 分阶段开发计划

### 阶段 0：项目初始化

工作内容：

- 建立后端目录。
- 配置 FastAPI、Pydantic、SQLAlchemy。
- 配置 SQLite。
- 建立基础配置管理。
- 实现健康检查接口。
- 建立基础日志格式。

验收标准：

- 后端可以正常启动。
- 健康检查接口返回成功。
- 数据库连接可用。
- 密钥不写入代码。

### 阶段 1：AutoDL 工作流连通

工作内容：

- 确认 AutoDL API 基础地址和 Token。
- 确认工作流 ID。
- 确认提交请求体和结果查询结构。
- 使用测试图片发起一次真实任务。
- 下载并检查输出视频。

验收标准：

- Python 能成功提交任务。
- 能获取外部任务 ID。
- 能查询外部任务结果。
- 能取得有效视频文件。

此阶段先不追求完整前端。

### 阶段 2：后端任务闭环

工作内容：

- 创建视频任务接口。
- 查询任务列表和详情。
- 任务状态持久化。
- 后台任务执行和轮询。
- 错误处理和有限重试。
- 结果存储抽象。

验收标准：

- 一次任务从创建到完成可以完整追踪。
- 服务重启后历史任务仍然存在。
- 失败任务能查看失败原因。
- 重复轮询不会重复生成结果记录。

### 阶段 3：React 前端工作台

工作内容：

- 视频生成表单。
- 参考图片上传。
- 提示词输入。
- 任务列表。
- 状态标签。
- 任务详情。
- 视频预览和播放。

验收标准：

- 用户不需要手工调用 API 就能完成视频生成。
- 页面刷新后仍能查询历史任务。
- 失败任务显示可理解的错误信息。

### 阶段 4：可靠性完善

工作内容：

- 请求超时。
- 轮询退避。
- 有限重试。
- 防止重复提交。
- 任务领取的并发保护。
- 日志关联本系统任务 ID 和外部任务 ID。
- 文件大小限制和输入校验。

验收标准：

- 外部服务暂时不可用时不会无限重试。
- 两个 Worker 不会无保护地重复执行同一任务。
- 能定位任务失败发生在哪个环节。

### 阶段 5：线上部署

工作内容：

- 配置线上数据库。
- 验证数据库迁移。
- 选择对象存储或持久化卷。
- 根据需要启用 Redis。
- 部署 API 服务。
- 部署独立 Worker。
- 配置环境变量、健康检查和日志。

验收标准：

- 实例重启后任务记录仍存在。
- 已生成视频仍然可访问。
- 后端与 GPU 工作流之间可以稳定通信。
- 不依赖开发机上的本地文件。

### 阶段 6：Agent 能力扩展

工作内容：

- 自然语言需求解析。
- 提示词生成与优化。
- 工作流路由。
- 视频结果质量检查。
- 失败恢复。
- 视业务复杂度引入 LangGraph。

验收标准：

- 每个 Agent/节点的输入输出清晰。
- 失败可以定位。
- 流程状态可以恢复。
- 业务任务记录仍由数据库负责持久化。

## 9. 环境配置原则

所有环境差异通过环境变量控制。

至少包括：

- `APP_ENV`
- `DATABASE_URL`
- `REDIS_ENABLED`
- `REDIS_URL`
- `AUTODL_BASE_URL`
- `AUTODL_API_TOKEN`
- `AUTODL_WORKFLOW_ID`
- `LOCAL_STORAGE_DIR`
- `PUBLIC_BASE_URL`

本地、测试和生产环境使用不同配置，不应通过硬编码判断环境。

## 10. 项目验收总清单

- [ ] FastAPI 后端能够启动。
- [ ] SQLite 本地开发正常。
- [ ] AutoDL 工作流真实调用成功。
- [ ] 创建任务接口快速返回。
- [ ] 任务状态可持久化。
- [ ] 视频生成成功后可以播放。
- [ ] 失败任务可查看错误摘要。
- [ ] 前端能够创建任务和查看结果。
- [ ] Redis 关闭时核心流程仍可运行。
- [ ] 线上数据库连接和迁移经过验证。
- [ ] 线上视频使用可靠存储。
- [ ] API Token 不暴露给前端。
- [ ] 服务重启后的任务恢复策略经过验证。
- [ ] Agent 扩展不会破坏已有业务接口。

## 11. 最终实施原则

先验证最小可行闭环，再扩展架构。

推荐顺序：

**真实调用 AutoDL → 后端任务管理 → 前端工作台 → 可靠性 → 线上部署 → Agent 扩展。**

这样每个阶段都有可运行、可验证的成果，避免一次性建设过多模块，却始终没有真正生成出视频。
