## 一、分析过程：我们是怎么一步步推导到这个方案的

这一节记录完整的决策链路，方便你以后回看"为什么是这样选的"，也方便面试时讲清思路。

### 1.1 从目标岗位倒推

目标岗位（企业级 AI Agent 开发）有 6 条要求，其中 3 条是硬门槛：

1. **必须有真实上线、可访问的 AI Agent 项目**（非 Demo、非课程作业、非纯调 API）
2. 熟悉主流 AI 框架（LangChain / LangGraph / LlamaIndex / Dify 等）、向量库（Milvus / pgvector / FAISS）、中间件（Redis、消息队列）
3. 在 **RAG 全链路**、**Agent 编排**、**Prompt Engineering**、**微调与部署**中至少一个方向有落地

结论：**只要做出一个"真实可访问、覆盖 RAG + Agent"的项目，并把过程写成文档，就能同时命中第 1、2、3、6 条。**

### 1.2 从个人情况倒推

- 5 年前端（React / Vue），后端会一点 Go / Java / Python（都不深），懂 MySQL / Redis
- 没有 AI Agent 项目经验 —— 这正是最大短板，也是本项目要补的核心

推导：
- 前端是强项 → 用 React 做高质量对话界面 + Agent 执行过程可视化，形成**差异化亮点**（很多后端选手做不出好界面）
- 后端够用即可，不必学深 → 选能最快出成果、且和岗位要求对齐的技术栈
- Redis 已会 → 直接用来做会话记忆 / 缓存，少学一样东西

### 1.3 技术选型的关键推导（含踩过的坑）

- **语言**：岗位点名的 AI 框架（LangChain/LangGraph/LlamaIndex）几乎全是 **Python 生态**。
  Go 这边 LangChainGo 已基本停维护、其他（如 Eino）偏小众。为对齐岗位，**后端用 Python**。
- **Web 框架**：排除 FastAPI，选 **Flask**（Python 最流行的轻量框架之一，上手快，和 LangChain 配合顺手）。
- **AI 编排**：**LangChain + LangGraph** —— 正是岗位要的主流框架，RAG 和 Agent 都有开箱组件。
- **向量库**：**Milvus** —— 直接命中岗位点名的向量库，工业界标准。
- **记忆 / 缓存**：**Redis** —— 用上已有技能，命中中间件要求。
- **对话模型**：**DeepSeek**（你已有 Key，OpenAI 兼容）。
- ⚠️ **最大的坑：DeepSeek 没有 embedding 接口**。DeepSeek 官方 API 只有对话（chat），
  没有向量化（embedding）接口。而 RAG 必须把文档和问题转成向量，所以 **embedding 必须另找服务**：
  选 **硅基流动 SiliconFlow 的 `bge-m3`**（OpenAI 兼容、有免费额度、中文效果好、1024 维）。

> 记住这条分工：**对话用 DeepSeek，向量化用 bge-m3(SiliconFlow)**。这是整个 RAG 能不能跑起来的前提。

## 二、第一版要做什么（功能目的与范围）

### 2.1 一句话目的

> 把工业传感器 / 示波器的文档喂进系统，用户用自然语言提问，系统**从文档里检索相关内容，
> 用 DeepSeek 生成答案，并给出引用出处**，前端以流式方式展示。

### 2.2 第一版包含的功能（Must have）

1. **文档管理**：在「文档管理页」上传多格式文档（**PDF / Word(docx) / Excel(xlsx) / TXT / Markdown**），
   查看已上传文档列表，并**按原始排版预览**文档内容（PDF 用 pdf.js 渲染原文件，Word/Excel 用对应渲染器）
2. **文档处理**：解析 → 分块 → 用 bge-m3 向量化 → 存入 Milvus
3. **问答检索**：用户提问 → 向量化问题 → Milvus 检索 top-k 相关片段
4. **生成作答**：把检索片段拼进 Prompt → DeepSeek 生成答案 → **带出处（命中了哪些文档/片段）**
5. **流式输出**：后端 SSE 推送，前端 React 实时逐字展示
6. **两个前端页面**（第一版明确拆成两页）：
   - **页面一 · 文档管理页**：上传文档；展示已上传文档列表（文件名、类型、大小、处理状态如"已入库/处理中"）；
     点击某篇**按原始排版预览**（PDF→pdf.js，Word→docx 渲染器，Excel→表格渲染器，TXT/MD→直接渲染）
   - **页面二 · 提问页**：输入问题，流式查看答案，并展示引用来源（命中了哪些文档/片段）
   - 两页之间用顶部导航 / 路由切换

### 2.3 第一版**不做**什么（刻意砍掉，避免陷进去）

- ❌ 复杂 Agent 编排（多步规划、工具调用）—— 放到第二阶段
- ❌ 重排（rerank）—— 放到第二阶段
- ❌ 多轮记忆 —— 第一版先做单轮问答，记忆放第二阶段
- ❌ 部署上线 —— 本阶段只在本机 `localhost` 跑通，部署以后再说
- ❌ 用户系统 / 权限 / 多租户 —— 不需要
- ❌ 大模型微调 —— 最后再碰

> 原则：**先让一条链路从头到尾跑通并能演示**，再在它上面加东西。砍功能不是偷懒，是控制复杂度。

## 三、项目架构

### 3.1 整体结构（两条链路）

系统有两条核心链路，建议分开理解：

**A. 离线 / 导入链路（Ingestion）—— 把文档变成可检索的向量**

```
文档(PDF/MD/TXT) → 解析(提取纯文本) → 分块(chunking) → 向量化(bge-m3)
                                                              ↓
                                                    存入 Milvus(向量 + 原文 + 元数据)
```

**B. 在线 / 问答链路（Query）—— 回答用户问题**

```
用户提问 → 向量化(bge-m3) → Milvus 检索 top-k 片段
                                      ↓
          拼 Prompt(问题 + 检索片段) → DeepSeek 生成 → SSE 流式 → React 展示(带出处)
```

### 3.2 组件职责

- **React 前端**：两个页面——①文档管理页（上传 / 列表 / **按原始排版预览**）②提问页（SSE 流式问答 + 引用展示）；用路由切换
  - 预览由前端渲染库负责：PDF→pdf.js(或 react-pdf)，Word(docx)→docx-preview，Excel(xlsx)→SheetJS 等
- **Flask 后端**：保存**原始文件**（供预览）+ 解析出**纯文本**（供 RAG 入库）；提供上传 / 列表 / 原始文件 / 问答接口
- **关键区分**：**预览 = 渲染原始文件（保排版）**；**RAG 入库 = 抽取纯文本（供分块向量化）**。两者是对同一文档的两条独立处理，别混在一起。
- **LangChain**：封装"文档加载 / 分块 / Embedding / 向量库 / 检索 / Prompt / LLM 调用"等组件
- **Milvus**：存储文档向量，做相似度检索
- **Redis**：第一版先做缓存（可选）；第二阶段用于会话记忆
- **DeepSeek**：对话生成（通过 OpenAI 兼容接口接入 LangChain）
- **bge-m3 (SiliconFlow)**：文本向量化

### 3.3 建议的目录结构（代码落地时用）

```
sensor-agent/
├── docs/                  # 本套文档
├── backend/               # Flask + LangChain
│   ├── app.py             # Flask 入口与路由
│   ├── ingest.py          # 导入链路：解析/分块/向量化/入库
│   ├── rag.py             # 问答链路：检索/拼Prompt/调用LLM
│   ├── config.py          # 配置(API Key、模型名、Milvus地址等)
│   └── requirements.txt
├── frontend/              # React + Vite
│   └── src/
│       ├── pages/
│       │   ├── Documents.tsx   # 页面一：文档管理（上传/列表/预览）
│       │   └── Chat.tsx        # 页面二：提问
│       ├── api/           # 调后端接口
│       └── App.tsx        # 路由（两页切换）
├── data/                  # 放你的传感器/示波器文档
└── docker-compose.yml     # 起 Milvus + Redis
```

### 3.4 后端接口清单（第一版）

- `POST /api/documents`           —— 上传文档（保存原始文件 + 触发解析/分块/向量化/入库）
- `GET  /api/documents`           —— 返回已上传文档列表（文件名、类型、大小、处理状态）
- `GET  /api/documents/{id}`      —— 返回某篇文档的元信息（类型、状态等）
- `GET  /api/documents/{id}/file` —— 返回**原始文件二进制**（前端 pdf.js/docx/xlsx 据此按排版预览）
- `POST /api/chat`（SSE）          —— 提问，流式返回答案 + 引用来源

> 预览走"原始文件"而非解析文本：后端只需把上传的原文件存起来并通过 `/file` 原样返回，
> 排版由前端渲染库还原。大文件预览时前端做分页/懒加载（pdf.js 原生支持按页渲染）。

## 四、技术栈清单（含选型理由）

- **React (Vite + TS)** —— 你的主场；SSE 流式 + Agent 过程可视化是差异化亮点
- **前端预览库** —— 按原始排版渲染：`pdf.js`(或 `react-pdf`) 看 PDF、`docx-preview` 看 Word、`SheetJS(xlsx)`(或 `x-spreadsheet`) 看 Excel；TXT/MD 直接渲染
- **后端解析库（供 RAG 抽文本）** —— `pypdf`/`pdfplumber`(PDF)、`python-docx`(Word)、`openpyxl`/`pandas`(Excel)；也可用 `unstructured` 统一处理多格式
- **Flask** —— Python 主流轻量 Web 框架；排除 FastAPI 后的首选；同步模型做 SSE 够用
- **LangChain + LangGraph** —— 岗位点名的主流 AI 框架；第一版主要用 LangChain，LangGraph 留给 Agent 阶段
- **Milvus** —— 工业界标准向量库，命中岗位要求；用 Docker 跑
- **Redis** —— 你已会；第一版做缓存，后续做记忆
- **DeepSeek** —— 已有 Key，OpenAI 兼容，接 LangChain 一行配置
- **bge-m3 (SiliconFlow)** —— embedding 模型；**因为 DeepSeek 无 embedding 接口**，必须用它；1024 维

## 五、实现步骤（按阶段，每步都有可见产出）

> 第一版只做"阶段 0 + 阶段 1"。后面的阶段见 `02-分层深入与升级路线.md`。

### 阶段 0：打通最小闭环（先确认环境没问题）

1. 建目录结构（见 3.3），初始化 `backend`（Python 虚拟环境）和 `frontend`（Vite + React）
2. 后端写一个最简接口：收到问题 → 直接调 DeepSeek → 返回答案（**先不接 RAG**）
3. 前端写一个输入框 + 发送 → 展示回复，并打通 **SSE 流式**
4. ✅ 产出：一个能和 DeepSeek 流式对话的网页（还没有文档检索）

> 阶段 0 的目的是先把"前端 ↔ Flask ↔ DeepSeek ↔ 流式"这条管子焊通，排除环境/网络/Key 问题。

### 阶段 1：接入 RAG（第一版的核心）

**先搭基础设施**

5. 写 `docker-compose.yml`，用 Docker 起 **Milvus**（和 Redis，可选）
6. 配好两个 Key：DeepSeek（对话）、SiliconFlow（embedding）

**导入链路（ingest.py）**

7. 文档解析：按格式用对应解析库（PDF/Word/Excel/TXT/MD）把内容提取成纯文本；同时**原样保存上传的原始文件**（供预览）
8. 分块：用 `RecursiveCharacterTextSplitter` 切块（先用默认参数，如 chunk_size≈500、overlap≈50）
9. 向量化：调 bge-m3 把每个块转成向量
10. 入库：把 向量 + 原文 + 元数据(来源文件/页码) 存进 Milvus
11. 把 7~10 封装成一个函数，既能被导入脚本调用，也能被 `POST /api/documents` 上传接口触发
12. ✅ 产出：上传一篇文档后，它被解析入库，并出现在文档列表里

**问答链路（rag.py）**

13. 用户提问 → 用 bge-m3 把问题向量化
14. 用问题向量在 Milvus 检索 top-k（如 k=4）最相关的片段
15. 拼 Prompt：`系统提示 + 检索到的片段 + 用户问题`，要求模型"只依据给定资料作答，并标注出处"
16. 调 DeepSeek 生成答案，SSE 流式返回（`POST /api/chat`）
17. ✅ 产出：接口能基于你的文档回答问题并带出处

**前端两个页面（frontend）**

18. **页面一·文档管理页**：上传组件 → 调 `POST /api/documents`；拉 `GET /api/documents` 渲染文档列表
    （含处理状态）；点列表项调 `GET /api/documents/{id}/file` 取原始文件，用对应渲染库（pdf.js/docx-preview/SheetJS）**按排版预览**
19. **页面二·提问页**：输入框 + 发送 → 调 `POST /api/chat`，用 SSE 流式逐字展示答案 + 引用来源
20. 用路由（如 react-router）把两页接起来，顶部加导航切换
21. ✅ 产出：**第一版完成** —— 在文档页上传并预览文档，到提问页问它并得到带出处的回答

### 验收标准（怎么算第一版做完了）

- 能在**文档管理页**上传文档、看到文档列表、预览文档内容
- 在**提问页**问一个文档里有答案的问题，能答对并给出正确出处
- 问一个文档里没有的问题，模型会说"资料中未提及"而不是乱编
- 答案是流式逐字出现的

## 六、注意事项（这些坑先知道）

1. **DeepSeek 不能做 embedding**：向量化全部走 bge-m3(SiliconFlow)。别试图用 DeepSeek 做向量化。
2. **向量维度要一致**：bge-m3 是 1024 维，建 Milvus 集合时维度必须填 1024，且检索时用的 embedding
   模型要和入库时**完全一致**，否则检索结果全是乱的。
3. **分块参数影响很大**：块太大→检索不精准、Prompt 太长；块太小→上下文被切碎。第一版用默认值，
   效果不好时优先调这里（见 02 文档的"分块"层）。
4. **工业文档多为 PDF 且含表格/图**：datasheet 常有参数表，纯文本解析可能丢表格结构。第一版先接受
   这个损失，解析质量的深入放到 02 文档的"文档解析"层。
5. **中文 / 中英混合**：bge-m3 对中文友好，没问题；Prompt 里明确要求用中文作答。
6. **让模型"忠于资料"**：Prompt 要强约束"只依据提供的资料回答，没有就说不知道"，否则会幻觉，
   这对工业参数这种严谨场景尤其重要。
7. **Milvus 要先起来**：代码连接前确认 `docker-compose up` 后 Milvus 已就绪，否则连接报错。
8. **Key 不要写进代码**：放 `.env` / 环境变量，别提交到 git。
9. **部署暂不考虑**：第一版只在 `localhost` 跑通即可，不要在这阶段纠结 GitHub Pages / 服务器。
10. **预览与解析是两件事**：预览是前端渲染**原始文件**（保排版），RAG 用的是后端抽取的**纯文本**。
    两条路各走各的，不要指望"抽取的文本"去还原排版，也不要拿"渲染用的原文件"去做检索。
11. **扫描型 PDF 的区别对待**：扫描件（整页是图片）**预览没问题**（pdf.js 照样渲染图片），但**抽不出文字**，
    RAG 检索会检索不到内容——这类文件需要 OCR 才能入库，第一版可先只预览、不纳入检索（或先跳过）。
12. **Excel/Word 抽文本的取舍**：Excel 要把表格转成"行列能对应"的文本（如每行拼成一句），否则向量化后语义混乱；
    Word 注意页眉页脚/目录等噪声。预览则交给前端渲染库，不受影响。
13. **文件体积与跨域**：原始文件通过 `/file` 返回，大文件走流式/分页；前后端分离时预览请求也要在 CORS 白名单内（部署阶段再处理）。

## 七、数据准备指引

第一版效果非常依赖你喂进去的文档质量，建议开工前先把数据理好：

- **数量**：第一版不用多，**5~15 篇**真实文档即可跑通并演示；贪多反而拖慢迭代。
- **格式优先级**：Markdown / TXT（最省心）> 文本型 PDF（可提取文字）> 扫描型 PDF（是图片，需 OCR，第一版先避开）。
- **怎么判断 PDF 能不能用**：用阅读器打开，能用鼠标**选中/复制文字**的就是文本型，能直接解析；
  整页是图片、选不中文字的是扫描型，第一版先不要用。
- **内容选择**：优先选"有明确问答价值"的，比如传感器参数表、示波器操作手册的功能章节、规格书，
  别放纯图册或封面目录。
- **整理方式**：全部放进 `data/` 目录；文件名起得有意义（如 `型号X-datasheet.pdf`），
  因为文件名后面会作为"出处"展示给用户。
- **准备几条测试问题**：顺手写下 5~10 个"你知道答案、文档里也有"的问题，留着做下面的评测。

## 八、效果评测（怎么量化 RAG 好不好）

> 只凭"感觉还行"没法迭代，也没法在面试里讲清楚。建一个小评测集，让效果**可量化、可对比**。

### 8.1 最小评测集

把上面准备的测试问题整理成一张表（放 `data/eval.jsonl` 或一个 Markdown 表），每行包含：

- `question`：问题
- `expected`：你认为正确的答案要点（关键词即可，不用整段）
- `source`：答案应该来自哪篇文档（用来检查出处对不对）

### 8.2 看三个核心指标

- **检索命中率（Recall）**：检索回来的 top-k 片段里，**有没有包含正确答案所在的片段**。
  这一步错了，后面模型再强也白搭 —— 先保证这个。
- **答案正确率**：模型最终答案是否覆盖了 `expected` 的要点（第一版可人工打分：对 / 部分对 / 错）。
- **幻觉率**：对"文档里没有"的问题，模型是否老实说"资料未提及"而不是编造。

### 8.3 怎么用

- 每次调了分块参数 / 换了检索 k 值 / 改了 Prompt，就把评测集**整批跑一遍**，对比指标变化。
- 这就是你后续深入每一层时的"验收尺子"——`02` 文档里每层的升级，都要用它来证明"确实变好了"。
- 第一版人工打分即可；想自动化时，可用一个 LLM 当"裁判"给答案打分（LLM-as-a-judge）。

## 附录 A · 配置级示例（非业务代码，仅供落地参考）

> 下面是"配置/模板"级别的示例，帮你把第一版落地，不是完整业务代码。实际数值按需调整。

### A.1 环境变量 `.env`

```ini
# 对话模型：DeepSeek
DEEPSEEK_API_KEY=sk-xxxxxxxx
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-flash

# 向量模型：SiliconFlow 的 bge-m3（DeepSeek 没有 embedding，必须用它）
SILICONFLOW_API_KEY=sk-xxxxxxxx
SILICONFLOW_BASE_URL=https://api.siliconflow.cn/v1
EMBEDDING_MODEL=BAAI/bge-m3
EMBEDDING_DIM=1024

# Milvus / Redis（本地 docker）
MILVUS_HOST=localhost
MILVUS_PORT=19530
REDIS_URL=redis://localhost:6379/0
```

> ⚠️ `.env` 不要提交到 git，加进 `.gitignore`。`EMBEDDING_DIM` 必须和建 Milvus 集合时的维度一致。

### A.2 分块参数（起步值）

```
chunk_size   = 500     # 每块约 500 字符
chunk_overlap = 50     # 相邻块重叠 50 字符，避免答案被切断
top_k        = 4       # 检索返回最相关的 4 个片段
```

> 效果不好时，优先调这三个值；系统性调法见 `02` 的"分块""检索"两层。

### A.3 RAG 系统 Prompt 模板示例

```
你是工业传感器与示波器领域的技术助手。请**只依据下面提供的资料**回答用户问题。

要求：
1. 答案必须来自资料；资料中没有的，直接说"根据现有资料无法回答"，不要编造。
2. 涉及参数、数值、型号时，务必与资料保持一致，不要臆测。
3. 用中文回答，表述清晰。
4. 在答案末尾用【出处】列出你引用了哪些资料片段（文件名/章节）。

【资料】
{context}   # 这里填入检索到的 top-k 片段

【用户问题】
{question}
```

> `{context}` 和 `{question}` 是占位符，运行时由后端填入。这个"忠于资料 + 列出处"的约束，
> 是工业问答防幻觉的关键，Prompt 的系统深入见 `02` 的"Prompt Engineering"层。

### A.4 `docker-compose.yml` 要起的服务

第一版本机需要用 Docker 起这几个服务（具体 compose 文件落地时再写）：

- **Milvus**：向量库（通常还依赖 `etcd` 和 `minio` 两个附属容器，用官方 standalone 版即可）
- **Redis**：第一版可选（做缓存）；第二阶段做会话记忆时必用

> 启动后先确认 Milvus 端口（默认 19530）可连通，再跑导入脚本，否则会连接报错（见注意事项第 7 条）。
