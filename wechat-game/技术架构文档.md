## 1. 技术目标

本项目采用数据驱动架构。

核心原则：

1. 游戏规则与关卡内容分离。
2. 物件数据与场景布局分离。
3. UI 与玩法逻辑分离。
4. 广告、存档等外部能力通过服务接口调用。
5. 普通关卡优先通过 JSON 配置完成。
6. 新增特殊玩法时，通过扩展机制模块实现，不在每个关卡中复制代码。

## 4. 模块职责

### 4.1 GameManager

负责：

- 游戏全局状态。
- 当前章节。
- 当前关卡。
- 游戏初始化。
- 游戏流程切换。

不负责具体物件点击和遮挡计算。

### 4.2 LevelManager

负责：

- 加载关卡配置。
- 检查关卡配置。
- 初始化目标。
- 初始化场景物件。
- 通知游戏进入关卡。

### 4.3 ItemController

负责：

- 单个物件的点击。
- 物件状态。
- 物件拾取动画。
- 物件移除。
- 点击事件上报。

### 4.4 TargetManager

负责：

- 当前目标列表。
- 目标物件数量。
- 已找到数量。
- 目标完成状态。
- 全部目标完成判定。

### 4.5 StorageManager

负责：

- 归位格数量。
- 当前占用物件。
- 错误物件存放。
- 容量判定。
- 清空归位格。

### 4.6 OcclusionManager

负责：

- 物件之间的遮挡关系。
- 可点击状态计算。
- 上层物件移除后的状态更新。
- 防止被遮挡物件错误响应点击。

不允许将遮挡判断分散到每个 ItemController 中。

### 4.7 HintManager

负责：

- 无操作计时。
- 提示目标选择。
- 闪烁动画触发。
- 点击后的计时重置。

### 4.8 LevelResultManager

负责：

- 通关判定。
- 失败判定。
- 星级计算。
- 结算数据。

### 4.9 SaveService

负责：

- 当前解锁关卡。
- 已通关关卡。
- 星级记录。
- 必要的玩家设置。

第一阶段使用本地存档接口，未来可以替换为云存档实现。

### 4.10 AdService

负责：

- 激励广告请求。
- 广告播放结果。
- 奖励回调。

第一阶段使用 MockAdService，不接真实广告 SDK。

### 5.5 计分与连击（v1.1 新增，Web 原型已实现）

计分只在 `GameSession` 里算，不改求解器与关卡数据：

- 找对一个目标得 100 基础分；连续找对有连击加成，每连击 +10%，上限 +50%（即第 6 连起固定 150 分）。
- 点错（进归位格）连击清零，不扣分；点被压住的物件不算点错，连击不变。
- 分数与连击随 `ClickResult`（`scoreGain`、`combo`）返回给 UI，HUD 显示分数与连击，找对时飘出“+分数”。
- 星级规则不动；结算面板显示本关分数与历史最高分，最高分进存档（见 §11.1）。

### 5.6 限时挑战模式（v1.1 新增，Web 原型已实现）

- 选关界面开关，存在存档 `settings.timedChallenge` 里，默认关闭。
- 打开后每关 120 秒倒计时，超时按失败处理（可重试）；切后台自动暂停，计时也停。
- 限时只影响 `GameSession` 的计时与失败判定，不改求解器与最少失误数。

## 6. 遮挡系统设计

### 6.1 基本原则

不能只通过物件的 ZIndex 判断是否遮挡。ZIndex 只负责绘制顺序，遮挡关系必须与画面上图标的真实重叠一致。

### 6.2 当前方案

关卡 JSON 显式记录 `blocking`（谁挡住我），由生成脚本按图标真实轮廓自动计算，校验器负责检查一致性：

```json
{ "id": "earphone_002", "layer": 1, "blocking": ["notebook_001", "key_003"] }
```

含义：`earphone_002` 被 `notebook_001` 和 `key_003` 压住，两者都被拿走后才解锁。

图标轮廓保存在 `web/src/data/item_masks.json`，由 `npm run export:icons` 导出。关卡生成、配置校验、运行时点击判定三处都读这一份轮廓。

### 6.3 遮挡计算

```typescript
function isBlocked(instance: ItemInstance): boolean {
  return instance.blocking.some((id) => isInScene(id));
}
```

注意：

- 被遮挡物件可能同时被多个物件遮挡，移除其中一个不一定马上解锁。
- 必须确认所有遮挡者都已移除。
- 点击判定只认图标本体，点在图标透明处会落到下面的物件上。

## 7. 游戏状态机

### 7.1 游戏主状态

```typescript
export enum GameState {
  INIT = "INIT",
  LOADING = "LOADING",
  READY = "READY",
  PLAYING = "PLAYING",
  PAUSED = "PAUSED",
  SUCCESS = "SUCCESS",
  FAILED = "FAILED"
}
```

### 7.2 状态流程

```text
INIT
  ↓
LOADING
  ↓
READY
  ↓
PLAYING
  ├── 所有目标完成 → SUCCESS
  ├── 归位格满 → FAILED
  └── 点击暂停 → PAUSED
                    ↓
                  PLAYING
```

### 7.3 状态约束

- SUCCESS 状态不能继续拾取物件。
- FAILED 状态不能继续拾取物件。
- PAUSED 状态不能触发游戏逻辑。
- 重开关卡必须重置所有物件状态。
- 切换关卡必须清理上一关的计时器和事件监听。

### 7.4 限时挑战的状态补充（v1.1 新增）

- 限时模式下 `PLAYING` 状态多一个 120 秒倒计时，`session.timeLeft` 每帧递减；到 0 时进入 `FAILED`，失败原因记为 `timeout`（与归位格放弃的失败区分，面板文案不同）。
- 切后台自动暂停时计时冻结，恢复后继续；重开关卡重置计时。

## 11. 存档设计

第一阶段建议保存：

```json
{
  "version": 1,
  "chapterId": "chapter_01",
  "unlockedLevel": 1,
  "completedLevels": [],
  "stars": {},
  "settings": {
    "musicEnabled": true,
    "soundEnabled": true
  }
}
```

存档要求：

- 有版本号。
- 读取失败时可以恢复默认值。
- 保存过程不能阻塞游戏主流程。
- 不直接把复杂业务对象整体序列化。
- 存档字段变更时考虑兼容旧版本。

### 11.1 存档 v2（v1.1 新增，Web 原型已实现）

v1 只有通关快照（解锁、星级），v2 增加：

```json
{
  "version": 2,
  "bestScores": { "level_001": 1250 },
  "inProgress": {
    "levelId": "level_003",
    "collected": ["milk_tea_cup_001"],
    "storage": ["key_002"],
    "hintUses": 1,
    "score": 210,
    "combo": 2
  },
  "settings": { "soundEnabled": true, "timedChallenge": false }
}
```

- `inProgress` 是关卡中断点快照：切后台/退出时保存，重进该关可“继续”或“重新开始”；通关后清除。
- `loadSave` 接受 v1 存档并原地升级为 v2（保留星级与解锁，`bestScores` 为空、`inProgress` 为空，不丢老进度）；版本号不是 1 或 2、或关键字段损坏时回默认存档。
- 注：技术架构 v1.0 的存档示例里还有 `musicEnabled`，代码里从来只有 `soundEnabled`（音效开关同时管震动，没有独立的音乐开关），以代码为准。

## 12. 架构边界

以下做法禁止：

1. 每关写一个独立玩法脚本。
2. 在 UI 脚本中直接修改核心游戏状态。
3. 在 ItemController 中判断全部目标是否完成。
4. 将广告 SDK 代码写进拾取逻辑。
5. 将关卡物件数量写死在代码里。
6. 用节点名称代替物件 ID。
7. 依赖场景节点顺序推断关卡目标。
8. 通过隐藏或透明度代替物件状态。

## 13. 技术验收标准

- 能够通过 JSON 加载 10 个关卡。
- 目标数量由配置决定。
- 物件位置由配置决定。
- 遮挡关系由配置决定。
- 拾取逻辑只实现一套。
- 普通关卡无需修改核心代码。
- 重开关卡能够完整重置。
- 事件监听没有重复触发。
- 存档能够正常保存和读取。
- 广告服务可以在 Mock 与真实实现之间替换。
