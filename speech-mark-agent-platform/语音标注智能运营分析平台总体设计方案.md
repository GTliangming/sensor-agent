# 一、项目背景与目标

## 1.1 项目背景

目前已经拥有一套完整的语音标注业务平台，包含：

- Vue3 前端管理系统
- Go 后端服务
- 完整的标注业务流程
- 任务、题包、题目管理
- 标注人员及工作组管理
- 标注、审核、流转等业务功能
- 现有数据库及业务数据

现在计划在现有业务平台之外，单独建设一个 Agent 智能运营分析平台。

新项目不直接修改原有 Go 服务，也不嵌入原有 Vue 前端，而是作为一套独立系统，通过 HTTP API 对接现有标注平台。

Agent 的核心职责不是简单地回答用户问题，而是：

1. 理解用户提出的业务问题。
2. 自主规划需要查询的数据。
3. 调用一个或多个业务工具。
4. 获取真实业务数据。
5. 对数据进行统计、分析和交叉验证。
6. 发现业务异常和潜在风险。
7. 给出有数据依据的分析结论和优化建议。
8. 生成运营报告。

## 1.2 项目核心定位

建设一个服务于语音标注业务的企业级智能运营分析平台。

第一阶段采用严格的只读模式：

- 可以查询标注平台的业务数据。
- 可以分析和统计业务数据。
- 可以调用多个只读工具。
- 可以进行多步骤任务规划。
- 可以生成业务建议和分析报告。
- 可以保存 Agent 自身的对话和执行记录。
- 不允许修改标注平台任何业务数据。

**第一阶段不开发任何真实业务写入能力。**

## 1.3 项目建设目标

本项目同时承担两个目标。

### 目标 A：解决真实业务问题

让 Agent 真正参与日常标注业务运营，减少人工查询、统计、分析和整理报告的工作。

### 目标 B：系统学习企业级 Agent 开发

通过真实业务场景，掌握：

- LLM 应用开发
- Prompt Engineering
- Function Calling / Tool Calling
- LangChain
- LangGraph
- Agent 状态管理
- 多步骤任务规划
- RAG 知识库
- Memory 记忆系统
- 多 Agent 协作原理
- Agent 评估体系
- 权限控制
- 异常处理
- 执行追踪和监控

学习方式采用原理讲解、业务设计、代码实现、运行验证相结合的方式。

# 二、总体架构设计

## 2.1 系统架构

整个系统由两个完全独立的项目组成。

### 项目 A：现有语音标注平台

技术栈：

- 前端：Vue3
- 后端：Go
- 数据库：现有业务数据库
- 缓存：现有 Redis
- 其他：沿用现有业务基础设施

职责：

- 标注业务管理
- 任务管理
- 题包管理
- 人员管理
- 工作组管理
- 标注及审核流程
- 业务数据存储

保持现有系统稳定，不为了 Agent 重构成熟业务代码。

### 项目 B：Speech Mark Agent Platform

技术栈：

| 模块 | 技术 |
|---|---|
| 前端 | React 19 |
| UI | Ant Design |
| 后端 | Python 3.12 + FastAPI |
| Agent Framework | LangChain |
| 工作流 | LangGraph |
| LLM | DeepSeek API |
| 数据库 | SQLite |
| 数据访问 | SQLAlchemy |
| 数据校验 | Pydantic |
| 向量检索 | 第一阶段按需选择 |
| 测试 | Pytest |
| 日志 | Python Logging / 结构化日志 |

职责：

- 智能业务问答
- 业务数据查询
- 多步骤任务规划
- 统计分析
- 异常检测
- 运营报告
- 知识库管理
- 对话记忆
- Agent 执行追踪
- Agent 质量评估

## 2.2 系统关系

两个项目之间只通过 HTTP API 通信。

Agent 不直接连接现有标注平台数据库。

## 2.3 数据隔离原则

必须区分两类数据：

**第一类：标注平台业务数据**

包括任务、题包、题目、人员、审核记录等。

Agent 只能通过经过授权的 Go API 读取。

**第二类：Agent 自身的数据**

包括：

- 用户对话
- 对话历史
- Agent 执行记录
- 工具调用记录
- 分析报告
- 用户偏好
- 知识库元数据

这些数据由 Agent 自己的数据库管理。

Agent 可以正常维护自己的数据，但不能借此修改标注平台的业务数据。

# 三、Agent 业务能力设计

第一阶段围绕五个核心业务方向建设。

## 3.1 业务数据查询

目标：让用户通过自然语言查询标注平台数据。

主要功能：

- 查询任务列表
- 查询任务详情
- 查询题包信息
- 查询题目状态
- 查询标注人员
- 查询工作组
- 查询任务进度
- 查询审核记录
- 查询历史流转记录

示例：

用户：

> 帮我查询目前所有正在进行中的任务。

Agent：

1. 理解用户查询意图。
2. 识别需要的业务数据。
3. 调用任务查询工具。
4. 获取真实数据。
5. 整理并返回结果。

需要支持：

- 时间范围筛选
- 状态筛选
- 人员筛选
- 工作组筛选
- 分页查询
- 多条件组合查询

## 3.2 业务统计分析

目标：从业务数据中提取运营指标。

主要分析方向：

### 任务维度

- 任务总量
- 任务完成数量
- 任务完成率
- 任务延期数量
- 平均任务完成时间

### 人员维度

- 人员任务数量
- 人员完成数量
- 人员完成效率
- 人员审核通过率
- 人员工作量分布

### 工作组维度

- 工作组任务总量
- 工作组完成率
- 工作组效率
- 工作组人员负载
- 工作组审核情况

### 审核维度

- 审核总量
- 审核通过率
- 审核退回率
- 平均审核耗时
- 退回原因分布

要求：

尽量使用 Go API 或确定性的 Python 数据计算完成统计，不要让 LLM 凭空计算数据。

LLM 主要负责理解问题、组织分析和解释结果。

## 3.3 异常检测与问题诊断

目标：主动发现业务中存在的问题。

典型场景：

- 长时间没有进展的任务
- 接近截止时间但完成率较低的任务
- 标注人员工作量异常
- 审核退回率明显升高
- 工作组任务完成效率下降
- 任务流转时间异常
- 人员工作量分布不均

异常检测分为两类：

**规则型检测**

通过明确业务规则和阈值判断。

例如：

- 超过规定时间没有更新的任务。
- 完成率低于设定阈值的任务。
- 审核退回率超过指定阈值的人员。

**智能分析型检测**

结合历史数据和业务上下文分析异常原因。

注意：异常不等于因果关系。Agent 必须区分真实数据、推测原因和待验证假设。

## 3.4 业务建议

目标：根据真实数据给出运营优化建议。

例如：

用户：

> 最近哪些工作组的工作效率比较低？有什么改善建议？

Agent：

1. 查询各工作组任务情况。
2. 统计各工作组完成率。
3. 对比历史周期。
4. 查询人员负载。
5. 查询审核退回率。
6. 分析可能影响因素。
7. 给出优化建议。

建议必须说明：

- 发现了什么问题。
- 数据依据是什么。
- 为什么认为这是问题。
- 建议采取什么措施。
- 哪些结论还需要人工验证。

Agent 只提出建议，不执行建议。

## 3.5 智能报告

目标：自动生成业务运营报告。

报告类型：

- 每日运营报告
- 每周运营报告
- 月度运营报告
- 项目进度报告
- 人员效率分析报告
- 工作组效率分析报告
- 异常风险报告

报告需要支持：

- 标题
- 统计周期
- 核心指标
- 数据图表
- 异常情况
- 原因分析
- 优化建议
- 数据来源及统计口径

# 四、Agent 核心技术架构

## 4.1 Agent Core

Agent Core 是整个系统的核心。

负责：

- 接收用户请求
- 识别用户意图
- 组织上下文
- 规划执行步骤
- 调用工具
- 管理执行状态
- 处理异常
- 生成最终结果

建议初期使用单 Agent + LangGraph。

不要一开始就引入多个 Agent。

## 4.2 LangGraph 工作流

第一阶段需要掌握 LangGraph 的核心概念。

包括：

- State
- Node
- Edge
- Conditional Edge
- Reducer
- Checkpoint
- Interrupt
- Retry
- Subgraph

建议初期设计以下工作流：

```text
START
  |
  v
接收用户请求
  |
  v
意图识别
  |
  v
任务规划
  |
  v
判断是否需要工具
  |
  +------ 不需要 ------> 直接生成回答
  |
  v
选择查询工具
  |
  v
执行工具调用
  |
  v
结果验证
  |
  +------ 数据不足 ------> 补充查询
  |
  v
数据分析
  |
  v
生成回答
  |
  v
END
```

后续逐步增加：

- 多工具并行查询
- 任务拆解
- 条件路由
- 超时控制
- 失败重试
- Checkpoint
- 人工确认节点

注意：第一阶段的人工确认主要用于报告确认、分析过程确认和信息补充，不用于执行标注业务修改。

## 4.3 Tool Calling

工具系统是 Agent 与真实业务系统交互的核心。

建议将工具划分为以下模块：

```text
tools/
├── business/
│   ├── task_tools.py
│   ├── package_tools.py
│   ├── question_tools.py
│   ├── user_tools.py
│   ├── group_tools.py
│   └── audit_tools.py
│
├── statistics/
│   ├── task_statistics.py
│   ├── workload_statistics.py
│   └── audit_statistics.py
│
├── analysis/
│   ├── efficiency_analysis.py
│   ├── risk_analysis.py
│   └── anomaly_analysis.py
│
└── common/
    ├── time_tools.py
    └── data_validation.py
```

工具设计要求：

1. 一个工具尽量负责一个明确的业务能力。
2. 参数必须通过 Pydantic 校验。
3. 明确返回数据结构。
4. 设置超时。
5. 支持错误处理。
6. 记录工具调用日志。
7. 对查询结果进行分页和数量限制。
8. 工具只能通过授权的只读 API 获取数据。

## 4.4 Go API Integration

Python Agent 通过独立的 API Client 对接 Go 服务。

建议结构：

```text
integrations/
└── speech_mark/
    ├── client.py
    ├── auth.py
    ├── task_api.py
    ├── package_api.py
    ├── user_api.py
    ├── group_api.py
    ├── audit_api.py
    └── schemas.py
```

要求：

- 统一 HTTP 请求封装。
- 统一身份认证。
- 统一错误处理。
- 请求超时控制。
- 适当的重试机制。
- 响应数据校验。
- 分页处理。
- 数据权限校验。
- 请求日志及追踪 ID。

Go API 应尽可能提供适合 Agent 查询的结构化数据接口。

不建议 Agent 自己拼接大量底层业务 API，更不允许直接执行 SQL 查询原有业务数据库。

## 4.5 RAG 知识库

RAG 用于补充业务数据无法直接提供的信息。

建议知识库内容：

- 标注业务规则
- 任务管理规则
- 题包管理规则
- 审核规则
- 人员工作组规则
- 业务操作说明
- 常见问题
- 平台使用文档
- 运营管理规范

典型流程：

```text
用户问题
   |
   v
问题理解
   |
   v
知识检索
   |
   v
相关文档召回
   |
   v
上下文组织
   |
   v
LLM 分析
```

需要明确：

RAG 负责检索业务知识，Go API 负责提供实时业务数据。

两者不能混淆。

第一阶段不必急于引入复杂向量数据库。先建立文档管理、切片、检索和引用能力，再根据实际检索效果决定向量存储方案。

## 4.6 Memory

记忆系统分为三类：

### 对话记忆

保存当前会话的历史消息，支持连续对话。

### 用户偏好记忆

保存用户长期有效的使用偏好。

例如：

- 默认关注的工作组。
- 常用统计周期。
- 常用分析指标。
- 报告输出习惯。

### 执行记忆

保存任务执行过程中的必要状态，例如：

- 已经查询了哪些数据。
- 当前分析进度。
- 已经完成哪些步骤。
- 哪些步骤失败。

注意：

执行状态不应该全部塞进长期记忆。需要结合 LangGraph State、Checkpoint 和数据库进行管理。

# 六、数据库设计

第一阶段使用 SQLite。

数据库只保存 Agent 自身的数据，不保存现有标注平台的业务数据副本作为权威数据源。

建议初期设计以下表：

| 表名 | 用途 |
|---|---|
| users | Agent 平台用户 |
| conversations | 会话信息 |
| messages | 对话消息 |
| agent_runs | Agent 执行记录 |
| tool_calls | 工具调用记录 |
| checkpoints | LangGraph 状态持久化 |
| user_preferences | 用户偏好 |
| knowledge_documents | 知识库文档 |
| knowledge_chunks | 知识切片 |
| analysis_reports | 分析报告 |
| evaluation_records | Agent 评估记录 |
| system_configs | 系统配置 |

数据库设计要求：

1. 统一主键设计。
2. 重要数据包含创建时间和更新时间。
3. 重要执行记录保留状态。
4. 合理设计索引。
5. 对话和执行记录支持分页。
6. 对长期数据设计清理策略。
7. 通过 Repository / Service 隔离数据库实现。

SQLite 先满足本地开发和第一阶段使用需求，后续根据部署和并发需求再评估数据库迁移。

# 七、安全与权限设计

虽然第一阶段只有读取能力，但仍然必须建立企业级安全机制。

## 7.1 身份认证

Agent 平台需要有自己的用户身份体系，或者在后续阶段接入现有统一认证。

Agent 调用 Go API 时，必须使用明确授权的身份凭证。

## 7.2 数据权限

不能因为 Agent 能够调用 API，就默认它可以读取所有业务数据。

需要遵循：

- 当前用户身份。
- 当前用户业务权限。
- 工作组数据范围。
- 项目数据范围。
- 其他现有业务隔离规则。

最终由 Go 服务端执行真实权限校验。

## 7.3 只读安全边界

第一阶段必须做到：

1. Agent 不注册任何标注平台写入工具。
2. Go 服务提供专门的只读 API。
3. Agent 使用独立的只读凭证。
4. 不允许直接连接标注平台数据库。
5. 不允许通过 SQL、脚本等方式绕过 API。
6. 对外部 API 请求实施白名单限制。
7. 对查询数量、分页和执行时间进行限制。
8. 对敏感业务数据进行脱敏处理。

不能仅仅依靠 System Prompt 告诉模型不要修改数据。

安全必须在代码、身份凭证和服务端权限层真正实现。

# 八、项目开发路线

开发采用逐步推进的方式。

每个版本都必须是一个能够运行、能够验证的完整功能。

## V0.1：项目基础架构

目标：搭建独立 Agent 项目。

开发内容：

- 创建独立 Git 仓库。
- 创建 React 项目。
- 创建 Python FastAPI 项目。
- 建立前后端通信。
- 配置 DeepSeek API。
- 建立 SQLite 数据库。
- 建立统一配置管理。
- 建立日志系统。
- 建立基础页面。

验收标准：

- 前端可以正常访问。
- 后端 API 正常运行。
- 可以成功调用模型。
- 可以完成基础 AI 对话。
- 可以保存对话记录。

## V0.2：Agent 与 LangGraph

目标：掌握 Agent 基础运行机制。

开发内容：

- LangChain 模型封装。
- LangGraph State。
- Node 和 Edge。
- Conditional Edge。
- Reducer。
- 基础工作流。
- 对话状态管理。
- Checkpoint。

验收标准：

- 能够运行完整的 LangGraph 工作流。
- 能够保存和恢复会话状态。
- 能够处理不同类型的用户请求。
- 能够观察工作流执行过程。

## V0.3：只读 Tool Calling

目标：让 Agent 具备调用业务工具的能力。

开发内容：

- Tool Registry。
- 工具定义。
- Pydantic 参数校验。
- 工具路由。
- 工具调用。
- 结果处理。
- 异常处理。
- 工具执行日志。

第一阶段可以先用模拟业务数据验证工具体系。

随后接入真实 Go API。

验收标准：

- Agent 能识别需要使用的工具。
- 能够正确传递工具参数。
- 能够处理工具返回结果。
- 能够连续调用多个工具。
- 不存在任何标注业务写入工具。

## V0.4：真实 Go API 集成

目标：接入现有标注平台。

开发内容：

- API Client。
- 统一身份认证。
- 任务查询。
- 题包查询。
- 人员查询。
- 工作组查询。
- 审核数据查询。
- 进度查询。
- 分页和筛选。
- 权限校验。

验收标准：

- 可以读取真实业务数据。
- 查询结果与原平台一致。
- 权限范围符合当前用户身份。
- API 异常时能够正确处理。
- 所有接口保持只读。

## V0.5：多步骤业务分析

目标：从简单查询升级为复杂业务分析。

开发内容：

- 任务规划。
- 多工具协作。
- 多步骤执行。
- 多工具并行查询。
- 数据聚合。
- 数据交叉验证。
- 结果可靠性检查。
- 分析报告生成。

验收场景：

> 分析最近一周各工作组的工作效率，找出效率较低的工作组，并分析可能的原因。

Agent 应能够自主拆分查询任务，获取相关数据，进行对比分析，最后给出依据充分的结论。

## V0.6：RAG 知识库

目标：让 Agent 理解标注平台的业务规则。

开发内容：

- 文档上传。
- 文档解析。
- 文档切片。
- Embedding。
- 向量检索或其他合适的检索方式。
- 关键词检索。
- 混合检索。
- Rerank（按需）。
- 检索结果引用。
- 检索质量评估。

验收标准：

Agent 能够结合业务规则和真实业务数据回答复杂问题。

## V0.7：Memory 记忆系统

目标：支持长期、连续的业务对话。

开发内容：

- 会话记忆。
- 用户偏好。
- 长期记忆。
- Checkpoint。
- 上下文压缩。
- 历史信息检索。
- 记忆更新策略。

验收标准：

- 能够记住当前会话上下文。
- 能够在新会话中使用经过保存的用户偏好。
- 不会将无关历史信息混入当前回答。
- 能够正确恢复中断的工作流。

## V0.8：异常检测与智能运营分析

目标：让 Agent 从被动查询升级为主动发现问题。

开发内容：

- 规则型异常检测。
- 指标阈值管理。
- 历史周期对比。
- 人员负载分析。
- 审核异常分析。
- 任务延期风险分析。
- 业务建议生成。

验收标准：

Agent 能够发现明确的异常，并提供可追溯的数据依据。

## V0.9：企业级可靠性与可观测性

目标：使系统具备稳定运行能力。

开发内容：

- 完整执行追踪。
- 工具调用监控。
- 模型调用监控。
- Token 成本统计。
- 超时处理。
- 有限重试。
- 错误恢复。
- Checkpoint 恢复。
- Agent 评估体系。
- Prompt 版本管理。
- 工具测试。
- 安全测试。

验收标准：

- 关键执行步骤可追踪。
- 工具失败有明确错误信息。
- 能够定位 Agent 分析错误的原因。
- 具备可重复运行的评估测试。
- 能够持续验证分析质量。

## V1.0：只读智能运营平台

目标：形成一套完整可用的企业级只读 Agent 系统。

完整能力：

- 真实业务数据查询。
- 复杂业务分析。
- 多工具调用。
- 多步骤规划。
- RAG 知识库。
- Memory。
- 异常检测。
- 运营报告。
- 执行追踪。
- 权限管理。
- 系统监控。
- Agent 质量评估。

V1.0 的核心验收标准：

**Agent 能够稳定、准确地理解业务问题，调用真实业务 API，完成复杂查询和分析，并给出有数据依据的结论。**

V1.0 不包含标注平台业务写入能力。

# 九、项目开发原则

## 9.1 不为了使用技术而使用技术

每一项技术都必须解决实际问题。

例如：

- 简单查询不必设计复杂 LangGraph。
- 数据统计优先使用确定性计算。
- 不要一开始就引入多 Agent。
- 不要一开始就引入 Redis。
- 不要一开始就建设复杂的分布式架构。
- RAG 应由实际知识检索需求驱动。
- Memory 应由真实连续对话需求驱动。

## 9.2 坚持真实业务验证

尽量使用现有标注平台的真实只读 API。

模拟数据可以用于早期开发和测试，但不能代替真实业务验收。

## 9.3 重视原理和设计能力

学习过程中重点掌握：

- 为什么需要某项技术。
- 它解决什么问题。
- 不使用它会怎样。
- 有哪些替代方案。
- 在真实业务中如何设计。
- 如何验证实现是否正确。

不以记住 API 和语法为最终目标。

## 9.4 采用渐进式架构

先单 Agent，再复杂工作流，最后根据实际需求考虑多 Agent。

先 SQLite，再根据实际部署需求考虑其他数据库。

先同步查询，再根据实际需要考虑异步任务和消息队列。

## 9.5 每个版本都必须完成验证

每个版本都必须提供：

- 业务需求。
- 技术原理。
- 架构设计。
- 实现步骤。
- 关键代码。
- 测试方案。
- 验收标准。
- 常见问题。

# 十一、未来扩展：业务写入与自动执行能力

**本章节只作为未来规划，不属于当前开发范围。**

必须等到 V1.0 只读系统已经完成，并且经过充分的业务验证、安全评估和稳定性测试后，才考虑这一阶段。

不提前开发真实写入工具，不提前开放业务修改权限。

## 11.1 为什么未来可能需要写入能力

只读 Agent 负责：

- 发现问题。
- 分析原因。
- 制定方案。
- 提供建议。

但无法直接完成业务操作。

未来如果需要进一步提高运营自动化程度，可以考虑：

- 智能任务分配。
- 题包分配建议及执行。
- 异常任务处理。
- 业务流程流转。
- 审核任务辅助处理。
- 运营策略执行。

## 11.2 未来需要学习的技术

| 技术 | 解决的问题 |
|---|---|
| Human-in-the-loop | 执行前人工审批 |
| 幂等性 | 防止重复执行 |
| 数据库事务 | 保证业务数据一致性 |
| 乐观锁 | 避免并发状态冲突 |
| 状态机 | 管理复杂业务流转 |
| 补偿机制 | 处理部分执行失败 |
| 操作审计 | 记录完整执行过程 |
| 权限控制 | 限制 Agent 可执行的操作 |
| Checkpoint | 支持中断后的任务恢复 |

## 11.3 未来执行流程

```text
用户提出业务需求
       |
       v
Agent 理解需求
       |
       v
查询真实业务数据
       |
       v
分析并制定执行方案
       |
       v
展示执行计划
       |
       v
人工审批
       |
       v
执行权限校验
       |
       v
调用 Go 业务 API
       |
       v
验证执行结果
       |
       v
记录审计日志
       |
       v
返回执行结果
```

## 11.4 写入能力开放原则

未来开放时，必须遵守：

1. 不能因为 Agent 能够分析数据，就默认它有修改数据的权限。
2. 所有写入操作必须经过独立的权限校验。
3. 高风险操作必须经过人工审批。
4. 重要操作必须支持幂等控制。
5. 涉及业务状态变化时必须遵循现有 Go 服务的业务规则。
6. 不能绕过现有业务 API 直接修改数据库。
7. 所有操作必须有完整审计记录。
8. 失败时必须有明确的恢复或补偿方案。
9. 从低风险、低影响的操作开始逐步开放。
10. 保留随时关闭 Agent 写入能力的机制。

**未来写入能力应作为独立版本建设，不能影响已经稳定运行的只读 Agent。**

# 十二、最终结论

Speech Mark Agent Platform 的建设顺序正式确定为：

**第一步：建设完整的只读 Agent。**

**第二步：完善业务分析能力、可靠性、安全性和可观测性。**

**第三步：验证系统真正能够解决实际运营问题。**

**最后：根据实际业务价值，再考虑是否增加写入与自动执行能力。**

整个项目坚持：

- 独立项目。
- 独立前端。
- 独立后端。
- 独立数据库。
- 真实 Go API 集成。
- 第一阶段严格只读。
- 逐步学习企业级 Agent 技术。
- 以真实业务价值驱动技术选型。

最终目标不是做一个能调用大模型的聊天机器人，而是建设一套能够理解业务、获取数据、分析问题、发现风险并辅助运营决策的企业级 Agent 平台。
