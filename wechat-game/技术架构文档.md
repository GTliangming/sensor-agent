# 《一屋百年》技术架构文档

- 文档版本：v1.0
- 引擎：Cocos Creator 3.8.8
- 语言：TypeScript
- 目标平台：微信小游戏
- 当前开发范围：第一章 10 关

---

## 1. 技术目标

本项目采用数据驱动架构。

核心原则：

1. 游戏规则与关卡内容分离。
2. 物件数据与场景布局分离。
3. UI 与玩法逻辑分离。
4. 广告、存档等外部能力通过服务接口调用。
5. 普通关卡优先通过 JSON 配置完成。
6. 新增特殊玩法时，通过扩展机制模块实现，不在每个关卡中复制代码。

## 4. 模块职责

### 4.1 GameManager

负责：

- 游戏全局状态。
- 当前章节。
- 当前关卡。
- 游戏初始化。
- 游戏流程切换。

不负责具体物件点击和遮挡计算。

### 4.2 LevelManager

负责：

- 加载关卡配置。
- 检查关卡配置。
- 初始化目标。
- 初始化场景物件。
- 通知游戏进入关卡。

### 4.3 ItemController

负责：

- 单个物件的点击。
- 物件状态。
- 物件拾取动画。
- 物件移除。
- 点击事件上报。

### 4.4 TargetManager

负责：

- 当前目标列表。
- 目标物件数量。
- 已找到数量。
- 目标完成状态。
- 全部目标完成判定。

### 4.5 StorageManager

负责：

- 归位格数量。
- 当前占用物件。
- 错误物件存放。
- 容量判定。
- 清空归位格。

### 4.6 OcclusionManager

负责：

- 物件之间的遮挡关系。
- 可点击状态计算。
- 上层物件移除后的状态更新。
- 防止被遮挡物件错误响应点击。

不允许将遮挡判断分散到每个 ItemController 中。

### 4.7 HintManager

负责：

- 无操作计时。
- 提示目标选择。
- 闪烁动画触发。
- 点击后的计时重置。

### 4.8 LevelResultManager

负责：

- 通关判定。
- 失败判定。
- 星级计算。
- 结算数据。

### 4.9 SaveService

负责：

- 当前解锁关卡。
- 已通关关卡。
- 星级记录。
- 必要的玩家设置。

第一阶段使用本地存档接口，未来可以替换为云存档实现。

### 4.10 AdService

负责：

- 激励广告请求。
- 广告播放结果。
- 奖励回调。

第一阶段使用 MockAdService，不接真实广告 SDK。

## 6. 遮挡系统设计

### 6.1 基本原则

不能只通过物件的 ZIndex 判断是否遮挡。

ZIndex 主要负责绘制顺序，遮挡关系还需要结合物件覆盖区域。

### 6.2 第一阶段方案

优先使用显式遮挡关系配置。

例如：

```json
{
  "instanceId": "item_002",
  "itemId": "earphone",
  "layer": 2,
  "blocks": ["item_005", "item_006"]
}
```

含义：

item_002 当前遮挡 item_005 和 item_006。

当 item_002 被拾取后，重新检查 item_005 和 item_006 是否还有其他遮挡物。

如果没有其他遮挡物，则解锁。

### 6.3 遮挡计算

伪代码：

```typescript
function isItemBlocked(itemId: string): boolean {
  const blockers = getActiveBlockers(itemId);

  return blockers.length > 0;
}
```

注意：

- 被遮挡物件可能同时被多个物件遮挡。
- 移除其中一个遮挡物后，不一定马上解锁。
- 必须确认所有有效遮挡物都已移除。

第一阶段先使用 JSON 显式配置，后续再考虑根据多边形区域自动计算。

## 7. 游戏状态机

### 7.1 游戏主状态

```typescript
export enum GameState {
  INIT = "INIT",
  LOADING = "LOADING",
  READY = "READY",
  PLAYING = "PLAYING",
  PAUSED = "PAUSED",
  SUCCESS = "SUCCESS",
  FAILED = "FAILED"
}
```

### 7.2 状态流程

```text
INIT
  ↓
LOADING
  ↓
READY
  ↓
PLAYING
  ├── 所有目标完成 → SUCCESS
  ├── 归位格满 → FAILED
  └── 点击暂停 → PAUSED
                    ↓
                  PLAYING
```

### 7.3 状态约束

- SUCCESS 状态不能继续拾取物件。
- FAILED 状态不能继续拾取物件。
- PAUSED 状态不能触发游戏逻辑。
- 重开关卡必须重置所有物件状态。
- 切换关卡必须清理上一关的计时器和事件监听。

## 8. 核心交互流程

### 正确拾取

```text
玩家点击
  ↓
检查游戏状态
  ↓
检查物件是否可点击
  ↓
判断是否属于目标
  ↓
播放正确拾取动画
  ↓
目标进度 +1
  ↓
移除物件
  ↓
刷新遮挡
  ↓
检查通关
```

### 错误拾取

```text
玩家点击
  ↓
检查游戏状态
  ↓
检查物件是否可点击
  ↓
判断不属于目标
  ↓
归位格容量检查
  ↓
加入归位格
  ↓
移除场景物件
  ↓
刷新遮挡
  ↓
检查失败
```

## 9. 事件设计

建议使用统一事件系统。

事件名称：

| 事件                    | 触发时机     |
| ----------------------- | ------------ |
| LEVEL_LOADED            | 关卡加载完成 |
| ITEM_CLICKED            | 玩家点击物件 |
| ITEM_COLLECTED          | 正确拾取     |
| ITEM_MISSED             | 错误拾取     |
| TARGET_PROGRESS_CHANGED | 目标进度变化 |
| STORAGE_CHANGED         | 归位格变化   |
| ITEM_UNLOCKED           | 物件解除遮挡 |
| HINT_TRIGGERED          | 提示触发     |
| LEVEL_COMPLETED         | 关卡完成     |
| LEVEL_FAILED            | 关卡失败     |
| LEVEL_RESTARTED         | 关卡重开     |

事件监听必须在组件销毁时解除，避免重复监听。

## 10. 资源加载

第一阶段：

- 关卡配置按需加载。
- 物件资源通过统一资源映射加载。
- 不允许在业务代码中散落大量硬编码资源路径。
- 资源加载失败时显示明确错误日志。
- 关卡加载完成后再进入 READY 状态。

未来资源量增加后，再评估分包和资源远程加载。

## 11. 存档设计

第一阶段建议保存：

```json
{
  "version": 1,
  "chapterId": "chapter_01",
  "unlockedLevel": 1,
  "completedLevels": [],
  "stars": {},
  "settings": {
    "musicEnabled": true,
    "soundEnabled": true
  }
}
```

存档要求：

- 有版本号。
- 读取失败时可以恢复默认值。
- 保存过程不能阻塞游戏主流程。
- 不直接把复杂业务对象整体序列化。
- 存档字段变更时考虑兼容旧版本。

## 12. 架构边界

以下做法禁止：

1. 每关写一个独立玩法脚本。
2. 在 UI 脚本中直接修改核心游戏状态。
3. 在 ItemController 中判断全部目标是否完成。
4. 将广告 SDK 代码写进拾取逻辑。
5. 将关卡物件数量写死在代码里。
6. 用节点名称代替物件 ID。
7. 依赖场景节点顺序推断关卡目标。
8. 通过隐藏或透明度代替物件状态。

## 13. 技术验收标准

- 能够通过 JSON 加载 10 个关卡。
- 目标数量由配置决定。
- 物件位置由配置决定。
- 遮挡关系由配置决定。
- 拾取逻辑只实现一套。
- 普通关卡无需修改核心代码。
- 重开关卡能够完整重置。
- 事件监听没有重复触发。
- 存档能够正常保存和读取。
- 广告服务可以在 Mock 与真实实现之间替换。
